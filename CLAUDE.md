# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Marv (the `marv` command) is a terminal coding agent (like Claude Code) written in TypeScript on **Bun** with an **Ink** (React-for-terminal) TUI. It is being built milestone by milestone; the roadmap lives in `~/.claude/plans/im-planning-on-making-staged-eclipse.md`. The owner is learning how agents work, so explain the *why* of each change.

Issue work run by agents (a planner, an orchestrator, workers in Herdr worktrees) follows `ORCHESTRATION.md`: it binds the orchestrator, and a worker only needs its `TASK.md` brief.

## Commands

```sh
bun install
bun run dev                 # run the TUI from source (same as `marv`)
bun test                    # all tests
bun test tests/commands     # one file (path substring filter)
bun test -t "streams"       # tests whose name matches
bun run typecheck           # tsc --noEmit (examples/ included)
bun examples/sdk.ts "question"   # the SDK, from code (needs OPENROUTER_API_KEY)
bun run stats               # sum up trajectory logs (--by model|marv)
bun run eval --verify       # eval tasks: each check fails before, passes with its solution
bun run eval --models a,b --label x [--repeat 3 --budget 1]   # real models (OpenRouter), see evals/run.ts
bun link                    # (once) puts `marv` on PATH (bin/marv → src/cli.tsx) — no build step
```

## Architecture

- `bin/marv` is the `bin` entry: a bash launcher that runs `src/cli.tsx` with `exec -a marv`, so the process is named `marv`, not `bun` (VS Code's terminal tab shows argv[0]). `src/cli.tsx` also sets the terminal title with OSC 0. It handles `--version`/`--help`, takes the project root from the current directory, reads the project's `AGENTS.md` once (`loadInstructions` in `src/prompt.ts`, capped at 20k chars), then renders `<App>`.
- **Config (`src/config/config.ts`)**: two layers, later wins: `~/.marv/config.json` (zod-validated, written with mode 0600 because it can hold the API key), then env vars (`OPENROUTER_API_KEY`, `MARV_MODEL`, `OLLAMA_HOST`, `MARV_MAX_STEPS` for the step limit; `/steps` sets and shows it). `mcpTools` (`auto`/`deferred`/`eager`, file only, no slash command) says how MCP tools are offered (see **MCP servers**). `PRESETS` describes each provider (label, base URL, which env var holds its key, default model). `FileConfig` is what's on disk; `resolveConfig()` produces the `Config` the app runs on. `MARV_CONFIG_DIR` relocates the config, so use it when testing by hand to keep your real config untouched.
- **Setup (`src/ui/Setup.tsx`)** runs on first run, or when OpenRouter has no key, and again via `/setup` (and `/model`, starting at the model step). It renders *in place of the prompt* (pinned at the bottom, below the transcript), not as a separate screen.
- `createProvider(config)` in `src/provider/index.ts` is the only place that maps config to a concrete `Provider`. OpenRouter uses `OpenAICompatProvider` (`src/provider/openai-compat.ts`: plain `fetch` to `POST {baseUrl}/chat/completions`, SSE parsed by `src/provider/sse.ts`; tool calls arrive in fragments keyed by `index` and are assembled before being emitted; `stream_options.include_usage` gets token counts incl. cached tokens). Ollama uses `OllamaProvider` (`src/provider/ollama.ts`: native `POST /api/chat`, NDJSON), because only the native API can set the context window (`num_ctx` = min(config `contextLength`, the context length the model was trained for, which `/api/show` reports as `model_info.*.context_length`; asked once, before the first request, and a failed or empty answer changes nothing; the configured value stays the upper bound, since Ollama can't tell what fits in VRAM; default 32768; Ollama's own default of 4096 is too small for an agent). It also sends `num_predict` (a cap per reply: min(8192, num_ctx/4), twice that with thinking on, since the cap counts reasoning; once a reply has reported its `prompt_eval_count`, also at most num_ctx minus the next prompt's estimate (`replyCap`: its JSON characters at the highest tokens per character measured, plus 5%; a ratio, since the session and its subagents share the provider, and the highest, since with a cached prefix Ollama may count only the new tokens), but never below 1024, so a nearly full window still gets a short reply and compaction makes room before the next turn) and `presence_penalty: 0`. Both were measured: qwen3.5's Modelfile sets a presence penalty of 1.5, which punishes every reused token, and code reuses tokens constantly: files came out garbled and cut off, tool calls unclosed, and one reply ran to 11k tokens; with 0 the same request wrote a complete file every time. Ollama sends nothing while the model writes a tool call, so the adapter passes Bun's `timeout: false` (its default 300 s limit cut long calls off; `num_predict` bounds the wait, Esc still stops it), and retries once when Ollama answers 500 because it couldn't parse the call (an unclosed one: a re-sample usually comes out whole; other 500s, like out of memory, aren't retried). When the cap cuts a tool call off, Ollama answers `done_reason: "length"` and drops the call. OpenRouter keeps Bun's timeout (it sends keep-alives while working, so the limit only catches dead connections). `think` follows `/think` (off by default: local thinking models can otherwise reason for minutes). On OpenRouter `/think` sets the unified `reasoning: { enabled }` (`reasoningFor` in `src/provider/index.ts`), using what the model list says (`ModelInfo.reasoning`): "off" goes only to models whose reasoning is optional, since OpenRouter rejects it for one that always reasons; for a model not (yet) in the list nothing is sent. The session remakes the provider once that info arrives (`lookup()` in `src/session.ts`).
- `src/app.tsx` holds the UI state (transcript, approval queue, agent views, setup) and makes one `MarvSession` from its props (see **Session**), which holds the conversation and runs the turns. The phases are `splash` → `main`, plus an optional setup overlay. There are two separate histories:
  - `items` (the App's): the **transcript the user sees**, including the welcome banner, help text, and errors.
  - the session's conversation (`ChatTurn[]`, inside `MarvSession`): **what the model sees**: user and assistant turns, the assistant's tool calls, and tool results.
  Keep them separate; Marv's own notices must never leak into the model's context.
- **Agent loop (`src/agent.ts`)**: `runAgent()` sends the conversation plus tool definitions, runs any tools the model asks for (via an injected `runTool`), appends the results, and repeats until a plain answer, an error, or ctrl+c. Text and tool-call loop detection (`src/repetition.ts`) catches a model stuck repeating the same sentence or the same calls: the first time it warns the model and goes on; a second time ends the run with `"loop"` in the trajectory. Every `maxSteps` steps (the TUI's config `maxSteps`, `/steps` to see or set it, `MARV_MAX_STEPS` to override; 0 never asks: `onLimit` is undefined, and without it maxSteps is a hard stop; subagents keep their own 50, `SUBAGENT_MAX_STEPS`) it calls `onLimit`, after that step's tool results are in: the session asks through its approver (`stepLimitRequest`: "Keep going?", scope `continue`; the App shows it like any approval) and a no stops it with a hint to say "continue"; without `onLimit` (subagents at their own 50 steps; a session with no approver) it's a hard stop. With `onLimit`, a `step_limit` event says what happened; without it, the run ends with an `error` and `done` `max_steps`. It yields `LoopEvent`s and knows nothing about the UI or vendors; `MarvSession` runs it once per turn, and `App.send()` turns the session's `SessionEvent`s into transcript entries (tool calls are `role: "tool"` messages updated in place: running → summary or error). Every tool call gets a result, even after ctrl+c, or the next request would be rejected; that includes a consumer that stops mid-tools (throws or breaks out): a `finally` answers the calls left without a result with "not run", in order. `rewriteCall` (optional) is applied to each call of a reply right after the ids are fixed, before it enters the history: a call to record and run instead (the session turns a direct call to a deferred MCP tool into `mcp_call`, so the history never names a tool that isn't offered). Tool-call ids are unique across the conversation: before a reply enters the history, an empty id or one already used (a duplicate in the reply, Ollama's `call_0` in every step, a resumed session's) gets a `_<n>` suffix, since the API and the UI both match results to calls by id. Tool calls run one at a time, except a run of consecutive calls of a `parallel` tool (`agent`; the session passes `isParallel`), which run concurrently, at most `MAX_PARALLEL` (4) at once; their `tool_start`/`tool_end` events arrive as they happen, but the results are appended in call order, so the history (and the prompt cache) doesn't depend on which finished first. A call starts only after its `tool_start` has been delivered (a consumer that stopped never has a tool running it can't show or stop), and after an abort or a "no" nothing new starts: queued calls get a "not run" result. A reply cut off at the output limit (`done` reason `length`) runs nothing: its calls may be incomplete (a `write_file` whose content stops mid-line), so each gets `NOT_RUN.cutOff`, and with no calls the model is told directly (`CUT_OFF_NOTE`, a user message from Marv; `CUT_OFF_REASONING_NOTE` when the reply reasoned and left nothing: it reasoned until the limit, or its tool call was cut off and dropped, and Marv can't tell which). The results go into the history before the `cut_off` event, so a consumer that stops there leaves it valid. `afterStep` (optional) runs after a step's tool calls are all answered, and its note, if any, is appended as a user message from Marv before the next request (the typecheck, see **Diagnostics**; it never rejects); it is skipped after a cut-off or empty reply, a decline, an abort and a final answer, runs before the next step-limit prompt, and an abort during it ends the run `aborted` and drops the note. Two cut-offs in a row end the run with `done` `length`; after a step that finished, one is forgiven again (writing several big files in parts). A reply with no text (whitespace doesn't count) and no tool calls, not cut off, failed or interrupted, is empty (`empty_reply` event, `next`): the first is asked for again unchanged (nothing enters the history, so the cache holds; OpenRouter's upstream hosts sometimes bill for a reply and send nothing, a third of the failed eval runs), the second gets `EMPTY_REPLY_NOTE` (a user message from Marv: continue, or say what you did), the third ends the run as an answer; a step that answered resets the count. The App shows the nudge and the stop, not the silent retry; trajectories record all three. The system prompt and `bash`'s description say to write files with `write_file`/`edit_file`, never heredocs or `echo >` (a small model put the heredoc terminator on the same line as more commands, read bash's warning as "truncation", and retried for 10 steps), and how to write a long file in parts.
- **Session (`src/session.ts`)**: `MarvSession` (which implements the public `Session` interface) is Marv without a UI, and the TUI's engine. It holds the conversation (what the model sees), the providers (through a `ProviderFactory`, `src/provider/factory.ts`: the TUI makes it from its `Config` with `configFactory`, the SDK from a `ProviderOption` with `providerFactory`, which throws on an unknown `kind`; a factory makes the session's provider, a subagent type's other model, and the provider again once the model list says how its reasoning switch works; a `Provider` of your own is used for everything, subagents too, and its `name` is recorded as the model), the system prompt and tool specs (built once per conversation), the "always" scopes (shared with subagents), the totals, and the trajectory and saved-session bookkeeping. `send(text)` starts the turn at once (`runTurn`) and returns an async iterable of `SessionEvent`s: `turn_start` first and `turn_end` last, exactly once however it ends (`interrupted` when stopped before the loop began: waiting for MCP servers, or an automatic compaction), the main loop's `LoopEvent`s, `subagent`/`subagent_progress` (tagged with the agent call's id), `status` (`waiting_for_mcp`/`compacting`/`running`) and `compaction`. The turn's work pushes into an `EventQueue` (`src/event-queue.ts`; one reader, a second throws) that `send()`'s iterator reads, so the turn doesn't depend on being read: one nobody reads still runs to the end. Leaving the loop early (break) interrupts the turn and waits for its cleanup, so every tool call has a result before the client goes on. The session is free (`busy` false) right before `turn_end`, so a client can send the next message as soon as it sees it; events after `turn_end` are dropped. The typecheck after file changes (see **Diagnostics**): `status` also has `checking` (and `running` again after each check), and a `check` event carries the `CheckResult` (a `checks` event the project checks' `ProjectCheckResult`, see **Project checks**); `SessionInit.diagnostics` and `checks` (both default true; `typecheck` and `projectChecks` are for tests) and `configure({ diagnostics, checks, maxSteps })` apply from the next turn; only the main agent gets `beforeChange`/`afterStep`. A turn reads all its settings when it starts (provider, factory, model info for pricing, sandbox, yolo, offered tools), so a change made with `configure()` applies from the next turn. `configure()` is all or nothing: it makes the new provider before changing anything, so what throws, an invalid provider (an unknown `kind`), a `maxSteps` that isn't a whole number of at least 0, or `yolo: true` where `noYolo` forbids it, leaves the session exactly as it was (a kept bad option would make every later `configure()` throw). One turn at a time: `send()` and `clear()` throw at once during one, `resume()` and `compact()` reject; `clear()` and `resume()` save the previous conversation first. `close()` interrupts, waits for the running turn, flushes, and closes the MCP servers the session started (`ownsMcp`); after it `send()` throws, and a second `close()` is harmless. The constructor throws if a tool of the caller's own (`SessionInit.tools`, offered to the main agent only) takes a built-in tool's name (`runTool` runs the first match, so the built-in would run), repeats another's, or starts with `mcp__` (MCP servers' tools), or is `tool_search`/`mcp_call` (deferred MCP tools). The approver it's given is wrapped: "always" scopes are answered by the session, and a stop answers pending approvals "no". Without an approver, only yolo-safe calls run and the step limit is a hard stop. Saved 200 ms after each turn, and by `save()`/`flush()`; the client can hand over its own transcript (`transcript`), otherwise the user's messages and replies are saved.
- **SDK (`src/sdk.ts`, package entry `@flologixai/marv/sdk`)**: `createSession(options): Promise<Session>` checks for Bun when it's loaded (`src/bun-guard.ts`, its first import: a clear message under a runtime that can load the TypeScript but has no Bun APIs; plain Node fails earlier, while linking, with its own error), that `cwd` is a folder, that with yolo on (the default) it isn't the home folder, above it, or `/` (`homeOrAbove` in `src/paths.ts`, through real paths: yolo-safe edits run before any approver is asked, so they'd change dotfiles unasked, approver or not; with `yolo: false` it's allowed, and `SessionInit.noYolo` carries the reason so the session refuses yolo on at construction and in `configure()`), and that `resume` comes with `persist` (`"latest"` with nothing saved starts a new conversation, an unknown id throws; call `session.resume()` yourself to get what was resumed). It loads only the `sources` asked for (`src/sources.ts`: `"user"` is everything under `~/.marv`, project memory included; `"project"` is the repository's `AGENTS.md`, `.marv/` and `.mcp.json`, whose servers still need trusting; default: nothing; with `cwd` your home folder, `"project"` also finds `~/.marv`'s skills and agents, as the CLI does), and ignores `OPENROUTER_API_KEY`/`MARV_MODEL` (a library uses what it's given). `mcpServers` (`Record<string, McpServerEntry>`, `parseMcpServers`) are trusted like your own: no trust prompt, started in your home folder, `${MARV_PROJECT_DIR}` points at the project; a server given in code wins a name clash with the config files (reported in `problems`). So never pass config read from a repository you don't control: `sources: ["project"]` is for that. It builds the session before starting the MCP servers (the constructor can throw: an unknown provider kind, a taken tool name) and closes everything if anything after fails, and makes the stores when `persist`/`trajectories` are `true`. `configDir` moves config, memory, `mcp.json`, sessions, trajectories, worktrees and MCP trust; personal skills and agents are still read from `~/.marv` in the home folder, as the CLI does, and a project's MCP servers can only be trusted with the CLI's `/mcp trust`. `maxSteps` (`SessionInit.maxSteps`, a whole number of at least 0, checked in the constructor) moves the step limit: a hard stop without an approver, the "Keep going?" interval with one; 0 never asks and never stops the main agent, while subagents keep their own limit (SUBAGENT_MAX_STEPS, 50). `mcpTools` (default `"auto"`) says how MCP tools are offered (see **MCP servers**). `onWarning` passes on the session's warnings (a trajectory that can't be written). `diagnostics` (default true) switches the typecheck after file changes (see **Diagnostics**); `CheckResult` and `TsError` are exported as types. `package.json`: `exports` `./sdk` (and `./package.json`), `engines.bun` >= 1.3, `private` (the repository itself is never published; see **Releasing**). Consumers type-check Marv's `.ts` sources with their own tsconfig, which needs `allowImportingTsExtensions` and `moduleResolution: "bundler"` (`bun init`'s defaults). The SDK must never import Ink, React or `src/ui/`. `examples/sdk.ts` is a runnable example; `tests/sdk.test.ts` imports through `@flologixai/marv/sdk` (Bun resolves the package's own name via `exports`). Known limit: Bun only.
- **Releasing (`scripts/release.ts`, `bun run release:build`)**: the package is `@flologixai/marv` (MIT; `marv` on npm is someone else's), built into `release/` (git-ignored) and published from there (`npm publish ./release --access public`; the README's Releasing section has the steps). Bun applies `patchedDependencies` only in this repository, and refuses to install a package that lists them, so: the CLI is bundled (`Bun.build`, `src/cli.tsx` plus web_fetch's converter as a second entry, `dist/tools/web/html-convert-cli.js`, which `convert.ts` finds beside the bundle) with the patched copies inside; `react-devtools-core` is stubbed (Ink's import of it ran at startup in the bundle and crashed wherever it isn't installed); the build fails if the bundle still imports a package (Bun's metafile; `canvas` is linkedom's optional `require`); the SDK ships as `src/` with only the dependencies its files import (found from a `packages: "external"` build, plus `@types/turndown`); the published package.json has no `patchedDependencies`, scripts or devDependencies, and `bin/marv` there runs `dist/cli.js`. SDK users type-check `src/` with their own tsconfig, which doesn't see `src/types/`, so `html.ts` references its declaration with `/// <reference path>`. Checked by packing, installing the tarball in a fresh `bun init` project (and with npm), and running `marv`, an SDK turn and `tsc` there.
- **Tools (`src/tools/`)**: each is a name, a description the model reads, a zod `input` schema (sent as JSON schema; also validates what comes back), a `label` for the transcript, and `run()` → `{ output, summary }`. Register new ones in `tools` in `src/tools/index.ts`. Read tools (`read_file`, `glob`, `grep`) run freely; `web_fetch` (also a read tool) asks once per site (see **Web**); tools with `kind: "write" | "execute"` (`edit_file`, `write_file`, `bash`) need approval, unless the tool defines `needsApproval(input)`, which then alone decides per call (`agent` asks only with `isolation: "worktree"`), or yolo mode runs it (see **Yolo mode**). `runTool()` first calls the tool's `preview()` (a diff, or the command; a `ToolError` there means the call can't succeed, so the user is never asked to approve it), then, unless the run was aborted meanwhile, `ctx.approve()`, which the App answers with the `Approval` prompt (yes / yes and don't ask again for the tool's `scope` this session / no). With no approver at all (an SDK session without `approve`), yolo-safe calls still run (the yolo check comes first) and anything else fails with "needs the user's approval, and there's no one to ask", which the model reads and works around; a subagent then gets no worktree auto-yes either (`subagentApprove`). The "don't ask again" scopes are one set in the session (`MarvSession.always`, in the approver it wraps around the client's), shared by the main agent and its subagents (an "always" for file edits in one covers the other), so remembered scopes never reach the App. Requests wait in a FIFO queue in the App (parallel subagents can ask at once): the prompt shows the oldest, who asks, and `N more waiting`, and is keyed per request so the choice cursor never carries over; "always" also answers the App's own requests already queued in the same scope. Esc or ctrl+c at an approval declines everything queued **and** aborts the run, so sibling subagents don't keep asking after the user said stop. A "no" returns a `declined` result and `runAgent` stops so the user can redirect. `runTool(call, ctx, available)` only runs tools in `available` (default: all), so a subagent can't call a tool it wasn't offered by naming it. `edit_file` replaces text that must match exactly once (or `replace_all`) and is re-planned at apply time in case the file changed while the user decided. Matching (`src/tools/edit-match.ts`, `applyEdit`): exact first; if nothing matches, whole lines ignoring trailing whitespace, then ignoring indentation, each only when unique; an indentation match re-indents `new_string` by the one column shift (tabs 4, 2 or 8 wide) that explains every matched line, in the file's tabs or spaces, or isn't used (an unindented first line is old_string starting at the code: not counted, and `new_string`'s first line gets the file's indentation); the result says which forgiving match applied. `read_file` numbers lines as `   12→text` (`numberedLine`; GitHub blobs and the closest-lines error too), not with `cat -n`'s tab: in a tab-indented file models took the separator for indentation (first line's tab missing, one extra on the others: every failed edit of the eval's tab task). A file whose line breaks are all CRLF gets CRLF in what `edit_file` inserts and what `write_file` writes (a model writes `\n`; an eval run spent 6 of 11 steps repairing mixed line endings). `write_file` also has `append: true` (it appends content at the end of an existing file instead of replacing it: the cut-off notes tell the model to write a long file in parts that way; a file that doesn't exist is just created, and a last line without a newline gets one first, which the result says). When nothing matches, the error shows the file's closest lines (`closestLines`: per-line bigram similarity, at least 0.5) numbered like `read_file`, so the model can copy the real text in its next call. After a change, `edit_file` and `write_file` check that the file still parses (`src/tools/syntax.ts`: JS/TS/JSX with `@babel/parser`, JSON (not JSONC: `tsconfig*.json`, `.jsonc`, `.vscode/`), YAML, Python through `python3 -I` and `ast.parse`; files over 2M chars skipped) and add a `Marv:` note with the line when the change broke it; a file that already didn't parse isn't blamed (`brokenBy`). **Never parse with `Bun.Transpiler`**: `transformSync` and `scan` execute macros (`import … with { type: "macro" }`), so checking a file would run its code outside the sandbox; every parser used here only parses. File changes carry their diff on `ToolResult.diff` (`DiffShown`: at most `MAX_SHOWN_DIFF` = 400 lines of at most `MAX_SHOWN_LINE_CHARS` = 500 chars, `more` counts the rest; numbered via `diffText`/`addedLines` and capped by `shownDiff` in `src/tools/diff.ts`, through `previewLines` like the collapsed view, so a big rewrite keeps the new file's start), for the screen only: `runAgent` sends the model `output`, trajectories record named fields. The App and the subagent log copy it to `ToolStatus.diff`; `DiffView` (`src/ui/DiffView.tsx`) draws it under the entry, 15 lines collapsed (`previewLines`: a change that doesn't fit keeps only its first few removals, so a full rewrite shows the new file's start), all with ctrl+o (which shows subagents' steps too), and the approval prompt uses the same component. Saved sessions keep it. `ToolContext.beforeChange` is started (not awaited, errors caught) by `edit_file`/`write_file`'s preview and awaited in `run` before writing; an abort while waiting writes nothing ("interrupted"). `runTool()` never throws: bad JSON, invalid input, and `ToolError`s become error results the model can recover from. All paths go through `resolveInProject()` (`src/tools/files.ts`), which expands a leading `~/` to the home folder (taken literally, it became a `~` folder in the project) and rejects anything outside the project root, including via symlinks (grep too: it never follows a symlink out of the project). `edit_file`'s not-found error suggests `write_file` only when the parent folder exists. `read_file`, `edit_file`, `write_file` and `grep` refuse special files (FIFOs, devices), since reading one would block forever (`requireRegularFile`, which says a missing path doesn't exist rather than calling it a special file). Files are listed with `git ls-files` (so `.gitignore` applies) through `runGit` (see **Subagents**; a 20 s timeout, an error rather than the unfiltered walk, and `ToolContext.gitEnv` pins a worktree subagent's git paths), falling back, outside a repo, to a walk that skips `node_modules`, `.git`, `dist`, etc. **Malformed-call repair (`src/tools/repair.ts`, issue #10)**: when a call fails to parse, `runTool` first tries `repairJsonArgs` (raw control characters inside JSON strings — literal tabs and newlines — are escaped and parsed again; broken JSON of any other kind is left to the ordinary error), and a tool's `repair(raw, ctx)` may fix what it can read with certainty before validation: `bash` a `timeout` given in milliseconds (a whole multiple of 1000 above the 600 s max: divided and clamped), and `read_file`, `glob`, `grep`, `edit_file`, `write_file` a `path` written with a leading slash (`/src/x.ts`) that doesn't exist as written but does relative to the project root (an existing absolute path, `~`, `..`, or a missing file is left alone). Every repaired call's result carries a `Marv:` note (both repairs at once: two notes, blank line apart) saying what was repaired, however the call ended (run, declined, interrupted, invalid, failed), so the model learns the right form; a repair never turns an error into a guess.
- **Web (`src/tools/web-fetch.ts`, `src/tools/web/`)**: `web_fetch(url, offset?)` reads a page. Marv fetches it itself, not the sandbox (which has no network), so it can enforce what `curl` can't: plain GETs only; `checkAddress` (`web/address.ts`) refuses anything but http(s) and any host that is, or resolves to, a loopback, private, link-local, CGNAT or multicast address (IPv4-mapped and NAT64 IPv6 too; `new URL` already turns `0x7f.1` into `127.0.0.1`), and each redirect (followed by hand, at most 5) is checked again; 20 s, 5 MB, text only (binary sniffed). HTML is converted in a subprocess (`web/convert.ts` → `web/html-convert-cli.ts`, JSON over stdin/stdout, an empty environment, cwd in Marv's own folder so a project's `bunfig.toml`/`.env` can't reach it, SIGKILLed on timeout (15 s), abort, completion or Marv's exit): converting a big or hostile page is seconds of synchronous CPU that would freeze the UI, and in Bun `worker.terminate()` doesn't stop running JavaScript, a killed process does. Inside it (`web/html.ts`, pure): linkedom + Readability (the main content) + turndown with GFM tables; hidden elements (inline `display:none`/`visibility:hidden`/`opacity:0`, `[hidden]`, `aria-hidden`), form controls and svg are removed (hidden text is the classic prompt-injection channel); links and images are filtered after `new URL` (http/https/mailto only, `<base href>` honored); the title is one line of at most 200 chars. The work is bounded: a 300k-character budget and a 20k-element cap prune the DOM before Readability, which is skipped for pages too large or too deep (Readability and turndown are superlinear); `reason` says why it fell back (`no-article`, `too-large`, `too-deep`, `timeout`, `error`) and `fetchPage` tells the model. On timeout or failure the page comes back as plain text (`web/plain.ts`: a linear, quote-aware tag scanner that skips hidden elements). linkedom quirks: no HTML5 optional tags (pages without `<body>` are re-wrapped) and no `table.rows` (patched onto its HTMLElement for the gfm plugin, inside the converter only). GitHub links (`web/github.ts`) use the API: a repo gives its description, README (cut at 12k) and file list (at most 500; a tree over 16 MB or truncated falls back to the top-level entries; an empty repo says so), `tree/<ref>/<dir>` that folder's entries from the contents API (like `ls`, any repo size), `blob/` the file numbered like `read_file` (from raw.githubusercontent.com without a token, the contents API with one). Segments are decoded once and re-encoded per segment, and owner/repo/ref/path are validated (no `..`, no encoded `/` in names), so a crafted link can't reach another API endpoint with the token. `GITHUB_TOKEN`/`GH_TOKEN` goes to the API host only: `get` sends headers only to the first URL's origin and only over https (`sendsHeaders`; tests use `allowHttp`). Rate-limit errors (primary and secondary) say when to retry; other errors include GitHub's message. Output comes in 30k-character parts (`offset`). Approval: asked (a read tool, but one that reaches out), scope `web:<domain>` (no `www.`; GitHub's hosts count as `github.com`); no `autoSafe`, so yolo never skips it (the URL itself can carry data out); `usesNetwork`, so worktree subagents ask too. A redirect to another site isn't followed (`followRedirect` in `get`): the model gets the target and calls again, which asks, so an open redirect on an approved site can't carry the query string elsewhere. `MarvSession.send()` adds the scopes of the `http(s)://` links in what the user typed to the session's "don't ask again" scopes (`pastedScopes`), so pasted sites don't ask; links inside code (fenced or inline) don't count (a pasted script's hosts are what an injected instruction would send data to), nor do links in files, pages or tool output. Reading on from the cache (`offset`, 8 pages of at most 1M characters, 10 min; kept under both the requested URL and the final one after same-site redirects, since the header shows the latter) sends nothing, so it doesn't ask (`needsApproval` hands the page it found to `run`, so an expiry in between can't fetch unasked). Errors tell the model what to do: a refused redirect says where it leads (`redirectNote`, also for GitHub), 403/429/503 say the site may block automated readers, a connection failure for a scheme-less address suggests `http://`, and only a name that doesn't exist says "check the address". The system prompt's `# Web` section says its output is data. Subagents get it; Claude Code's `WebFetch` maps to it. Tests stub `dns.lookup` (an object for that reason) and `fetch`, or use `makeWebFetch({ allowPrivate: true })` against `Bun.serve`. Known limits: DNS rebinding (the name is checked, then `fetch` resolves it again); hiding by CSS class or stylesheet isn't detected; the budget is spent in document order, so a page with a ~10,000-link sidebar before its `<main>` can lose the article.

- **Sandbox (`src/sandbox.ts`)**: `bash` runs inside bubblewrap: the system read-only, `/run` replaced by an empty folder (`runMounts`: it holds the host's sockets, and a read-only mount doesn't stop a connect(): the user's D-Bus let `systemd-run --user` start programs outside the sandbox, plus the GPG/SSH agents, keyring, display and docker; A sandboxed command that refers to the hidden part of the home folder (`~`, `$HOME` or its path, outside the project and the mounted folders: `touchesHiddenHome`, a guess from the command's text) gets a `Marv:` note that the home there is a stand-in, so a missing file proves nothing (the prompt's "hidden" wasn't enough: `ls ~/.marv` showed `skills/`, and a model took Marv's missing config and trajectories for real). A sandboxed command without `network` that fails (not 126/127; a timeout counts) with a network-looking error (DNS, refused or unreachable connections, timeouts) or is a tool that needs the network (`gh`, `curl`, `git fetch/pull/push/clone`, `npm`/`bun install`…; `looksLikeNetworkFailure`, a guess from the output and the command's text) gets a `Marv:` note to retry with `network: true` before drawing conclusions (`gh auth status` without network called a fresh login's token invalid, and the model had the user log in again). For a failed `gh` command the note adds where to actually go: the GitHub MCP server (`~/.marv/mcp.json`), not another login, and never mounting gh's config into the sandbox (a token there must not reach command output; `GH_NOTE`, issue #27). `/sandbox off` runs commands directly (still approved, with a warning in the prompt); without bwrap the prompt warns too. Outside the sandbox commands start under `setsid` so a timeout or ctrl+c kills the whole process group.
- **Project checks (`src/checks/`, issue #41)**: a project's rules as code, `.marv/checks/<name>.yaml|yml|json` (declarative: `glob`, optional `exclude`, exactly one of `forbid` (each match is a violation, at its line) and `require` (a file without a match is one), `flags` from `imsu`, `message`, `why`) or `<name>.ts` (a bun script; its leading `// glob:`/`// exclude:` comments are read as text, never run, default every change; it prints JSON lines `{file?, line?, message, why?}` and must exit 0). `loadChecks` (`load.ts`) reads them each turn and reports broken files (bad YAML, a regex that doesn't compile, a duplicate name) as problems (`/checks`). They run as a second `CheckKind` (`projectChecks` in `kind.ts`, `ProjectChecks`) through the typecheck's machinery (see **Diagnostics**): baseline before the turn's first change (all checks), and after a step only the checks a changed file `concerns` (glob matches and exclude doesn't, or it's the check's own file; the files come from `ToolResult.changed`, which `edit_file`/`write_file` set beside `diff`, and a diff without it runs them all); a step no check concerns runs nothing. A pass's `covers` limits the comparison to the checks it ran, the rest of the baseline stands. Violations are matched by check, file and message, not line (`violationKey`), and the model gets `checksNote` (at most 20, then each check's why once), in the same user message as the typecheck's. Everything runs in one sandboxed command (`runnerCommand`: `bun -e` with `runChecks`' source and the checks as JSON; the sandbox can't see Marv's own files, so `runner.ts`'s `runChecks` must stay self-contained), with the project read-only, no network, the repository's `.git` (a worktree's common one too, `worktreeGit`) read-only so a script can ask git, 60 s for the whole run and 30 s per script (`SCRIPT_TIMEOUT_MS`). The runner prints `{done: true}` last, so a cut-off or crashed run is unreadable (`parseRunner`); a script that crashes, times out, exits non-zero or prints a non-violation line becomes a `failed` violation of that check (told once, like any other). Regular expressions are compiled in Marv only to validate them; matching happens in the sandbox (a hostile pattern can only time out). bun not in the sandbox is `missing-interpreter`. Checks are repository code on the typecheck's footing: sandbox only, never asked, off without the sandbox. Config `checks`, `/checks` (list, problems, the last result; `on|off`), SDK `checks`, session event `checks`, trajectory `check` records with `source: "checks"`. Marv's own: `prompt-cache.ts`, `write-shrink.ts` (a tracked file that lost more than half of its committed lines, at least 20, compared with `HEAD`), `imports.yaml`, `render-options.yaml`; `tests/project-checks.test.ts` proves each fires and stays quiet, and that they run clean on this repository (so it's excluded from the imports rule: its fixtures are violations). Known limits: the same as the typecheck's (main agent only; bash edits aren't seen).
- **Prompt cache (don't break it)**: providers reuse work for an identical prompt *prefix* (measured on Ollama: a follow-up turn's prompt in 76 ms instead of 1.2 s; one changed letter in the system prompt and it's back to 1.2 s). So: the system prompt is built once per conversation (`.marv/checks/prompt-cache.ts`; `clear()` rebuilds it with the memory reloaded), the tool specs are built once per session, `conversation` is only appended to (never edited or trimmed, except by compaction; `/clear` resets it), and adapters serialize deterministically. A conversation with deferred MCP tools offers the same two specs whatever the servers do: new MCP tools reach the model only in appended notes, so trusting a server mid-session doesn't reset the cache. `tests/agent.test.ts` checks that every request extends the previous one exactly. The status bar shows the last request's size (`12.3k/32.8k ctx` when the window is known) and the cache hit rate when the provider reports it (OpenRouter); Marv warns once when Ollama's window is 85% full.
- **Provider seam (`src/provider/types.ts`)**: every provider implements `Provider.stream(history, { system, tools, signal }) → AsyncIterable<AgentEvent>` (`text_delta`, `thinking_delta`, `tool_call_delta`, `tool_call`, `usage`, `done`, `error`, `retry`), converting its native stream into Marv's own events. The UI never sees a vendor format. Errors become `error` events with an actionable message (bad key → /setup, unknown model → /model, unreachable → is it running?); SDK sessions name the option instead (`provider.apiKey`/`provider.model`): `providerFactory` passes `SDK_HINTS` (`src/provider/errors.ts`) through `createProvider` to the adapters, which default to `TUI_HINTS`. The system prompt lives in `src/prompt.ts`. Model lists for the picker come from `src/provider/models.ts` (OpenRouter `/models`, filtered to tool-capable; Ollama `/api/tags` + `/api/show`).
- **Rendering**: Marv runs full-screen in the terminal's alternate screen, so there is no terminal scrollback. Ink's options live in `src/render-options.ts`; `incrementalRendering: true` stays (`.marv/checks/render-options.yaml` says why; `tests/render-options.test.tsx` guards it too). The root `<Box>` is sized to the window; `ScrollView` (`src/ui/ScrollView.tsx`) takes the leftover height and scrolls the transcript itself (PgUp/PgDn or the mouse wheel, follows the bottom until you scroll up; `followKey` snaps back on submit). The prompt and status bar are pinned below it. Don't use `<Static>` here: in the alternate screen its output would scroll off and be lost. The whole transcript stays mounted, so **ink is patched** to skip drawing nodes entirely outside the visible (clipped) rows: unpatched, Ink wraps and draws every scrolled-away message on every frame, and a 60-entry session took ~270 ms per keystroke (now ~30 ms). `tests/render-performance.test.tsx` guards this. Wheel scrolling glides: notches add to a distance that a 20 ms timer covers a third at a time (at least a row), and Ink draws up to 60 frames/s (`maxFps: 60`); 20 ms keeps every step in its own frame (16 ms beat against Ink's limiter and stuttered). Two more patches keep frames cheap (~7 ms): **string-width is patched** (`patches/string-width@8.3.0.patch`) to cache widths and skip its per-character emoji regex for characters that can't be emoji (it was ~36% of CPU while scrolling; `tests/string-width.test.ts` pins its answers), and the Ink patch skips `findStaticNode`'s walk of the whole tree after every commit unless a `<Static>` was ever created. Text from the model or from files (replies, thinking, tool labels and summaries, approval previews, subagent steps) passes through `printable()` (`src/printable.ts`) before it's drawn: it strips escape sequences and control characters, which the terminal would execute rather than show (OSC 52 writes the clipboard, others retitle or redraw). Ink already drops them when it draws; this is defense in depth, applied at render time so the model's own conversation is untouched, and careful not to eat real text (UTF-8 misread as Latin-1 contains C1 bytes).
- **Mouse (`src/mouse.ts`)**: Ink has no mouse support, so Marv turns on SGR mouse reporting (mode 1002: presses, drags, wheel), wraps `stdin.read()` to strip mouse codes before Ink parses them, and emits `MouseEvent`s on the `mouse` emitter. Mouse mode is terminal-wide, so it is turned off in a `process.on("exit")` handler.
- **Selection (`src/selection.ts`, `src/clipboard.ts`)**: with mouse reporting on, the terminal can't select text, so Marv does: drag highlights, release copies (wl-copy / xclip / xsel / pbcopy, falling back to OSC 52), a click or any key clears it. The selection is stored in *transcript* rows, not screen rows (the transcript's `ScrollView` publishes its position and scroll via `onViewport`), so the highlight stays on its text while scrolling, and dragging past the top or bottom auto-scrolls. Only visible rows are ever drawn, so the store remembers each transcript row's text as it passes through the viewport and copies from that (like a terminal's scrollback); a resize or `/clear` resets it. **ink is patched** (`patches/ink@8.0.0.patch`, applied by `bun install`; edit with `bun patch ink`, then `bun patch --commit node_modules/ink`) with a `transformOutput(frame) → frame` render option, through which the store sees each frame and draws the highlight, and a `repaint()` that re-applies it to the last frame. Moving the highlight therefore costs ~3 ms instead of a full ~30 ms React render + layout + draw.
- **Slash commands (`src/commands/index.ts`)** are pure functions that return a `CommandAction` (`print` | `clear` | `setup` | `model` | `thinking` | `sandbox` | `yolo` | `trajectories` | `diagnostics` | `checks` | `feedback` | `mcp-trust` | `skill` | `resume` | `compact` | `memory` | `remember` | `forget` | `exit`) and receive a read-only `CommandContext` (current config). The App applies the action. Add new commands to the `commands` array; they automatically show up in the `/` menu (`PromptInput`: ↑/↓ select, Enter runs the highlighted one, Tab or → completes so you can add arguments). A `print` action with `markdown: true` (e.g. `/skills`, `/agents`) is rendered through the Markdown renderer, so lists get hanging indents.
- **Replies are Markdown** (`src/ui/Markdown.tsx`): `marked.lexer()` turns the text into tokens and each becomes Ink boxes: list markers and quote bars sit in fixed-width columns (hanging indents), inline code is colored without backticks, code blocks get a left rule and their language, tables are aligned as plain text. While a reply streams (`streaming` prop), `createStreamLexer()` caches the blocks before the last safe boundary and re-parses only the unfinished end, because `marked` slows down faster than the text grows (~20 ms at 11 KB); finished messages are parsed whole once. An unclosed code fence renders fine mid-stream. A cut is a blank line outside any fence (tracked by its character and length: ```` ```sh ```` inside ````` ````markdown ````` doesn't close it, and a backtick "fence" with backticks after it is inline code) or HTML comment, before a complete line that starts a new block and isn't a list item (a loose list cut there would render as several lists); `tests/markdown.test.tsx` checks every streamed prefix of random replies against parsing it whole. Known limit: a reference link and its definition in different chunks render as text until the reply is finished (finished replies are parsed whole). The system prompt tells the model its replies are rendered as Markdown.
- **Tokens and cost (`src/usage.ts`)**: every request's `usage` event is added to the session's `Totals` (requests, input, cached and output tokens, cost; `MarvSession.count()`, subagents' and summaries' requests included). OpenRouter reports the real charge in `usage.cost` on every final chunk; without it the cost is estimated from the model's prices (`~$`), and Ollama is `local`. The session looks up the current OpenRouter model's context window and prices in the background (`lookup()`, through `configFactory(...).lookup`: the App's `loadModels`; again when the provider is reconfigured), so the status bar shows context use there too. A turn prices its requests with the model it started with; known limit: a subagent on another model is priced with the main model's prices. `/cost` prints the breakdown. Totals survive `/clear`.
- **Project keys (`projectKey` in `src/paths.ts`)**: per-project files (sessions, project memory, trajectories, MCP trust, worktrees) live under `<readable path>-<10-char hash of the full path>`; the readable part alone collided (`/a-b/c` vs `/a/b-c`, any two non-ASCII names of equal length), which made projects share memory, sessions and trusted MCP servers. Data under the old key (`legacyProjectKey`) is still found: sessions are read from both folders but only if their recorded `root` matches (and move on their next save), a project memory file is moved on load; old MCP trust is deliberately not carried over (those servers ask once more).
- **Private files (`src/private-file.ts`)**: sessions, memory and MCP trust are written with `writePrivate`: 0600 in a 0700 folder, through a temp file named with the process id and random bytes, then renamed into place; writes of one file from one process are queued, so an older write never lands after a newer one, and two processes never share a temp file (with one shared `.tmp` name, overlapping saves left a session unreadable in a third of test rounds).
- **Sessions (`src/sessions.ts`)**: every conversation is saved to `~/.marv/sessions/<project>/<id>.json` (0600; via `writePrivate`) by the session 200 ms after each turn ends, by the App between turns (what Marv prints there is part of the transcript; so a turn usually saves twice, identically, which is harmless), and again on the way out (`onFlush` is `session.flush()`: `cli.tsx` awaits it, at most 2 s, before exiting, since quitting cancels the timers; it also flushes the trajectory): both histories (transcript and conversation), provider/model, and totals. The saved conversation goes through `answerAllCalls` (`src/agent.ts`), so a run still winding down can't leave a tool call without a result in it. `/clear` starts a new session (`MarvSession.clear()`, which saves the previous conversation first, as `resume()` does). `/resume` (and `marv -r`) opens `SessionPicker`; `marv -c` restores the latest one here. Session files are schema-checked on load (`SessionShape`): an old format or a hand edit is skipped like a damaged file. Restoring brings back both histories and the cost, and keeps saving to the same file. Never into a running turn: the App's `resumeSession` (and the picker, once its list has loaded) refuses while `abortRef` holds a run, `session.resume()` itself rejects during a turn, and while `marv -c` is still loading the prompt keeps what's typed without sending it; `showResumed` then draws the restored transcript, and the message-id counter is never lowered. The App takes `sessions` (a `SessionStore`) and `resume` props and hands the store to its session; without it nothing is saved (most tests). The saved-file type is `SavedSession`.
- **Trajectories (`src/trajectory.ts`, `src/feedback.ts`, `src/trajectory-stats.ts`)**: every turn is logged, append-only, to `~/.marv/trajectories/<project>/<session id>.jsonl` (0600; one file per session, so `/clear` starts a new one and a resume continues it), for measuring Marv over time and as future training data. On by default (config `trajectories`, `/trajectories on|off`); the App takes a `TrajectoryStore` prop and hands it to its session (none in most tests: nothing is logged). One JSON record per line, each with `v` (format version), `t`, `session`: `session` (once per file per process: Marv version, provider, model, the full system prompt, tool names, git HEAD), `turn_start`, then per agent `request` (usage, ms since the previous step ended), `assistant` (text + reasoning), `tool` (the call, exactly what the model got back, `approval`: `none`/`auto`/the answer, ms), `error`, `agent_end` (reason, steps, tools, ms); a subagent gets `subagent_start` and its own records under `agent: "<turn>.<n>"`. `compact` records the summary that replaced the history. `check` records the typecheck after a step's changes (status, ms, `before` (baseline error count), `errors`, `added`, `note` (exactly what the model was told), `reason`); `turn_start` records `diagnostics`. The request clock restarts after a step's check (`AgentRecorder.restartClock`), but a write's `tool` ms includes waiting for the baseline. The session writes the `session`/`turn_start` records, and its `AgentRecorder`s turn `LoopEvent`s into the rest (main loop, and `AgentHost.onEvent` for subagents); `runTool` reports how a call was approved on `ToolResult.approval`. Feedback is a `feedback` record pointing to its turn: `/good [note]`, `/bad [note]`, `/label <tags>` (explicit, the last turn), and the user's next message, matched by `classifyReply` (keywords, negative checked first so a polite correction counts as one; the phrase is logged so it can be re-scored). Writes are queued (in order) and never throw into a run; the first failure is reported once. `bun run stats [--by model|marv]` prints turns, good rate (explicit rating wins over implicit), tokens and tools per turn, median time and how turns ended.
- **Evals (`evals/`)**: `bun run eval` (`evals/run.ts`) runs real models (OpenRouter) on the tasks in `evals/tasks/<name>/`: `task.md` (the request), `repo/` (the starting files, committed into a fresh temp git repository), `check/` (hidden tests, copied in only after the run, run in the sandbox: `bun test ./__eval__.test.js`), `solution/` (for `--verify`, which checks every task fails before and passes with its solution; run it after changing a task). A task whose `repo/` has a `tsconfig.json` gets Marv's own TypeScript (`typescript` plus the native `@typescript/*` package) copied into its workspace's `node_modules` after the start commit (`evals/typescript.ts`: copied, not linked, since the sandbox hides the home folder; `node_modules/` goes in `.git/info/exclude`, so git and Marv's file listing never see it), so its check, and the agent, can run `node_modules/.bin/tsc` offline. The `ts-*` tasks' checks run their tests plus tsc (`ts-required-field` adds a hidden `@ts-expect-error` file through `tsconfig.eval.json`, so making the new field optional fails), each repo has a `typecheck` script as real projects do, and `RunResult.ranTypecheck` (`ranTypecheck()`, from the bash command's text) says whether the model ran a typecheck itself. Each run is an SDK session with no approver and yolo on, so it runs unattended, with `maxSteps` 50 (`--max-steps`: the TUI asks at 25 and a user says yes once; with no approver, 25 was a hard stop that slow, careful models hit before finishing); `--budget` stops starting runs once OpenRouter's reported spend reaches it. Results go to `evals/results/<stamp>-<label>/` (git-ignored): `results.jsonl` (one `RunResult` per run) and `logs/<model>/<task>-<rep>.json` (every tool call, its output, the replies, and the final diff). `--diagnostics on|off` (default on) passes the session's typecheck setting, the log keeps each `check` result, and `RunResult.checkNotes` counts steps after which the model was told about new errors. A task with an `mcp.json` (`{ "server": "tracker", "data": "<file in evals/mcp/data>" }`) gets the 25-tool issue-tracker MCP server `evals/mcp/tracker.ts` (deterministic, local; its read tools and `add_comment`, which writes only the fixture's output file, are marked read-only so they run with no approver; `tests/eval-mcp.test.ts` checks its specs cross the deferral threshold), and the comments it records are copied into the workspace as `__tracker_comments__.json` before the check (a solution brings its own): `mcp-fix-from-issue`, `mcp-comment`, `mcp-unused` (issue #14). `--mcp-tools auto|deferred|eager` sets `mcpTools`, `--mcp <servers.json>` connects more servers to every run; `RunResult` has `mcpTools` and `mcpCalls`, and `--report` shows prompt tokens per request (and MCP calls per run when there are any). `--report a.jsonl b.jsonl` compares runs (`formatSummary` in `evals/summary.ts`: per label and model, pass rate, edit failure rate, steps, cost, then per task). Half the tasks stress editing (tabs, trailing whitespace, CRLF, near-duplicate blocks, a file longer than one `read_file` page), so their bytes matter: `.gitattributes` marks `evals/tasks/**` `-text`, and `bunfig.toml` limits `bun test` to `tests/` (the tasks have test files of their own). One stresses what the model *reads* rather than edits: `failing-suite`'s failing `bun test` floods the transcript with a many-hundreds-of-lines diff. Compare labels from the same day: providers behind a model id change.
- **Compaction (`src/compact.ts`)**: when the last request used ≥85% of the context window (`COMPACT_AT`; known for Ollama and, via the model list, OpenRouter), the session's turn (`runTurn` → `summarizeInto`) first asks the model to summarize the conversation (`summarize`: same system/tools/history plus one instruction message, so it hits the prompt cache), then replaces `conversation` with `compactedHistory(summary)` and continues. It also runs mid-turn: after a step's tool calls are all answered, `runAgent`'s `onFull` checks `tryCompact()` and compacts there too (a long turn can fill the window by itself); since the loop holds `conversation` itself, `summarizeInto` rewrites it in place (`splice`), `MID_TURN_NOTE` (a user turn telling the model to continue where it left off) is appended, because the compacted history ends with the model's own "Got it" and the next request would otherwise end with an assistant message, the loop yields `compacted` and goes on from the summary, and the usual `status`/`compaction` events say how it went. A summary that failed mid-turn isn't asked for again that turn (each retry would be another paid request that likely fails the same way; `midTurnCompactFailed`, reset in the turn's `finally`), while the next turn tries again. A reply that calls a tool (the tools are offered, for the cache) or stops at the output limit isn't a summary: `summarize` returns an error and the history is kept. `/compact [focus]` does it on demand (`session.compact()`, which rejects during a turn); Esc cancels it with nothing changed (mid-turn, stopping the summary stops the turn: the loop's abort check runs right after `onFull`). The transcript is never touched, and the summary request counts toward tokens and cost. This is the one deliberate exception to "never rewrite the history": the cache starts over once.
- **Waiting line (`src/ui/ThinkingView.tsx`)**: while a reply is awaited it shows the label, the seconds since it appeared (one wait per reply, like the `✻ Thought for 8s` line after it) and an estimated token count (`estimateTokens`, 4 chars a token: providers report usage only at the end), plus the reasoning's last lines. A tool call streams for a long time (a write_file's content: up to minutes; a trajectory had 18k tokens) and used to show nothing: OpenRouter's adapter now also emits each fragment as `tool_call_delta` (display only; the call still runs from the complete `tool_call`; Ollama sends nothing while writing a call, so it gets only the timer), the loop and session pass it on, and the App and the subagent log keep the latest call as a draft (dropped at the step's end: `STEP_ENDS`) that `DraftView` shows as `Writing src/app.js… (8s · ~400 tokens)` with the code's last lines, below any text streamed before the call (`src/tool-draft.ts` reads the unfinished JSON: `path`, and `content`/`new_string`/`command`).
- **Herdr (`src/herdr.ts`)**: in a Herdr pane (`HERDR_ENV=1`, `HERDR_SOCKET_PATH`, `HERDR_PANE_ID`; `herdrTarget`), `cli.tsx` makes a `HerdrReporter` and passes it to `App` as `herdr`. The App reports `blocked` while an approval waits (message: the asking subagent and the request's label), `working` while `busy`, `idle` otherwise, and the session (id and `SessionStore.file()`) whenever `session.id` changes; `cli.tsx` sends `pane.release_agent` on the way out (at most 1 s). Each report is one JSON line on the socket (`pane.report_agent` etc., source `herdr:marv`, agent `marv`, a rising `seq` so Herdr drops stale ones), the protocol of Herdr's own integrations. Best effort: repeats are skipped, only the newest state is sent when several pile up, a silent Herdr gets one retry (500 ms, then 1500 ms) and is let go, nothing throws. The sandbox's empty environment keeps `HERDR_*` from commands. Herdr 0.8.2 stores sessions and allows `herdr agent prompt|send-keys` only for its built-in kinds; `tests/herdr.test.tsx` covers the protocol and the App's states.
- **Render budget**: `App.send()` batches streamed tokens and reaches React at most every 33 ms (`STREAM_FLUSH_MS`, matching Ink's 30 fps cap), flushing immediately at step ends; subagents' progress joins the same flush; `MessageView` and `Transcript` are memoized so a transcript change only re-renders the entries that changed. `tests/render-performance.test.tsx` guards keystroke cost and stream batching (also with 4 subagents reporting).
- Colors live only in `src/ui/theme.ts`. Message markers (`●`, `>`) sit in a fixed 2-column `Gutter` box: a Text with a trailing space (`"● "`) is laid out 1 column narrower than it's drawn, so the text beside it overflows and loses a character per wrap (`tests/messageview.test.tsx`).
- **CI (`.github/workflows/ci.yml`, checked by `tests/ci.test.ts`)**: on every pull request and push to `main`, one job on `ubuntu-24.04` runs `bun install`, `bun run typecheck`, `bun test` and `bun run eval --verify` (no API key: `--verify` only checks that each eval task's check fails before and passes with its solution). The runner installs bubblewrap and lifts Ubuntu 24.04's AppArmor restriction on unprivileged user namespaces (`sysctl kernel.apparmor_restrict_unprivileged_userns=0`), so the `sandboxAvailable()`-gated tests run rather than skip, and an `if: always()` step writes whether the sandbox really ran to the job summary. Installs are cached (`~/.bun/install/cache`, keyed on `hashFiles('bun.lock')`). setup-bun installs bun to `~/.bun/bin`, which the sandbox mounts as a toolchain, so sandboxed commands can run it. The runner's system `node` matters: sandboxed typechecks and the ts-* eval checks run tsc's `#!/usr/bin/env node` launcher, and the sandbox hides the home folder, so a per-user node (nvm, mise) is invisible; a workflow step checks `git`/`python3`/`node` so a runner-image change fails loudly.

## Code review (Open Code Review)

Every push is reviewed locally by [Open Code Review](https://github.com/alibaba/open-code-review) (`ocr`, model and key in `~/.opencodereview/config.json`; currently OpenRouter's `glm-5.3-flash` with `extra_body: {"reasoning":{"effort":"low"}}`, since its default reasoning ran past ocr's 300 s request timeout), whoever wrote the change. PRs are reviewed on GitHub by Greptile; an OCR workflow for PRs is on the `ci/ocr-review` branch for later.

- **Before pushing**: `.githooks/pre-push` (on after `bun install`) runs `bun run review` on each pushed commit against `origin/main`. A critical or high-severity finding refuses the push. The gate fails closed: a review that didn't finish, unreadable output, or a finding with an unknown severity also blocks. `bun install` turns the hook on only when `core.hooksPath` isn't already set and not in CI. Read the findings it prints, fix them, commit, and push again. Run `bun run review` yourself first to see them sooner. Don't bypass it with `--no-verify`; if a finding is wrong, say why in the PR description.

## Conventions

- Imports use explicit `.ts`/`.tsx` extensions (`.marv/checks/imports.yaml`); use `import type` for types.
- UI tests use `ink-testing-library`. Pass `splashMs={0}` to skip the splash, `makeProvider={() => new FakeProvider()}` (`tests/fake-provider.ts`) for an instant, offline stream (or a `ScriptedProvider` to script tool calls step by step), a `root` temp dir for the tools, and a `ConfigStore` on a temp dir.
- Providers: OpenRouter (default model `anthropic/claude-sonnet-5.5`) and Ollama (local, no key). A saved provider Marv no longer knows (e.g. the removed `echo`) is dropped on load, which reopens setup. Tests never hit the network: the adapters are tested against a local `Bun.serve`, and `App` takes `loadModels`/`makeProvider` props.
