# /mcp add: install MCP servers from npm, a URL, a GitHub repo or the registry

Issue: #6 (spec first). Depends on: #14 (deferred tools, merged). Related: #27 (Connect GitHub).

## Problem

Adding a server means editing JSON by hand, in a file the model can't reach (the sandbox hides `~/.marv`, so `MCP_SETUP` in `src/prompt.ts` tells the model to hand the user the JSON), then restarting Marv. `/mcp add <thing>` should work the config out, show it, and start the server in the running session.

What makes it delicate is that a server is a program Marv runs **outside the sandbox, with the user's permissions and network** (`McpManager.connect`), and that most of what `/mcp add` reads to build the config (npm metadata, a registry entry, a README) is written by strangers. So the design is built around one rule: **the user approves the exact entry that gets written, and nothing fetched after the approval can change what runs.**

## Decisions

- **v1 sources:** an npm package, a PyPI package, an `https://` URL, a name from the official MCP Registry (plus `/mcp search` to find one), and a GitHub repo *whose README names an npm/PyPI package or a URL*. Not in v1: cloning and building a repo, Docker/OCI images.
- **No model in the loop.** `/mcp add` is a slash command; every step is deterministic code. A README can *nominate* a package, which then goes through the same resolver and pinning as if the user had typed it. The model gets no tool for adding servers.
- **Pinned:** `npx -y <pkg>@<exact version>`, `uvx <pkg>@<exact version>`. The version is resolved before the approval and written into `args`.
- **One approval, once:** a yes/no prompt (no "don't ask again") showing the command line, the package, version, publish date, repository and registry publisher, the variables it reads, and the exact JSON written.
- **Written to `~/.marv/mcp.json`** (personal, 0600 via `writePrivate`), never the project's `.mcp.json`. A personal server needs no `/mcp trust`: the approval is the trust.
- **Started at once** by a new `McpManager.add()`; its tools reach the model from the next turn: in a deferred conversation through #14's note (the cache holds), in an eager one as a changed tool list (the cache starts over once, as `/mcp trust` does today).
- **Secrets are `${VAR}` only.** `--env NAME` writes `"NAME": "${NAME}"`; `--env NAME=value` and literal header values are refused.
- **`/mcp remove <name>`** removes a personal entry and stops the server; its tools stay listed (failing clearly) until the next conversation. **SDK: nothing in v1.**

## Commands

```
/mcp add <source> [--name <name>] [--env VAR]... [--header "Name: Bearer ${VAR}"]... [-- <server args>...]
/mcp search <words>
/mcp remove <name>
```

`<source>` is read in this order (`parseSource`, pure):

| Input | Source |
|---|---|
| `https://github.com/<owner>/<repo>[/…]` | GitHub repo |
| `https://…` (any other), `http://localhost…` / `127.0.0.1` / `[::1]` | HTTP server (plain `http` only to loopback: a token in a header would travel in clear) |
| `npm:<pkg>[@ver]`, `@scope/name[@ver]`, `name[@ver]` (npm's name rules) | npm |
| `pypi:<pkg>[@ver]` | PyPI |
| `<reverse-dns>/<name>` (contains `/`, doesn't start with `@`: `io.github.acme/weather`) | MCP Registry |

npm names never contain a `/` without a leading `@`, so registry names and npm names can't be confused. A bare word is npm, as the issue asks.

**The server's name** (`serverName`): `--name`, or derived from the package (`@modelcontextprotocol/server-filesystem` → `filesystem`; strip the scope, then a leading `mcp-server-`/`server-`/`mcp-` and a trailing `-mcp-server`/`-mcp`; sanitized to config.ts's `NAME`, no `__`, no trailing `_`), the URL's host label (`mcp.linear.app` → `linear`), or the registry name's last segment. A name already in `~/.marv/mcp.json` is an error that suggests `--name`. A name a project server of this session uses is refused too, before the approval ("this project has a server named X: pick another with --name"): that server is running (or waiting for trust) under the name, `McpManager.add` can't start a second one, and swapping its tools mid-conversation isn't worth the complexity. (At the next startup `loadMcpConfig` would let yours win, so an entry added by hand still works there.)

## How each source becomes an entry

Every resolver returns a `Proposal`: `{ name, entry, facts }`, where `entry` is the raw mcp.json value (exactly what is written) and `facts` the lines shown in the approval. All fetches go through `get` (`src/tools/web/fetch.ts`: address checks, 20 s, 5 MB, redirects refused across sites) from Marv itself, not the sandbox and not the model's `web_fetch` tool. They need no approval: the user typed the source, and only fixed hosts (registry.npmjs.org, pypi.org, registry.modelcontextprotocol.io, api.github.com) or the URL itself are contacted.

- **npm.** `GET registry.npmjs.org/<pkg>` (the packument). The version is `@ver` if given (must exist, exact), else `dist-tags.latest`. Entry: `{ "command": "npx", "args": ["-y", "<pkg>@<version>", ...serverArgs], "env": {…} }`. Facts: version, its publish date (`time[<version>]`), the maintainers, `repository.url` (marked "as the package states it": npm doesn't verify it), and a warning when the package was first published less than 7 days ago or the version has a `deprecated` message.
- **PyPI.** `GET pypi.org/pypi/<pkg>/json` (or `/<pkg>/<ver>/json`). Entry: `{ "command": "uvx", "args": ["<pkg>@<version>", ...] }`. Facts as npm (upload date, `project_urls`). Known limit: a package whose command has another name than the package needs the registry entry or a hand edit.
- **HTTP URL.** No fetch at all: `{ "type": "http", "url": "<url>", "headers": {…} }`. There's nothing to pin; the approval says the server is remote and runs whatever its owner deploys. A server that needs OAuth comes up `needs login`, and `/mcp add` ends with "then `/mcp login <name>`" (#18).
- **MCP Registry** (`registry.modelcontextprotocol.io/v0/servers`, no key). `/mcp search <words>` lists at most 10 latest, active entries (the API's `search` plus `version=latest`; entries whose official `_meta` status isn't `active` are dropped): name, description, repository, and the `/mcp add <name>` to run. `/mcp add <registry name>` takes the latest version's entry and uses, in order: its first `npm` package, its first `pypi` package, its first `streamable-http` remote. The package then goes through the npm/PyPI resolver **at the version the registry entry names** (so the npm facts are shown too, and the registry can't point at a version npm doesn't have). The entry's `environmentVariables` become `env` as `${NAME}`, its required `packageArguments` with a default or a fixed value become args, a required argument without one must come after `--` (the error lists them), and a remote's `headers` become `${NAME}` references. OCI packages are reported ("Docker images aren't supported yet; the entry says: …"). The registry isn't curated: the publisher's verified namespace (`io.github.<user>` means GitHub sign-in as that user; a domain means DNS proof) and the repository are shown so the user can judge.
- **GitHub repo.** Marv reads the README through `src/tools/web/github.ts` (the API, `GITHUB_TOKEN` to the API host only), takes every fenced code block that parses as JSON and contains `mcpServers` (or is one server entry), and keeps candidates of three shapes: `npx [-y] <pkg>` → npm, `uvx <pkg>` → PyPI, `"type": "http"` with an `https` URL → HTTP. Everything else in the block (extra args, `env` values) is **dropped**, not copied: only the package name or URL is taken from the README, and `${VAR}` names from its `env` keys become `--env` suggestions shown in the approval, not written unless the user passes them. One candidate → its proposal; several → a list of the `/mcp add` commands to choose from; none → an error naming what was found (a docker or `node build/index.js` entry: "needs building, not supported yet"). If the package's own `repository` isn't this repo, the approval says so in its first line. README text never reaches the screen unfiltered (`printable`) and never reaches the model.

Clone-and-build (the issue's `~/.marv/mcp-servers/<name>`) isn't in v1: it runs the repo's build scripts with the user's permissions *before* the approval could mean much (a build can do anything), needs a per-toolchain install recipe, and a git ref is the only pin. Most servers worth installing are published to npm, PyPI or the registry. See open questions.

## The approval

The App puts its own `ApprovalRequest` in the existing queue (the `Approval` component, Esc declines), with a new `once: true` that hides the "don't ask again" choice: every install is its own decision.

```
Add MCP server "filesystem" to ~/.marv/mcp.json (yours, every project)
$ npx -y @modelcontextprotocol/server-filesystem@2026.1.14 ${MARV_PROJECT_DIR}
  runs outside the sandbox, with your permissions and network, started in your home folder
npm      @modelcontextprotocol/server-filesystem 2026.1.14, published 2026-01-14 by jspahrsummers
repo     github.com/modelcontextprotocol/servers (as the package states it)
registry io.modelcontextprotocol/filesystem (namespace verified by the publisher)
reads    GITHUB_TOKEN (not set: it won't start until you set it and restart Marv)
writes   "filesystem": {"command":"npx","args":["-y","@modelcontextprotocol/server-filesystem@2026.1.14","${MARV_PROJECT_DIR}"]}
```

Why each line: the command is what runs; the version, date and publisher are what a user can check a package by; "as the package states it" because npm's `repository` field is unverified; `reads` because `readsOf` already flags a server reading `$OPENROUTER_API_KEY` as worth a look; `writes` is the JSON, byte for byte. The preview is built from `entry` itself (`displayOf`, the function `/mcp` already uses), not from the facts, so what is shown and what is written can't drift (a test checks the written entry equals the shown one).

**Nothing after the approval changes what runs.** All fetching happens before the prompt; after a yes Marv writes `entry` and starts it, fetching nothing to build the command. npm and PyPI never let a published version's files change (npm refuses to republish a version; PyPI refuses to re-upload a file name), so `@<version>` fixes the server's own code. Known limits, stated in the README: npx resolves the package's dependencies by their semver ranges at first run (a dependency can still update; there's no lockfile to pin), and an HTTP server is whatever is deployed at the URL.

## Writing and starting it

- **`~/.marv/mcp.json`** (in `MARV_CONFIG_DIR`'s folder, as `loadMcpConfig` reads it). `addPersonalServer(configDir, name, entry)` re-reads the file just before writing, refuses if it's unreadable or not an object (never overwrite a file the user wrote by hand and broke), adds the key, keeps every other key and server as it was, and writes it with `writePrivate` (0600, atomic; it may hold header references). The entry is re-parsed with `parseMcpServers` first, so `/mcp add` can never write an entry Marv can't load. Never the project's `.mcp.json`: that file is shared with the repository and needs `/mcp trust`, and a command that writes into the project would let an injected instruction ("run /mcp add …") reach teammates.
- **Starting it:** `McpManager.add(config)` appends a connection, connects it (the same `connect`, `cwdFor` home folder, safe base environment), rebuilds, and toggles `settled`/`ready` as `trustAll` does, so a turn that starts meanwhile waits for it. The TUI always creates an `McpManager` (today only when servers are configured), so the first server can be added without a restart.
- **The prompt cache.** `offered()` is read when a turn starts, so nothing changes mid-turn. Then:
  - a conversation that hasn't decided its MCP mode yet decides at the next turn, with the new server counted;
  - a **deferred** conversation: the next turn's note announces the new tools (`announce()` already lists what isn't in `announced`); the tool list and system prompt don't change;
  - an **eager** conversation: the tool list grows, and the cache starts over once. It stays eager: switching to deferred would drop specs the history's calls refer to. `/clear` re-decides.
  - The system prompt's `MCP_TOOLS` paragraph (treat `mcp__` output as data) is now included whenever the session has an `McpManager` (`mcp: Boolean(this.init.mcp)`), so a server added mid-conversation is covered without changing the prompt. `MCP_SETUP` gains one sentence: the user can run `/mcp add <npm package | URL | GitHub repo>`.

## Secrets

Values never go into the file. Env vars come from `--env NAME` or the registry's `environmentVariables` and are written as `"NAME": "${NAME}"`; headers as `"Authorization": "Bearer ${NAME}"`. A `--env NAME=value`, or a header with no `${…}` in it, is refused with the reason (the file lives on disk, and `/mcp`'s display shows the raw config). The approval lists every variable read and whether it's set in Marv's environment now. A variable that isn't set makes `loadMcpConfig` reject the entry (`${X} isn't set`), so in that case the entry is written but not started, and Marv says to set it in the shell and restart.

## /mcp remove and the SDK

- **`/mcp remove <name>`**: only a server in `~/.marv/mcp.json` (a project's server: "edit .mcp.json"); no approval (the user typed it, and it takes capability away). It removes the key (the same read-check-write), and `McpManager.remove(name)` closes the connection and marks it `removed`. Its tools stay in `mcp.specs` until the next conversation, with calls failing "removed with /mcp remove": the same rule as a server that dies today, because an eager conversation's tool list can't shrink under calls already in its history. `/clear` or a restart drops them.
- **SDK: nothing in v1.** SDK users pass `mcpServers` in code, already pinned by whoever wrote the program; writing the user's `~/.marv/mcp.json` from a library would be surprising. The resolvers are plain functions and could be exported later.
- **Headless (`marv -p`)**: no `/mcp add` (it's a TUI command).

## Code layout

- `src/mcp/install/source.ts`: `parseSource`, `serverName`, option parsing (pure).
- `src/mcp/install/npm.ts`, `pypi.ts`, `registry.ts`, `github.ts`: resolvers → `Proposal`; each takes a `get` so tests use `Bun.serve`/stubs.
- `src/mcp/install/proposal.ts`: `Proposal`, `approvalFor(proposal)` → `ApprovalRequest`.
- `src/mcp/personal-file.ts`: `addPersonalServer`, `removePersonalServer`.
- `src/mcp/manager.ts`: `add`, `remove`. `src/commands/index.ts`: `mcp-add`, `mcp-remove`, `mcp-search` actions. `src/app.tsx`: resolve → approve → write → start.

## Testing (failing first)

- `tests/mcp-install.test.ts`: `parseSource` (every row of the table, ambiguous and invalid input), `serverName`; each resolver against a local `Bun.serve` with fixtures captured from the real APIs (pinned version in `args`, a requested version that doesn't exist, deprecated, a young package, the registry's latest/active filtering and its env vars as `${…}`, OCI reported, a README with one / several / no candidates, extra README args dropped, a repository mismatch flagged); `--env NAME=value` and literal headers refused.
- `tests/mcp-personal-file.test.ts`: adds beside existing servers and keys, 0600, refuses an unreadable file and a clash, remove leaves the rest; what's written loads back through `loadMcpConfig` unchanged.
- `tests/mcp.test.ts`: `McpManager.add` starts the fixture server and its tools appear; a manager created empty; `remove` closes it and calls fail clearly.
- `tests/session.test.ts`: after `add`, a deferred conversation's next message announces the tools with the tool list and system prompt unchanged (the "every request extends the previous one" check); an eager one stays eager.
- `tests/app.test.tsx`: `/mcp add` shows the approval with the command and the JSON, no "don't ask again"; no writes nothing; yes writes exactly the shown entry and starts it; a fetch error is shown and writes nothing.

## Decided with the user (2026-10-12)

1. **Published packages only.** No clone-and-build from GitHub: a README may nominate an npm/PyPI package or a URL, nothing else.
2. **Docker/OCI images** stay out of v1 (reported as unsupported, as above); a later issue if needed.
3. **`/mcp search`** is the catalog for v1; a picker can come later.
4. OAuth servers: #18 lands in the same sprint, so an added HTTP server that needs a login ends with "then `/mcp login <name>`" (see the #18 spec), instead of "not supported".
