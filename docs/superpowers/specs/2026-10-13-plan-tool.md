# The plan tool: a checklist the model keeps for long tasks

Issue: #15 (spec first, sprint 4, #32). Related: compaction (`src/compact.ts`), saved sessions (`src/sessions.ts`), the evals (`evals/`).

## Problem

On a long task (a feature touching six files, a refactor with follow-ups, a request with five separate asks in one paragraph) the model works one step at a time and the requirements live only far back in its history. Two things go wrong. The model forgets part of the request: it fixes the code, runs the tests, and answers, with the README and the changelog it was asked to update untouched. And after compaction the request survives only as the summary's paraphrase, so "what's left" is whatever the summary happened to keep. The user, meanwhile, sees a stream of tool calls and can't tell whether Marv is on step two of three or of twelve.

A plan the model writes down at the start and ticks off as it works fixes both: writing it makes the model enumerate the asks once, re-reading it (its own last call is in the history) tells it what's left, and the TUI can show it. Claude Code's `TodoWrite` is the same idea; this spec makes Marv's version fit its rules (prompt cache, compaction, resume, subagents).

## Decisions

- **One tool, `plan`, that replaces the whole list.** No ids, no patches, no separate "mark done" tool.
- **It stores items `{ text, status }`, status `pending` | `in_progress` | `done`, at most one `in_progress`** (that one is "the current item"). At most 20 items, each 1–200 characters. An empty list clears the plan.
- **The plan is the session's state**, set only by the tool: `MarvSession` holds it, saves it with the session, and re-injects it after compaction. The user doesn't edit it.
- **The model sees the plan only through its own calls and through compaction's summary message.** Nothing changes the system prompt or the tool specs mid-conversation, and no note is appended per step (prompt cache).
- **The TUI pins it above the prompt** while it has unfinished items; each call is also an ordinary transcript entry (`Plan · 2/5 done`).
- **Main agent only.** Subagents get no plan tool.
- **On by default; `SessionInit.plan` / SDK `plan: false` turns it off for a session** (the eval's "off" arm). Fixed for the session's life, because it changes the tool list.

## The tool (`src/tools/plan.ts`)

```ts
input: z.object({
  items: z.array(z.object({
    text: z.string().min(1).max(200),
    status: z.enum(["pending", "in_progress", "done"]),
  })).max(20),
}).refine(at most one in_progress)
```

Description (what the model reads, kept constant): use it for a task of three or more steps, or when the user lists several things; write the plan before starting, mark an item `in_progress` before working on it and `done` as soon as it is, add items you discover, remove ones that turn out unnecessary; send the whole list each time; skip it for a one-step task or a question.

**Why whole-list replace.** The list is short (20 items of at most 200 chars is ~1k tokens worst case, a typical plan ~150), so resending it costs little output. It is idempotent and has nothing to get wrong: a patch API needs ids the model must carry from an earlier result, and small models already confuse call ids. Every call is a complete snapshot, so the latest call in the history *is* the plan, which is what makes it survive without extra notes. A malformed call (two `in_progress`, 25 items) is an ordinary validation error the model fixes in its next call.

**No approval, no `kind`.** It changes nothing outside the session, like a read tool; yolo doesn't matter. Not `parallel`.

**Result.** To the model: one line, `Plan saved: 2 of 5 done; now: Write the tests.` (or `Plan cleared.`); the list itself is already in the call. To the screen: `ToolResult.plan` (the items), like `diff` a screen-only field: `runAgent` sends `output`, trajectories record named fields. `summary`: `2/5 done`. `label`: `Plan`.

**Where the state goes.** A new `ToolContext.plan?: PlanHost` (`{ set(items): void }`), which the session gives the main agent's context only, as it does `agentHost`. A call without one (a subagent that somehow names it, an SDK tool list without it) is `ToolError("The plan tool isn't available here.")`. `runTool` already refuses tools not in `available`, so this is defense in depth.

## Prompt cache

The rules (CLAUDE.md, Prompt cache) hold without exceptions:

- The tool spec is built once (`toolSpecs`), and `toolSpecsFor` drops it when the session has `plan: false`, decided at construction; `configure()` can't toggle it.
- The system prompt gains one constant sentence in its tools paragraph when `plan` is offered (`systemPrompt` already takes the tool names): "For a task with several steps, keep a plan with the plan tool and update it as you go." Fixed per session, like the web section.
- The plan reaches the model through its own tool calls (already in the history, appended only) and through the compacted summary message (where the cache starts over anyway). No per-step reminder note: it would be an appended user message (cache-safe), but it is noise on every step and small models start answering the reminder instead of the task. If the eval shows models let the plan go stale, a reminder is the follow-up (see Open questions).

## Compaction

The summary replaces the history, and with it the plan calls. So `compactedHistory(summary, plan?)` appends the plan to the summary's user message when one is set and unfinished:

```
This conversation was compacted to save space. Here is a summary of everything before this point:

<summary>

Your plan (from the plan tool), as it stood:
- [done] Read the report command
- [in progress] Add the --json flag
- [pending] Update README and CHANGELOG
Keep updating it with the plan tool.
```

This covers both compaction paths, because both go through `summarizeInto`: before a user message (that message follows) and mid-turn (`MID_TURN_NOTE` follows, unchanged). It's structured text from the session's state, not the model's paraphrase, so nothing is lost. The summary instruction stays as is (it already asks for "what's done, what's left").

## Resume and clear

- `SavedSession` gains `plan?: PlanItem[]`, written by `save()` and schema-checked on load (`SessionShape`: a bad `plan` drops the plan, not the session). `resume()` restores it, and `Resumed` carries it so the App can pin it again. The model needs nothing extra: a resumed conversation is byte-identical, so its last plan call (or the compacted summary that holds the plan) is still in it.
- `clear()` drops the plan (a new conversation). `configure()` and a new turn leave it alone: the plan spans turns ("now also do X" can add an item).
- `Session.plan` (read-only getter) lets SDK clients read it; each change also arrives as the `tool_end` event's `result.plan`. No new `SessionEvent`.

## The TUI

`src/ui/PlanView.tsx`, pinned between the transcript's `ScrollView` and the approval/prompt, shown while the plan has an item not `done`:

```
 Plan 2/5 ─────────────────────────────
  ✓ Read the report command
  ✓ Parse the new flag
  ▸ Add the --json output           (in progress, highlighted)
  ○ Update README and CHANGELOG
  ○ Run the tests
```

At most 6 rows: with more items, done ones collapse into the header's count and the list shows the current item and the next ones, then `+N more`. Hidden on windows under 20 rows (the transcript needs them). Hidden once every item is done (the transcript entry shows the final `5/5 done`). Text passes through `printable()`. Colors from `theme.ts`. It re-renders only when the plan changes (memoized; the plan updates at `tool_end`, inside the 33 ms flush). In an `AgentView` it stays (it's the main agent's plan).

Why pinned, not only the transcript: the transcript scrolls away within a few tool calls, and "where is Marv in this task" is a question the user asks while it works. The transcript entry stays, so the history of plan changes is still visible.

## Subagents

None. A subagent gets one self-contained task and returns one report; its 50 steps are well inside what it can track, and a plan of its own would need a second panel and a second state with no reader. `plan` is not in `SUBAGENT_TOOLS`. A Claude Code agent file listing `TodoWrite` stays reported as a problem, as today.

## Headless and trajectories

`marv -p` gets the tool too (it's the SDK); its output shows nothing for it beyond the usual tool line. Trajectories need no new record: the `tool` record holds the call and its result. `bun run stats` is unchanged.

## The eval

Question: on long multi-step tasks, does the plan tool raise the pass rate (and does it cost steps on short ones)?

- `evals/run.ts --plan on|off` (default on), passed as the SDK's `plan`. `RunResult` gains `planCalls` (calls to `plan`) and `planOpen` (the run ended with an answer while the plan still had unfinished items: the model let it go stale), and `testsPassed`/`testsTotal` parsed from the check's `bun test` summary, for partial credit: a plan should turn "forgot one of five asks" into a pass, and pass/fail alone hides 4/5 vs 1/5.
- **Two new tasks** where forgetting is the failure mode, each with a hidden check per requirement:
  - `multi-ask`: a small CLI (`report` command) and one prose paragraph, written like an issue, with five asks scattered through it: a `--json` flag, a renamed option with the old name kept as a deprecated alias that warns, a fix to an off-by-one in the totals, the README's usage section, and a CHANGELOG entry. Not a numbered list (a numbered request is already a plan).
  - `callback-to-promise`: a module with a callback API and seven callers across five files plus their tests; convert to async/await everywhere, keep one exported callback wrapper for compatibility. Long enough to need 20+ steps.
- **Arms:** plan on vs off, same day, same models. Models as in #14's measurement: `anthropic/claude-sonnet-5.5`, `openai/gpt-oss-120b`, `qwen/qwen3.5-9b` (check the ids against OpenRouter's list first). 2 tasks × 3 models × 3 repeats × 2 arms = 36 runs, plus a regression pass: the 17 existing tasks once, one model (Sonnet), both arms (34 runs), to see whether the tool costs steps or passes where there's nothing to plan.
- **Budget:** `--budget 3` per arm on the new tasks, `--budget 2` per arm on the regression pass: at most $10 in all. Long tasks on Sonnet cost roughly $0.20–0.40 a run, the others far less.
- **Ship on by default** if "on" is no worse on pass rate overall, better (or better in `testsPassed`) on the two new tasks for at least two of the three models, and costs at most ~10% more steps on the existing tasks. Otherwise keep the tool with `plan: false` as the default and report why.

What the eval doesn't cover: compaction. On OpenRouter a model's window is far larger than these tasks; plan survival across compaction is covered by unit tests (a scripted provider and a small `contextLength`).

## Testing (failing first)

- `tests/plan-tool.test.ts`: validation (two `in_progress`, 21 items, empty text, 201 chars → errors the model can read), the output line, `ToolResult.plan`, no host → `ToolError`, no approval asked even with an approver that says no and yolo off.
- `tests/session.test.ts`: a `plan` call sets `session.plan`; `clear()` drops it; `save()`/`resume()` round-trip; a bad saved `plan` is dropped, the session still loads; `plan: false` → the spec is absent from every request and from the system prompt; the system prompt and specs are identical before and after plan calls (each request extends the previous one, as `tests/agent.test.ts` checks); a subagent's tool list has no `plan`.
- `tests/compact.test.ts` (or the session's compaction tests): `compactedHistory` with a plan appends it, with a finished or no plan doesn't; mid-turn compaction keeps the plan in the request that follows, before `MID_TURN_NOTE`.
- `tests/app.test.tsx`: a scripted `plan` call pins the panel with the current item; a full plan clears it; a resumed session shows it; `/clear` hides it; the collapsed rows with 12 items.
- `tests/system-prompt.test.ts`: the sentence is there only when `plan` is offered.

## Open questions for the user

1. **Budget and models for the eval** ($10 cap, the three models above, 3 repeats): OK, or a different mix (e.g. a local Ollama model instead of qwen via OpenRouter)?
2. **A reminder when the plan goes stale.** v1 has none (cache-safe either way, but noisy). If the eval shows `planOpen` often, should a follow-up add a `Marv:` note after N steps without a plan call (Claude Code does something like it), or rather drop the tool's default to off?
3. **A TUI switch.** v1 has only the SDK/eval option. Should the TUI get config `plan` (and `/plan on|off`, applying from the next `/clear`, since it changes the tool list), or is always-on enough?
