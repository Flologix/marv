# MCP OAuth: logging in to remote MCP servers

Issue: #18 (spec first). Related: #6 (`/mcp add` and the catalog: shares `src/mcp/manager.ts` and `/mcp`, lands first), #14 (deferred tools: what makes a 40-tool server like GitHub's affordable), #27 (Connect GitHub, today with a hand-made token).

## Problem

A remote (Streamable HTTP) MCP server that wants a login can only be used today with a token pasted into `headers` (`"Authorization": "Bearer ${TOKEN}"`): create a personal access token by hand, export it, rotate it yourself. The MCP spec defines a login instead: the server answers 401 with `WWW-Authenticate: Bearer resource_metadata=…`, the client discovers the authorization server (RFC 9728, RFC 8414), registers itself (dynamic client registration, RFC 7591) if it has to, and runs an OAuth 2.1 authorization-code flow with PKCE, sending a resource indicator (RFC 8707).

The MCP SDK (1.32.0, which Marv has) already implements the client side: `StreamableHTTPClientTransport` takes an `authProvider: OAuthClientProvider`, sends its access token on every request, and on a 401 calls `auth()` (`client/auth.js`), which discovers, registers, refreshes with the refresh token, or, as a last resort, calls the provider's `redirectToAuthorization(url)`, after which `connect()` throws `UnauthorizedError` and the app calls `transport.finishAuth(code)` once the browser comes back. PKCE (S256) and the `state` parameter are the SDK's (`startAuthorization`); storing everything is the provider's job. So Marv writes one provider, a store, a loopback listener and the UX; no GitHub-specific code.

## Decisions

- **Only the user starts a login, with `/mcp login <server>`.** Startup, a tool call and the model never open a browser: a server that needs a login shows as `needs login` (startup notice, `/mcp`), and its calls fail with a message saying so. There's no tool for logging in.
- **Tokens live in `~/.marv/mcp-tokens.json`** (in `configDir`), written with `writePrivate` (0600 in a 0700 folder, atomic, queued), keyed per **server URL and owner**: your servers (personal and SDK) share one login per URL across projects; a project's server gets its own, per project. Log in once in the TUI and `marv -p` and SDK sessions using the same config folder reuse (and refresh) it.
- **The redirect is a loopback listener on `127.0.0.1` with a random port**, PKCE and `state` from the SDK. Where no browser can open (SSH, no display), Marv prints the URL, and the user pastes the address the browser ends up on; the listener and the paste both work, whichever comes first.
- **Refresh is the SDK's**, on a 401 from the server; Marv only makes it safe across two Marv processes and keeps it from ever falling through to a browser.
- **Project servers are trusted before any network contact, login included.** `/mcp login` on an untrusted server says "trust it first: /mcp trust".
- **The SDK and headless mode get no interactive login in v1**: they use stored logins and report a server that needs one.
- **A token never reaches the model, the transcript, a session file, a trajectory or a sandboxed command** (see Secrets).

## The login flow

`/mcp login github` (a server that is configured, `type: "http"`, trusted, and has no `Authorization` header of its own):

1. Marv starts the callback listener: `Bun.serve` on `127.0.0.1`, port 0 (the OS picks), path `/callback`. If the server has a stored client registration with a port, that port is tried first (see Registration).
2. It connects with an **interactive** provider (below). The SDK discovers, registers if needed, and calls `redirectToAuthorization(url)`. Marv checks the URL is `https:` (or `http:` on a loopback host, for tests), then shows in the transcript: `Log in to github at api.github.com: opening your browser… If it doesn't open, open this link and, if your browser then shows an error page, paste its address here: <url>` and opens it with `xdg-open` / `open` (spawned with the URL as one argument, no shell; skipped, link only, when there's no `DISPLAY`/`WAYLAND_DISPLAY` on Linux or `SSH_CONNECTION` is set).
3. The callback (from the browser, or a pasted `http://127.0.0.1:<port>/callback?…` message, which the App hands to the login instead of sending it to the model) is checked: `state` must match (a constant-time compare), an `error` parameter becomes the login's error. The browser gets a short "You can close this tab" page; the listener closes after the first valid callback.
4. `transport.finishAuth(code)` exchanges the code (with the PKCE verifier) for tokens, which the provider stores; Marv then reconnects the server as at startup, lists its tools, and rebuilds the tool list (`rebuild()`), as `/mcp trust` does.
5. The transcript says `github: logged in · connected · 41 tools`, or why not.

A login gives up after 5 minutes. `/mcp login <server>` again (or `/mcp logout <server>`) cancels the one waiting. The login isn't a turn: the prompt stays free, and a turn running meanwhile keeps its tool list. New tools reach the model **the way `/mcp trust`'s do**: from the next turn, announced in a note in a deferred conversation (#14, cache intact), or as new specs in an eager one (the cache starts over once, as trusting does today).

Why loopback, not a pasted code: a public client's redirect must be a URL the authorization server accepts, and RFC 8252 (native apps) says loopback IP redirects with any port, plus PKCE, which the MCP spec's authorization section recommends for native clients. An out-of-band "copy this code" page needs the server to host one (most don't), and the device flow isn't in the MCP spec or the SDK. `127.0.0.1`, not `localhost` (RFC 8252 §8.3: a name can resolve elsewhere). The paste fallback covers a browser on another machine: the redirect fails there, but its address still holds the code and state.

## The provider (`src/mcp/oauth.ts`)

`McpOAuthProvider implements OAuthClientProvider`, one per HTTP server, backed by the store, in one of two modes:

- **passive** (startup, tool calls, the SDK): `tokens()`, refresh and `saveTokens()` work; `redirectToAuthorization()` throws `LoginNeeded` instead of opening anything, and `saveClientInformation()` throws too, so a background connection never registers a client with a server the user never logged in to.
- **interactive** (`/mcp login` only): `redirectToAuthorization()` hands the URL to the login UI; registration is allowed.

`redirectUrl` is `http://127.0.0.1:<port>/callback` (always defined: an undefined one makes the SDK try a non-interactive client-credentials grant). `clientMetadata`: `client_name: "Marv"`, that `redirect_uris`, `grant_types: ["authorization_code", "refresh_token"]`, `response_types: ["code"]`, `token_endpoint_auth_method: "none"` (a public client), and `client_uri` the repository. The PKCE verifier stays in memory: a login lives in one process. `saveDiscoveryState`/`discoveryState` cache discovery in the store, so a startup with tokens makes no discovery requests. The SDK stamps tokens and clients with their `issuer`; they're stored unchanged (the SDK then never sends a refresh token to another authorization server).

**At startup**, a server with no stored tokens connects **without** an `authProvider` (so the SDK can't run discovery or registration in the background); a 401 then means `needs login` (a server with its own `Authorization` header gets `failed: the server refused the token in headers`, as today). One with stored tokens connects with a passive provider: an expired access token is refreshed by the SDK on the first 401; a refresh that fails reaches `redirectToAuthorization`, which throws `LoginNeeded`, and the server is `needs login`. The same happens mid-session: a tool call whose refresh fails returns `ToolError("github needs a new login: the user can run /mcp login github")`, the state changes to `needs login`, and the App shows one notice. Its tools stay listed (the tool list is fixed), and later calls fail the same way until the login.

**Registration.** Dynamic registration happens on the first login (interactive only) and is stored with the port it registered (`redirect_uris` is part of the registration, and not every server honors RFC 8252's "any loopback port"). Later logins reuse that port; if it's taken, Marv picks another, drops the client, and registers again. A server without dynamic registration (`registration_endpoint` missing) needs a pre-registered client, in the config:

```json
"github": { "type": "http", "url": "https://api.githubcopilot.com/mcp/",
            "oauth": { "clientId": "Iv1.abc…", "clientSecret": "${GITHUB_MCP_CLIENT_SECRET}", "callbackPort": 33418 } }
```

`oauth` (all optional; `clientSecret` should be a `${VAR}`, like `headers`) is part of the raw entry, so it's in the trust key and in `/mcp`'s display (unexpanded). With `clientId`, `clientInformation()` returns it (and `token_endpoint_auth_method` becomes `client_secret_post` when a secret is given); `callbackPort` fixes the port, since such a client's redirect URI is registered by hand.

**Refresh across processes.** Servers that rotate refresh tokens break a naive store: Marv A refreshes and saves; Marv B still holds the old refresh token, gets `invalid_grant`, and the SDK calls `invalidateCredentials("tokens")`, then retries. The provider re-reads the file in `tokens()` (small, and only on connect and on 401s), and `invalidateCredentials("tokens")` deletes only if the stored refresh token is still the one that failed; otherwise it keeps the newer one, and the SDK's retry refreshes with it. Within one process, calls to a server are sequential (MCP tools aren't `parallel`, subagents get none), so two refreshes don't overlap.

## The store (`src/mcp/oauth-store.ts`)

```
~/.marv/mcp-tokens.json   (0600, writePrivate)
{ "v": 1, "logins": {
    "personal https://api.githubcopilot.com/mcp/": {
      "server": "github", "client": { …, "issuer": "…", "port": 50214 },
      "tokens": { "access_token": "…", "refresh_token": "…", "expires_in": 28800, "issuer": "…" },
      "savedAt": 1791820800000, "discovery": { … } },
    "project:<projectKey> https://mcp.example.com/": { … } } }
```

- **Key: owner + URL**, the URL as expanded (with its path: one host can serve several resources, and tokens are issued for one resource). Not the server's name: renaming a server in `mcp.json` keeps the login, and two names for one URL share it. Not shared between owners: trusting a project's `.mcp.json` means "run this server", not "act as my GitHub account"; a repository that names your server's URL would otherwise get your login by the trust you gave it for something else. `server` is only for display.
- Schema-checked with zod on read; unreadable or the wrong shape is "no logins" (everyone logs in again), never a crash, as `McpTrust` does. Writes are read-modify-write through `writePrivate`'s per-file queue; `savedAt` lets `/mcp` show when a token expires.
- `/mcp logout <server>` removes the entry (client, tokens, discovery), revokes the refresh token when the authorization server lists a `revocation_endpoint` (RFC 7009, best effort, 5 s), closes the connection, and sets the server to `needs login`. If there's nothing to revoke against, the transcript says the grant still exists on the provider's side and where it's usually removed.

## `/mcp` and #6

`McpState` gains `"needs-login"`; `McpServerStatus` gains `login?: { loggedIn: boolean; expiresAt?: number; host?: string }` (the authorization server's host, for "log in at api.github.com"). `/mcp` shows:

```
- github (yours): connected · 41 tools · logged in at github.com (token renewed automatically) …
- linear (yours): needs login: `/mcp login linear`
- docs (this project): not trusted yet: … (`/mcp trust` to start it)
```

`/mcp login <server>` and `/mcp logout <server>` join `trust` as subcommands (new `CommandAction`s `mcp-login`/`mcp-logout`; usage errors name the servers that can log in). A startup notice lists servers that need a login, next to the existing untrusted notice. The `/` menu completes server names after `login`/`logout`.

For #6: its catalog shows registry entries' remotes; `probeLogin(url)` (exported from `oauth.ts`: an unauthenticated fetch of the server's protected-resource metadata through the SDK's `discoverOAuthProtectedResourceMetadata`, 5 s, no registration) lets an entry say "needs login" before it's installed, and an added HTTP server that comes up `needs-login` ends `/mcp add` with "then `/mcp login <name>`". #6 lands first; this rebases onto its manager and command changes.

## The SDK and headless mode

`createSession` reads and refreshes logins from `configDir`'s `mcp-tokens.json` with the passive provider; a server that needs a login is reported through `onWarning` (`MCP server "github" needs a login: run marv in a terminal and /mcp login github; logins are stored in <configDir>/mcp-tokens.json`), and its calls fail with the same text. No `onAuth` callback in v1: a library has no prompt to paste into, a loopback redirect only works on the user's own machine, and a program opening a browser because a server returned 401 is surprising. The common case (a script or CI job using a server you already logged in to) works through the shared store. `marv -p` is built on the SDK and behaves the same. A later `session.mcpLogin(server, { open(url) })` can add it without changing the store.

## Secrets: where a token can't go

- **The model**: tokens exist only in the store and in the transport's `Authorization` header. Errors the model sees are Marv's own text (`LoginNeeded`, `UnauthorizedError` → "needs a new login"), never a raw HTTP or OAuth error body. No tool can start a login, read the store or call `/mcp`. `read_file`/`grep`/`web_fetch` can't reach `~/.marv` (`resolveInProject`; web_fetch refuses loopback addresses, the callback listener's included).
- **The transcript, session files and trajectories**: the transcript shows the authorization URL (it holds a `state` and a PKCE challenge, neither secret) and never the callback's `code`: a pasted callback URL is consumed by the login before it becomes a message, and shown as `(login callback)`. Trajectories record nothing of a login; `/mcp` shows `display` (unexpanded config) and expiry, never a token.
- **Sandboxed commands**: the store is under the home folder, which the sandbox replaces with an empty one (only toolchains and `~/.marv/skills` come back); the environment is cleared. A sandboxed command with `network: true` shares the host's network and could reach the callback port, but without the `state` its callback is refused, and a code is useless without the PKCE verifier. (With `MARV_CONFIG_DIR` inside the project, as in some tests, the store is as exposed as `config.json`'s API key already is.)
- **Other sites**: the SDK sends the token only to the server URL; its default redirect policy follows redirects only within the origin. Discovery URLs come from the server, which is yours or trusted.

## Decided with the user (2026-10-12)

1. **No built-in GitHub App.** A server without dynamic registration (GitHub's hosted one among them) needs the user's own `oauth.clientId` (and `clientSecret` as a `${VAR}`). The README keeps #27's fine-grained token as the simple path for GitHub and documents `oauth.clientId` for those who register their own app.
2. **`oauth.scope`** (a space-separated string) is added to the config's `oauth` object: when set, it's the scope Marv asks for, overriding the SDK's order (the 401's scope, then the metadata's `scopes_supported`); without it, the SDK's order applies.
