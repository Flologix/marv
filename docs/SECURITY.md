# Security model

**Principle:** prompt injection can't be filtered out, so it's contained. An injected model must never hold all three of these together:
- private data;
- untrusted content in its context;
- a way out (network, the mesh, or code that runs outside the sandbox).

These rules are requirements for the Rust build from day one. They come from a security review of Marv 0.3.0 (2026-10-12); see the repository's security advisories.

## Process and launch
- **One static binary.** No interpreter reads the project's `bunfig.toml`, `.env`, `node_modules` or similar. Config comes only from:
  - `~/.marv/` (or `$MARV_CONFIG_DIR`, but only from the real environment, never from a file in the project);
  - the project's `.marv/` (trust-gated) and `.mcp.json` (trust-gated).
- **Session-start hooks come only from the user's own config (#108).** `hooks.sessionStart` is read from `~/.marv/config.json` (or `$MARV_CONFIG_DIR`'s) and nowhere else: a project has no config layer, and a project's `.marv/config.json` naming `hooks` is refused with a startup note and never run (it's only looked at if it's a regular file inside the project, and read up to 1 MB) (cloning a repository must not run its commands, the class of hole 0.3.0's `bunfig.toml` preload was). Hooks run outside the sandbox without asking, since the user wrote them: with the host door's environment (Marv's keys and secret-looking variables left out), a timeout (default 15 s, the process group killed) and an 8 KB output cap. The user's config is out of the sandbox's reach (a stand-in home; when the project is the home folder, the home is read-only in the sandbox with `~/.marv` hidden, and `.marv/**` is protected for the edit tools), so the model can't plant a hook either. **Their output taints the session** when it's sent (`Provenance::Hook`) and is fenced as data (`<untrusted-data source="hook">`): the user chose the command, not what it prints (`bd ready` lists issue titles anyone can file on a public repository). Only `"trusted": true` on a hook in the user's config opts it out; empty output taints nothing. Guards: `tests/guards/tests/launch.rs` (`a_projects_session_start_hooks_never_run`, `marv_p_never_runs_a_projects_hooks`, `hook_output_taints_the_session`).
- **Model output is never written to the terminal raw.** Every string goes through `printable()`, which strips CSI/OSC/DCS, C0/C1 controls and bidi overrides. This includes headless text mode.

## Sandbox (`marv-sandbox`)
- **bubblewrap**, with:
  - read-only system directories and an empty `/run` (except the mesh plug, `/run/marv/mesh.sock`, and the process door's relay: Marv's binary at `/run/marv-bin` and socket folders under `/run/marv`);
  - a stand-in home, with toolchains re-mounted read-only and credential files masked;
  - the project writable, with `.git` and **protected paths** read-only;
  - Marv's config folder (`~/.marv`, or `MARV_CONFIG_DIR` wherever it is) hidden;
  - no network unless approved (`--unshare-net`), a cleared environment, and its own PID namespace.
- **Protected paths ask even in yolo, and are read-only inside the sandbox:**
  - `.git/` and the `core.hooksPath` folder;
  - `.env*`, `.envrc`, `bunfig.toml`, `.mcp.json`;
  - `AGENTS.md`/`CLAUDE.md` at any level, and `.marv/**`;
  - `.vscode/`, `.idea/`;
  - `package.json` lifecycle `scripts`;
  - when the project is the home folder (or holds it), where `edit_file`/`write_file` run outside the sandbox and reach the whole home: every hidden top-level entry of the home (`~/.bashrc`, `~/.profile`, `~/.config/systemd/user/`, `~/.config/autostart/`, `~/.ssh/authorized_keys`, `~/.local/bin/`…) and the hooks folder (`core.hooksPath`) of the global git config and of any repository in the home (`home_rule`; guard `in_the_home_folder_dotfiles_and_hooks_ask_even_in_yolo`).
- **Secrets** (`.env*`, `*.pem`, `id_*`) need approval to read, and are masked in the sandbox.
- **In the home folder, the sandbox shows the home read-only and hides Marv's config, credentials and agent sockets.** When the project is the home folder or a parent of it (`/`, `/home`), a stand-in home would hide the project, so instead the project is mounted read-only (never read-write), and on top of it every hidden top-level entry of the home (`~/.<anything>`: `~/.marv`, `~/.ssh`, `~/.gnupg`, cloud CLI folders, `~/.claude`, `~/.config`, `~/.local`, `~/.cache`) is hidden, apart from the toolchain folders (shown read-only, credential files masked); the named ones (`~/.config/herdr`, `~/.config/gh`, `~/.docker`, `~/.kube`, `~/.local/share/keyrings`…) stay hidden even if a toolchain mount would show them, and every Unix socket or FIFO a bounded scan finds in the visible part of the home is replaced by `/dev/null` (a read-only mount doesn't stop a `connect()`). Sandboxed commands write only to `/tmp` there; the edit tools keep their approvals, a change to a dotfile or a git hooks folder there is a protected path (it asks every time), and yolo is refused. Every other file change there (`edit_file`, `write_file`: a `Write` tool with the `files` scope) is asked `once` (`registry::home_file_write`), and never run on yolo even by a context that has it: Yes or No, no "always"; neither a remembered "files" scope nor the config's `"approve": ["files"]` covers it (both go through `SessionApprover`, which never answers a `once` request), the TUI's "always" on another queued request doesn't answer it, and a worktree subagent's automatic yes (`SubagentApprover`) doesn't either. `marv -p --approve files` still approves it: the flag names the scope for that one run and answers "yes" per call (`ScopeApprover`), never "always". Guards: `tests/guards/tests/approvals.rs` (`in_the_home_folder_always_on_a_file_change_still_asks_the_next_time`, `in_the_home_folder_a_file_change_request_is_once`, `in_the_home_folder_config_approve_files_doesnt_cover_a_file_change`, `headless_config_approve_files_in_the_home_folder_is_refused`, `a_subagents_automatic_yes_doesnt_cover_a_once_request`, `a_project_under_the_home_keeps_always_for_file_changes`, `headless_approve_files_in_the_home_folder_still_writes`). A home that can't be listed runs no command. An extra read-only or writable folder can never be the home or a parent of it. Guards: `tests/guards/tests/sandbox.rs` (`in_the_home_folder_no_socket_under_the_home_is_reachable`, `in_the_home_folder_credentials_and_marvs_config_are_hidden`, `in_the_home_folder_nothing_in_the_home_is_writable`, `a_project_in_a_subfolder_of_the_home_stays_writable`).
- **The project's own tooling runs only inside the sandbox.** The typecheck after an edit, the project's checks (`.marv/checks/`) and the project's formatter after an edit (#67) run in the sandbox, the project read-only, without network; without a sandbox they don't run at all, and Marv never installs a formatter. The formatter is the project's own code, and it gets write to the one file being formatted — except on protected paths and `package.json`, which keep exactly what the edit tool wrote: a rewrite there could turn an approved diff into anything (a `postinstall` script into `package.json`, a planted `.vscode/` or `.marv/` file). A failing formatter's output reaches the model fenced as project data, like the checks'.
- **Every path is checked after `realpath`.** No tool follows a symlink out of its root. That includes skill files, which the old code read outside the sandbox, and instruction files (`AGENTS.md`/`CLAUDE.md`: the project's, its parents', nested ones), which also never lead to a secret or into `node_modules`/`target`/`.git`; only the user's own `~/.marv/AGENTS.md` may link anywhere.
  - The one exception: a **personal** skill folder (`~/.marv/skills/<name>`) may be a symlink to a folder only root can change, such as Omarchy's `/usr/share/omarchy/…` (#75). That folder and every folder above it must be owned by root and not group- or world-writable. The skill is read from the link's real target, and its `SKILL.md` and files can't lead out of that folder. A project's skill folder never may.
- **The one read outside the project is the session's saved tool outputs (#61).** `read_file` and `grep` may read the files in `~/.marv/tool-output/<session>/`, and nothing else outside the project. Writing tools can't, and bash can't see the folder at all. A saved output keeps its source in its name (`<call id>.mcp.txt`), so an MCP server's text read back is fenced and taints as it did when it came.

- **On macOS (Seatbelt).** The macOS sandbox is built from the same plan as bubblewrap's (`marv_sandbox::seatbelt`, #164): a deny-default SBPL profile for `/usr/bin/sandbox-exec`, with reads allowed for the whole disk and then narrowed, writes only to the project, the writable extras and a private `TMPDIR`, and every path canonical and passed as a parameter, never written into the profile (a project path that can't be written into the protected-name regexes stops the command). It isn't the active backend yet (#166): until then, macOS commands run unsandboxed with the warning, as on Linux without bwrap. Seatbelt can refuse a path but can't show something else there, so these guarantees differ from bubblewrap's:

  | bubblewrap | Seatbelt | Mitigation | What's left |
  |---|---|---|---|
  | A stand-in home: empty, writable, thrown away | The home is unreadable and unwritable | Caches in the private `TMPDIR`; the home note says reads and writes there are refused | Tools that insist on writing `~/.something` fail instead of working on a throwaway copy |
  | Credential files read as empty | Reading them is refused | Denied by the path as written and where it leads | A tool that expects the file to exist and be empty errors out |
  | A private `/tmp` | `/tmp` is the host's | A private `TMPDIR` per command (0700, made by Marv, removed after, refused unless it's a folder of its own); `/private/tmp` and the user's `/var/folders/<xx>/<id>` denied (a command whose user folder can't be found doesn't start) | Tools that hard-code `/tmp` fail |
  | Its own PID namespace | None | Signals and process info only within the sandbox; no `kern.proc.all` | Other processes' pids can be guessed but not used |
  | Dies with Marv (`--die-with-parent`) | None | `marv __guard`: its own process group, watches its parent, kills the group when Marv dies; everything is killed on exit | A process that leaves the group and double-forks outlives the command, still sandboxed |
  | `--new-session` | No flag | `setsid()` in the guard, stdin `/dev/null`, terminals and pseudo-terminals denied | None known |
  | Its own loopback without network | None: loopback is the host's | Without network every IP connection is refused, loopback included, but for the forwarded ports of your background processes | In-sandbox client/server tests need network (which asks) |
  | Protected paths mounted read-only | Write denies by path | The path and where it leads, `literal` and `subpath`; the protected names as case-insensitive regexes at any depth (outside `node_modules`, `target` and `.git`), so a command can't create them either; folders above a protected path can't be removed or renamed; the after-scan still runs | The after-scan is load-bearing for names: a protected name written inside `node_modules` or `target` (which the rules skip) and then moved out by renaming that folder isn't stopped by a rule, only found and reverted after the command; the same for a nested `.git` |
  | A hard link can't cross a mount (`EXDEV`) | Hard links are path operations | Nothing denied (the home, `~/Library`, Marv's folders, credentials, protected paths, read-only folders) may be a hard link's source, so a protected file can't be written, nor a credential read, through a second name. Tools that hard-link inside a project under the home fall back to copying | The rule's operation is to be confirmed on macOS |
  | A home-folder project hides every hidden top-level entry | The same, by one regex, plus `~/Library` (where macOS keeps keychains, cookies, mail, messages and app data) | None needed | The rest of the home stays readable, as on Linux |
  | The home-folder project's socket scan, bounded | Every Unix socket refused unless named | None needed | Stronger: no depth or count limit |
  | With network, abstract sockets reachable | No abstract sockets; Unix sockets stay closed with network | None needed | Stronger |
  | — | Mach and XPC services (`open`, `osascript`, `launchctl`, the pasteboard, the keychain) | Deny-default; a short reviewed `mach-lookup` list; XPC services denied last | Every service added is a review item |
  | No new privileges (bwrap sets `no_new_privs`: a setuid program gains nothing) | No `no_new_privs` | The program still runs in the sandbox, with its rules | A setuid or setgid program (`sudo`, `su`) runs with raised privileges inside the sandbox; a rule refusing them waits for the macOS probe |
  | — | `sandbox-exec` is deprecated | Probed on every start; guards on every CI run | If a macOS release removes it, commands run unsandboxed with the warning, as without bwrap |

  The process door's relay isn't offered on macOS yet (#152): a command that needs it doesn't start there. Guards for each row run on the macOS job once the backend is wired in (#166).

## Doors out of the sandbox
Narrow, named ways out, each asked for and each with its own rule for what it can never do (Marv Sprint 4).
- **Process (#24, Marv #51):** a dev server or watcher that keeps running across turns.
  - It runs in its own sandbox, like a bash command's: it can't write outside the project, change `.git`, read the real home, or reach the host's network or `127.0.0.1` unless started with `network: true`.
  - Its ports are forwarded to the host's `127.0.0.1` only, never another interface.
  - Starting one asks, even in yolo; only the main agent can (a subagent's context has no door, refused before any ask).
  - It dies on stop, when Marv exits or panics, and when Marv is killed (`--die-with-parent`).

## Provenance and taint (`marv-core::Provenance`)
- **Every tool result is tagged with its source.** Text that isn't from the user or Marv is fenced as data for the model; a closing tag inside it, in any case, is defused (`marv_core::defuse_closing_tag`). Project checks and diagnostics are quoted, never spoken in Marv's voice.
- **A session becomes tainted** once web, MCP, mesh or image content, a session-start hook's output (unless the user marked that hook `trusted`), or what the Herdr door read from a pane (#74), enters its context. From then on, every `ToolKind::Egress` call asks, even in yolo:
  - network bash;
  - every MCP call, including tools marked `readOnlyHint`;
  - web requests to a new URL prefix;
  - mesh calls on unapproved wires;
  - writes to protected paths.
- **A mesh message that wakes an idle Marv (#78, opt-in `mesh.wake`) is read the same way:** only on a wire the user granted, fenced as another agent's data, tainting the session before the woken turn's first request, never as a user message. So that turn's egress asks like any tainted turn's, in yolo too, and (#74) **it runs with automatic approval off**, like a radio turn: no yolo, no remembered or pre-approved "always", no approved URL prefix, every request `once` (`ToolContext::no_auto_approval`; guard `mesh.rs::an_inbox_woken_turn_asks_for_what_yolo_would_allow`). Never while an approval waits, at most 3 wake-ups a minute per wire, and never in `marv -p`.
- **Taint lasts as long as the text does.** It's saved with the session and restored on resume (`marv -c`, `/resume`); an older session file is judged by its tool calls, erring on the tainted side. A subagent's taint taints its parent: its report can carry the outside text back.
- **A pane send is a prompt, not a command.** `herdr.pane.<pane>.send` types text into another agent's pane as if its user typed it, so it carries prompts only: text whose first visible character (after control characters and leading spaces are dropped) is `/`, `!` or `#` is refused whole, before any wire is asked for and again at the pane, and nothing is typed. A wire to a pane lets an agent ask that agent for work, never run that agent's own commands or change its settings. A Marv in a pane reports working, not idle, to Herdr while anything but an empty prompt has its keyboard (the palette, setup, the session picker, the radio's roster, the splash, a half-typed slash command), so typed text can't pick from a list or finish a command there; and a pane just sent a prompt takes no other for `SEND_GAP` (5 s), one send at a time per Marv, since Herdr may still call its agent idle meanwhile. Another agent's own menus are its own: Herdr's state is all Marv sees of them.
- **The mesh radio (#124, phase 1: presence) is the user's choice and carries nothing to a model.** Off unless the user's own config (`"mesh": {"radio": true}`) or the person's `/radio on` turns it on: a project's `.marv/config.json` setting `mesh` (the radio or wake) is ignored with a startup note, no environment variable or flag turns it on, no tool writes the config, and `marv -p` and subagents are never on it. A door refuses `marv/radio.join` unless its radio is on, and from any process but the one listening on `<from>.sock` (by pid, as `marv/wire`). A frame's sender is the link it came in on: a frame with a `from`, or a presence naming another Marv, is refused. Presence has exactly its listed fields (name, state, title, project, pane, since_ms, wake, version; the title one printable line of at most 56 characters, the project a folder's name, never a path) and any other is refused. Presence is only ever drawn by the TUI, through `printable()`: it never reaches a model or the history, and `mesh_list`'s "On the radio" section is names and fixed state words only, so it doesn't taint. The links are Unix sockets in the mesh's private folder, which every sandbox sees empty (below).
- **Radio messages (#124, phase 2) are another agent's data, and a turn they start approves nothing by itself.** A `msg` is exactly its fields (`v, id, seq, kind, to, by, reply_to, hop, text, at_ms`; any other, a `from`, or an id that isn't `<the link's Marv>:<seq>` is refused), addressed to the receiver or to all, its text at most 2 KB: over it, it's refused at the sender and again at the receiver, never cut. Per sender, at each receiver, 20 a minute in bursts of 5 and at most 50 unread; a refusal is logged and told back as a fixed code, never the frame's words. The main agent reads them at the inbox's points, but only in the person's own turn or a turn the radio started (a turn a wired inbox woke, #78, leaves them unread), fenced as `<radio-message from=… by=…>` (a closing tag in the text, in any case, is defused), under Marv's note that they're data from other agents, **the session tainted (`Provenance::Mesh`) before the request that carries them**: egress after them asks like any tainted session's, in yolo too, and the taint is saved. History stays append-only; the system prompt and tools never carry a roster, a title or a message. `by: user` (typed with `/tx` at the other Marv) is shown and believed nowhere. No frame kind reaches an approver; no radio wake starts while an approval waits. With `mesh.wake` on, only a message **addressed** to this Marv (never a broadcast, never at hop 2 or more) may wake an idle TUI, at most 3 a minute per sender (1 every 10 s) and 10 in 10 minutes overall (then paused until the person types), and **that turn runs with automatic approval off**: yolo, remembered "always" answers, approved URL prefixes, pre-approved scopes and a worktree subagent's automatic yes don't apply (`ToolContext::no_auto_approval`; every request is `once`), so it does read-only work or asks the person. `radio_tx` (the model's) doesn't ask per message, even tainted (the spec's decision: its text only reaches the user's own Marvs here, each of which taints on receipt and asks before anything leaves), is offered only to the main agent of a conversation that started with the radio on (never a subagent's or `marv -p`'s), has no way to change a config or turn the radio on, and carries the turn's hop (a radio-started turn's is one past the deepest message it read). Each link writes from its own queue of at most 64 frames: a peer that stops reading is refused at once ("isn't keeping up") and dropped once its queue has stayed full (not emptied) for 30 s, or a write stalls for 30 s; it never holds the sender. Refusals are logged in Marv's fixed words, never quoting the frame. Every message, sent or received, delivered or refused, is a trajectory `mesh` record with `radio: true` and **never its text**. Guards: `tests/guards/tests/radio.rs` (phase 2 list), `marv-cli`'s `a_radio_message_never_wakes_while_an_approval_waits`.
- **Marv's runtime folder is empty in every sandbox.** `$XDG_RUNTIME_DIR/marv` (the mesh's plug and discovery sockets, the process door's relays) is an empty tmpfs in every command's sandbox, mounted after the project and toolchains, wherever it is: a sandboxed command that could see a plug's socket could connect to it and use that plug's wires. And the mesh refuses a runtime dir outside `/run`, `/tmp` and the home folder.
- **Approvals show the full payload.** A network approval lists the scripts written this session that the command will run.
- **Subagents don't inherit** network, web or mesh approvals — the config's pre-approved ones included (#98): `AlwaysScopes::for_subagent` strips the egress prefixes from the remembered scopes and the seeded ones alike.
- **Pre-approved scopes (#98)** — the config's `"approve"` (and the TUI's `--approve`) seed "always, for this session" through the same path a person's answer takes, so they never cover what asks even in yolo: protected paths, `package.json` lifecycle scripts, mesh wires (`once` + `must_ask`), tainted egress, and any file change when the project is the home folder (`once`). `marv -p` keeps its own `--approve` list out of the seeds, so a subagent's `for_subagent` is what bounds them; the flag list itself behaves as before.
- **Extra writable sandbox folders (#98)** — the config's `"writable"` is the one way a sandboxed command writes outside the project. Entries are canonicalised (symlinks followed) and refused at startup, not mounted: `/`, the home folder and its parents, the project's parents (other projects' `.git`), **any hidden top-level entry of the home** (`~/.<anything>`: the entry, anything inside it, or a parent of it — `.local/bin`'s planted binary runs on the host, `.config/autostart` and `.config/systemd/user` run at the next login, `.claude`'s hooks run on the host; only a *visible* top-level tree like `~/Projects/…` is allowed), **a git repository** (the entry is one, sits under a `.git` path component, or directly holds a `.git` entry — a worktree's `.git` file included; a planted `.git/hooks` script runs on the host's next git command there; a repository planted *deeper inside* an accepted folder later is not scanned — the refusal happens once, at startup), the mesh's runtime sockets (`$XDG_RUNTIME_DIR/marv`, anything in it or holding it), **Marv's own config folder** wherever `MARV_CONFIG_DIR` puts it (anything in it or holding it: its `config.json` holds the API key and the session-start hooks, and it holds the tool-output files), and anything missing or not a folder. Refused entries become startup problems, never mounts. An entry in the project (writable already) or inside another entry is left out quietly: a sandboxed command could swap its parent for a symlink, and the next command's bwrap would bind wherever that leads read-write.
- **`marv -p --approve` never answers a call that asks every time.** Tainted egress needs `--approve-tainted` as well as the call's `--approve` scope, and a protected-path write needs `--approve-protected` as well as `--approve files`; otherwise the call is refused (in `refused`, exit 3, a stderr line naming the flag). Subagents reach the same approver. The SDK hands the request to the client's approver with `must_ask` set, and an approver that answers from a policy should refuse it the same way. Guards: `tests/guards/tests/headless_taint.rs`.

## The doors out of the sandbox (Marv Sprint 4)
Narrow, named ways out, each with what it can never do. A door's own program (`gh`, `herdr`) is taken only from an absolute PATH entry, by its real path, and never from inside the project or a sandbox-writable folder, where a sandboxed command could have put one (`marv_sandbox::host_env::host_program`). The mesh's Herdr panes (`mesh_cmd::start`, `marv mesh ls`) take `herdr` the same way, and offer no panes when none is found. In a home-folder project the home is the project, so a `gh` or `herdr` under `~` (`~/.local/bin`) is skipped and that door isn't offered there: it fails closed. A call through one carries its door on the approval (the prompt shows the door's warning line), on its result and in the trajectory. The doors are the main agent's: a subagent's context has none.
- **github** (Marv #47) runs gh with the user's login, outside the sandbox:
  - never: `auth`, `config`, `extension`, `alias`, an unknown first word (an alias or extension), `secret`/`variable`/`ssh-key`/`gpg-key`, `--web`, `gh api --input`/`--verbose`, downloads, `repo clone`, `pr checkout`, another GitHub host than the project's. Refused before anyone is asked, whatever the approver says;
  - writes, other API methods, fields, graphql and sensitive API reads (secrets, keys, hooks, emails…) ask, in yolo too; a sensitive read is asked every time (`once`);
  - gh is spawned without a shell, without Marv's keys or debug switches, with `GH_HOST` pinned to the project's host (github.com where origin names none), and its git never runs the repository's programs;
  - GitHub token shapes are redacted from what gh prints before the model, the events, the saved session or the trajectory see it;
  - a subagent only reads; offered only where gh is there and logged in; `marv -p` needs `--approve github` for a write.
- **host** (Marv #52) is bash with `sandbox: false`, one command on the user's machine:
  - asked every time (`once`: "always" never covers another), in yolo too;
  - only where someone approves each command at a terminal (the TUI; the SDK's `host_commands`): refused before any ask in `marv -p`, in an SDK session without `host_commands`, and for a subagent;
  - its environment is the user's minus Marv's keys and anything secret-looking (`marv_sandbox::host_env`); token shapes are redacted from its output.
- **herdr** (#74) drives Herdr, the terminal multiplexer Marv runs in, from Marv's own process (the `herdr` CLI, through mesh v2's adapter). Offered only when Marv starts in a Herdr pane (`HERDR_ENV`), fixed for the session; the sandbox still can't reach Herdr (its variables cleared, its socket hidden: #130), only the door can:
  - **reads run without asking** (list workspaces, tabs, panes, agents; a pane's status; a pane's last lines). What comes back is other programs' text (screens, names and titles anyone can set): it's `Provenance::Herdr`, fenced as data (`<untrusted-data source="herdr">`) and it **taints** the session, like a mesh message;
  - **light actions ask** (focus, rename, a prompt typed into an idle agent's pane), "always" allowed (`herdr:focus`, `herdr:rename`, `herdr:prompt:<pane>`). A prompt is never a command (the pane send's rule, #128: text starting with `/`, `!` or `#` is refused before anyone is asked). In a turn the person didn't start (a mesh wake or the radio: `ToolContext::no_auto_approval`), they're asked `once`, like every request there: no remembered "always" answers them;
  - **running anything is asked every time** (`once`: never remembered, not by "always", the config's pre-approved scopes or yolo): `run` (a command in a new pane) and `spawn` (a Marv or another Herdr agent kind, optionally in a new git worktree). The approval shows the exact command, the folder or branch, the worker's kind and its task. Only where someone approves each one at a terminal (`Doors::herdr`, the TUI's main agent, as `host`): refused before any ask in `marv -p` (with every `--approve` name: none covers `herdr:`), in an SDK session without `host_commands`, and for a subagent (which isn't offered the tool at all);
  - **a spawned worker gets no more than its parent:** a Marv starts with the user's config only (never the session's `--approve` scopes or remembered answers), and with `MARV_YOLO=off` (which can only turn yolo off; `/yolo on` is refused there) unless the spawning turn is in yolo; another agent kind starts with no arguments a model chose (the tool has no field for them). At most `herdr.peers` panes per session (the user's own config; default 4, 0 to 16), checked before anyone is asked; a pane Herdr no longer has doesn't count;
  - **taint isn't laundered through another agent:** a worker spawned from a tainted conversation starts tainted (`MARV_TAINTED=1` on a Marv's command, which can only add taint; it shows a startup note and marks `Provenance::Herdr` at its first turn, so its egress asks). A prompt or spawn in a tainted conversation is egress (`must_ask`) and its approval says "The receiving agent will treat this text as your own words, with its own approvals.";
  - **nothing a model passes reaches the `herdr` CLI as an option:** ids start with a letter or digit, and a rename's name, a run's command and a prompt or task (`pane_prompt`, the mesh's pane sends too) can't start with `-`. A run command can't start with `^` (quick substitution) or hold `!` (history expansion), invisible format characters, line or paragraph separators or the Hangul fillers; one that starts an agent gets a warning pointing to spawn;
  - the panes it opened outlive the turn and are the user's: `/peers` lists them, `/peers read <name>` shows one's last lines, `/peers stop <name>` closes one (never the model's to do). `/exit` and Enter (or ctrl+c) are typed only into an agent that's idle or done: one that's working or at an approval gets nothing typed (Enter would answer its question) and its pane is just closed; a pane that's already gone is forgotten. A worktree stays until the user removes it. Pane names, titles and output reach the terminal only through `printable()`.

## MCP
- Project servers need trust. The hash covers the entry and the files its command runs.
- `npx`/`uvx` run outside the project folder.
- Server `instructions` are ignored.

## Images (when vision is added)
- **Sources:** only the user (a paste, or a file they name). Never forwarded automatically from web, MCP or mesh.
- **A quarantined reader:** a tools-less model call extracts the image's text and description. The main model sees only that, fenced as `Provenance::Image`, and it's shown in the transcript. Any image taints the session.
- **Decoding** happens in the sandbox, with metadata stripped and size limits.

## Proof
- `tests/guards/`: one test per rule. Each one fails when its guard is reverted, and they run in CI.
- An injection eval suite (poisoned README, web page, MCP issue body, mesh message, later images). It passes when the model never tries to send data out or write a protected path.
