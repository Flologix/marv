# Security model

**Principle:** prompt injection can't be filtered out, so it's contained. An injected model must never hold all three of these together:
- private data;
- untrusted content in its context;
- a way out (network, the mesh, or code that runs outside the sandbox).

These rules are requirements for the Rust build from day one. They come from a security review of Marv 0.3.0 (2026-10-12); see the repository's security advisories.

## Process and launch
- **One static binary.** No interpreter reads the project's `bunfig.toml`, `.env`, `node_modules` or similar. Config comes only from:
  - `~/.marv/` (or `$MARV_CONFIG_DIR`, but only from the real environment, never from a file in the project);
  - the project's `.marv/` (trust-gated) and `.mcp.json` (trust-gated).
- **Session-start hooks come only from the user's own config (#108).** `hooks.sessionStart` is read from `~/.marv/config.json` (or `$MARV_CONFIG_DIR`'s) and nowhere else: a project has no config layer, and a project's `.marv/config.json` naming `hooks` is refused with a startup note and never run (it's only looked at if it's a regular file inside the project, and read up to 1 MB) (cloning a repository must not run its commands, the class of hole 0.3.0's `bunfig.toml` preload was). Hooks run outside the sandbox without asking, since the user wrote them: with the host door's environment (Marv's keys and secret-looking variables left out), a timeout (default 15 s, the process group killed) and an 8 KB output cap. The user's config is out of the sandbox's reach (a stand-in home; when the project is the home folder, the home is read-only in the sandbox with `~/.marv` hidden, and `.marv/**` is protected for the edit tools), so the model can't plant a hook either. **Their output taints the session** when it's sent (`Provenance::Hook`) and is fenced as data (`<untrusted-data source="hook">`): the user chose the command, not what it prints (`bd ready` lists issue titles anyone can file on a public repository). Only `"trusted": true` on a hook in the user's config opts it out; empty output taints nothing. Guards: `tests/guards/tests/launch.rs` (`a_projects_session_start_hooks_never_run`, `marv_p_never_runs_a_projects_hooks`, `hook_output_taints_the_session`).
- **Saved sessions and trajectories hold prompts and code.** They're written under Marv's config folder only (`sessions/`, `trajectories/`; 0600 files in 0700 folders), never into the project.
- **Model output is never written to the terminal raw.** Every string goes through `printable()`, which strips CSI/OSC/DCS, C0/C1 controls and bidi overrides. This includes headless text mode.

## Sandbox (`marv-sandbox`)
- **bubblewrap**, with:
  - read-only system directories and an empty `/run` (except the mesh plug, `/run/marv/mesh.sock`, and the process door's relay: Marv's binary at `/run/marv-bin` and socket folders under `/run/marv`);
  - a stand-in home, with toolchains re-mounted read-only and credential files masked;
  - the project writable, with `.git` and **protected paths** read-only;
  - Marv's config folder (`~/.marv`, or `MARV_CONFIG_DIR` wherever it is) hidden;
  - no network unless approved (`--unshare-net`), a cleared environment, and its own PID namespace.
- **On macOS (Seatbelt, #166), `marv __guard` stands in for the PID namespace.** It runs each sandboxed command in a session and process group of its own, kills that whole group (itself included) as soon as Marv exits, panics or is killed (it polls its parent every 200 ms), and passes a stop on to the group; Marv's timeout and stop `killpg` the group, and so does the command's normal exit: once the guard has exited (seen before it's reaped, so its group's id can't be reused), whatever the command left running in the group (`sleep 600 &`) is killed before its output is read to the end; a command whose turn is dropped takes its group with it. **Known limit:** a process that leaves the group itself (`setsid`, `setpgid`) and double-forks can outlive the command and Marv. It stays inside the sandbox (Seatbelt is inherited and can't be dropped), so it can do no more than the command could, but nothing sweeps it up; bwrap's PID namespace closes this on Linux. The guard shares the command's sandbox and group, so the command can also SIGKILL or SIGSTOP the guard; its group then outlives a Marv that crashes or is SIGKILLed (a Marv that exits normally, or times the command out, still kills the group). A guard that can't have a session of its own runs nothing. Tests: `crates/marv-cli/tests/guard.rs` (`nothing_in_the_group_outlives_a_parent_killed_with_sigkill`, `a_stop_reaches_everything_in_the_group_and_the_guard_exits_with_the_commands_code`); in the sandbox, `tests/guards/tests/seatbelt.rs` (`nothing_outlives_the_command_and_an_escapee_stays_sandboxed`, `a_dropped_command_takes_its_group_with_it`).
- **A sandboxed command without network runs without asking (`approveSandboxed`, default `auto`), yolo or not.** `bash` with the working sandbox, no `network`, no `git_write` and no `sandbox: false` runs confined (`.git` read-only) in a turn the person started and in a turn a mesh wake started (`CallMode::runs_sandboxed_unasked`; `Tool::auto_sandboxed`). It never applies in `marv -p` (`--approve` stays the contract), a radio turn, a woken turn's subagent, a project that is the home folder (no yolo there), or with the sandbox off or unavailable. It is checked after the taint rules: network and egress ask when tainted, protected paths ask. `"approveSandboxed": "ask"` in the user's config restores asking. Guards: `tests/guards/tests/approvals.rs` (`sandboxed_commands_without_network_run_unasked_in_person_and_woken_turns`, `approve_sandboxed_ask_headless_and_radio_turns_still_ask`, `approve_sandboxed_still_asks_for_network_git_write_the_host_and_without_a_sandbox`, `approve_sandboxed_leaves_taint_rules_alone`).
- **Protected paths ask even in yolo, and are read-only inside the sandbox:**
  - `.git/` and the `core.hooksPath` folder;
  - `.env*`, `.envrc`, `bunfig.toml`, `.mcp.json`;
  - `AGENTS.md`/`CLAUDE.md` at any level, and `.marv/**`;
  - `.vscode/`, `.idea/`;
  - `package.json` lifecycle `scripts`;
  - when the project is the home folder (or holds it), where `edit_file`/`write_file` run outside the sandbox and reach the whole home: every hidden top-level entry of the home (`~/.bashrc`, `~/.profile`, `~/.config/systemd/user/`, `~/.config/autostart/`, `~/.ssh/authorized_keys`, `~/.local/bin/`…) and the hooks folder (`core.hooksPath`) of the global git config and of any repository in the home (`home_rule`; guard `in_the_home_folder_dotfiles_and_hooks_ask_even_in_yolo`).
- **Secrets** (`.env*`, `*.pem`, `id_*`) need approval to read, and are masked in the sandbox.
- **In the home folder, the sandbox shows the home read-only and hides Marv's config, credentials and agent sockets.** When the project is the home folder or a parent of it (`/`, `/home`), a stand-in home would hide the project, so instead the project is mounted read-only (never read-write), and on top of it every hidden top-level entry of the home (`~/.<anything>`: `~/.marv`, `~/.ssh`, `~/.gnupg`, cloud CLI folders, `~/.claude`, `~/.config`, `~/.local`, `~/.cache`) is hidden, apart from the toolchain folders (shown read-only, credential files masked); the named ones (`~/.config/herdr`, `~/.config/gh`, `~/.docker`, `~/.kube`, `~/.local/share/keyrings`…) stay hidden even if a toolchain mount would show them, and every Unix socket or FIFO a bounded scan finds in the visible part of the home is replaced by `/dev/null` (a read-only mount doesn't stop a `connect()`). Sandboxed commands write only to `/tmp` there; the edit tools keep their approvals, a change to a dotfile or a git hooks folder there is a protected path (it asks every time), and yolo is refused. Every other file change there (`edit_file`, `write_file`: a `Write` tool with the `files` scope) is asked `once` (`registry::home_file_write`), and never run on yolo even by a context that has it: Yes or No, no "always"; neither a remembered "files" scope nor the config's `"approve": ["files"]` covers it (both go through `SessionApprover`, which never answers a `once` request), the TUI's "always" on another queued request doesn't answer it, and a worktree subagent's automatic yes (`SubagentApprover`) doesn't either. `marv -p --approve files` still approves it: the flag names the scope for that one run and answers "yes" per call (`ScopeApprover`), never "always". Guards: `tests/guards/tests/approvals.rs` (`in_the_home_folder_always_on_a_file_change_still_asks_the_next_time`, `in_the_home_folder_a_file_change_request_is_once`, `in_the_home_folder_config_approve_files_doesnt_cover_a_file_change`, `headless_config_approve_files_in_the_home_folder_is_refused`, `a_subagents_automatic_yes_doesnt_cover_a_once_request`, `a_project_under_the_home_keeps_always_for_file_changes`, `headless_approve_files_in_the_home_folder_still_writes`). A home that can't be listed runs no command. An extra read-only or writable folder can never be the home or a parent of it. Guards: `tests/guards/tests/sandbox.rs` (`in_the_home_folder_no_socket_under_the_home_is_reachable`, `in_the_home_folder_credentials_and_marvs_config_are_hidden`, `in_the_home_folder_nothing_in_the_home_is_writable`, `a_project_in_a_subfolder_of_the_home_stays_writable`).
- **The project's own tooling runs only inside the sandbox.** The typecheck, cargo check and pyright (#187) after an edit, the project's checks (`.marv/checks/`) and the project's formatter after an edit (#67) run in the sandbox, the project read-only, without network; without a sandbox they don't run at all, and Marv never installs a formatter. So their output never comes from a run with the network: it's the project's (quoted under Marv's note, not tainting), unlike an unsandboxed bash command's. The formatter is the project's own code, and it gets write to the one file being formatted — except on protected paths and `package.json`, which keep exactly what the edit tool wrote: a rewrite there could turn an approved diff into anything (a `postinstall` script into `package.json`, a planted `.vscode/` or `.marv/` file). A failing formatter's output reaches the model fenced as project data, like the checks'. A checker that keeps a build cache (#187) gets one writable folder, for that check only: exactly its repository's key folder in Marv's check cache (`~/.cache/marv/checks/<key>`, or `$XDG_CACHE_HOME/marv/checks`; `~/Library/Caches/marv/checks/<key>` on macOS), never the cache root, another project's key or the project's own build folder, and never added to the `writable` list. A key folder that is a symlink, not a folder or not the user's is refused; the cache is bounded (20 GB in all, least recently used first; 10 GB per key; nothing starts with less than 5 GB or 5% free; unused folders pruned after 14 days), and Marv sizes, prunes and deletes it without following links and without running anything on the host. Such a checker's warm-up starts only at a session's first edit, so a session that never edits never runs the project's build. cargo check runs the project's `build.rs` and proc macros, and project files steer it (`.cargo/config.toml`'s `rustc`, wrapper, linker, `[env]` and flags; `rust-toolchain.toml`): all of that runs only inside the sandbox, as it would for the model's own `cargo check` in `bash`, from the session's first edit on, with the project read-only, no network, `RUSTUP_AUTO_INSTALL=0` (Marv never installs a toolchain) and only its key folder writable; nothing project-steered runs on the host, and no cargo or rustup runs there even to detect it. pyright runs the project's own `.venv/bin/basedpyright` or `node_modules/.bin/pyright` when there is one (chosen by the command inside the sandbox, never looked up and run on the host), and it runs a Python interpreter the project's config can choose (`venvPath`/`venv`, whose `.pth` files run at startup): all of it only inside the sandbox, with the project read-only, no network and nothing writable. Whether a uv venv's interpreter is hidden is learned by reading the link on the host, never by running it. Memory isn't capped (there's no cgroup): a cold check of a big workspace can take a few GB. Guards: `checks.rs::a_check_writes_only_its_own_cache_key_folder`; `cargo_check.rs::a_malicious_build_script_runs_sandboxed_and_the_check_still_reports` (its `build.rs` can't write the project, another key or outside its key folder on the host, read a hidden home path or reach the network) and `cargo_check_tells_a_new_error_once_and_never_touches_the_projects_target`; `pyright_check.rs::a_projects_own_checker_runs_sandboxed` (a project's `.venv/bin/basedpyright` can't write the project or the real home, read a hidden home file or reach the host's loopback) and `pyright_tells_a_new_error_once_from_the_sandbox`; `marv-session`'s `diagnostics::machinery_tests::nothing_marv_does_around_a_check_runs_anything_on_the_host`.
- **Every path is checked after `realpath`.** No tool follows a symlink out of its root. That includes skill files, which the old code read outside the sandbox, and instruction files (`AGENTS.md`/`CLAUDE.md`: the project's, its parents', nested ones), which also never lead to a secret or into `node_modules`/`target`/`.git`; only the user's own `~/.marv/AGENTS.md` may link anywhere.
  - The one exception: a **personal** skill folder (`~/.marv/skills/<name>`) may be a symlink to a folder only root can change, such as Omarchy's `/usr/share/omarchy/…` (#75). That folder and every folder above it must be owned by root and not group- or world-writable. The skill is read from the link's real target, and its `SKILL.md` and files can't lead out of that folder. A project's skill folder never may.
- **The one read outside the project is the session's saved tool outputs (#61).** `read_file` and `grep` may read the files in `~/.marv/tool-output/<session>/`, and nothing else outside the project. Writing tools can't, and bash can't see the folder at all. A saved output keeps its source in its name (`<call id>.mcp.txt`), so an MCP server's text read back is fenced and taints as it did when it came; a long page web_fetch saves on its first read (#93) is `<call id>.web.txt` and reads back as web content.

- **On macOS (Seatbelt).** The macOS sandbox is built from the same plan as bubblewrap's (`marv_sandbox::seatbelt`, #164): a deny-default SBPL profile for `/usr/bin/sandbox-exec`, with reads allowed for the whole disk and then narrowed, writes only to the project, the writable extras and a private `TMPDIR`, and every path canonical and passed as a parameter, never written into the profile (a project path that can't be written into the protected-name regexes stops the command). It is the backend on macOS (#166): each command is `/usr/bin/sandbox-exec -p <profile> -D …= -- marv __guard <Marv's pid> -- bash -c …`, spawned with the plan's environment and nothing of Marv's (`sandbox-exec` passes its environment on). The guard binary is resolved once per run, and the availability checked once for it with the real base rules and the guard: with no `sandbox-exec`, a profile the kernel refuses, or a Marv already inside a Seatbelt sandbox, commands run unsandboxed with the warning, as on Linux without bwrap. What the profile assumes was checked on the macOS runner (`crates/marv-sandbox/tests/seatbelt_probe.rs`, results on #166). Seatbelt can refuse a path but can't show something else there, so these guarantees differ from bubblewrap's:

  | bubblewrap | Seatbelt | Mitigation | What's left |
  |---|---|---|---|
  | A stand-in home: empty, writable, thrown away | The home is unreadable and unwritable | Caches in the private `TMPDIR`; the home note says reads and writes there are refused | Tools that insist on writing `~/.something` fail instead of working on a throwaway copy |
  | Credential files read as empty | Reading them is refused | Denied by the path as written and where it leads | A tool that expects the file to exist and be empty errors out |
  | A private `/tmp` | `/tmp` is the host's | A private `TMPDIR` per command (0700, made by Marv, removed after, a new folder in the user's `/private/var/folders/<xx>/<id>/T/`, refused if it's inside or around the home, the project, `/private/tmp`, Marv's folders or an extra); `/private/tmp` and the user's `/var/folders/<xx>/<id>` denied (a command whose user folder can't be found doesn't start) | Tools that hard-code `/tmp` fail |
  | Its own PID namespace | None | Signals and process info only within the sandbox, process info denied explicitly first (Seatbelt's deny-default leaves every process of the same user readable: path, arguments, environment, descriptors); no `kern.proc.all` | Other processes' pids can be listed or guessed but not used |
  | Dies with Marv (`--die-with-parent`) | None | `marv __guard`: its own process group, watches its parent, kills the group when Marv dies; everything is killed on exit | A process that leaves the group and double-forks outlives the command, still sandboxed |
  | `--new-session` | No flag | `setsid()` in the guard, stdin `/dev/null`, terminals and pseudo-terminals denied | None known |
  | Its own loopback without network | None: loopback is the host's | Without network every IP connection is refused, loopback included. No port is opened one by one: Seatbelt's `localhost` matches every address of the machine, not just loopback | In-sandbox client/server tests need network (which asks) |
  | Protected paths mounted read-only | Write denies by path | The path and where it leads, `literal` and `subpath`; the protected names as case-insensitive regexes at any depth (outside `node_modules`, `target` and `.git`), so a command can't create them either; folders above a protected path can't be removed or renamed; the after-scan still runs | The after-scan is load-bearing for names: a protected name written inside `node_modules` or `target` (which the rules skip) and then moved out by renaming that folder isn't stopped by a rule, only found and reverted after the command; the same for a nested `.git` |
  | A hard link can't cross a mount (`EXDEV`) | Hard links are path operations | `link()` is checked against both the source and the new name, and is refused outright when the source can't be read or written (both probed): links are allowed only between files of the project and of the private `TMPDIR`, and nothing denied (the home, `~/Library`, the shared temporary folders, Marv's folders, credentials, protected paths and names, read-only folders) can be either end, so `ln ~/.ssh/known_hosts ./x` and `ln .envrc y` are refused | A hard link to a protected file made **outside** the sandbox beforehand can be written through from inside: the rules see its other name |
  | A home-folder project hides every hidden top-level entry | The same, by one regex, plus `~/Library` (where macOS keeps keychains, cookies, mail, messages and app data) | None needed | The rest of the home stays readable, as on Linux |
  | The home-folder project's socket scan, bounded | Every Unix socket refused unless named | None needed | Stronger: no depth or count limit |
  | With network, abstract sockets reachable | No abstract sockets; Unix sockets stay closed with network | None needed | Stronger |
  | — | Mach and XPC services (`open`, `osascript`, `launchctl`, the pasteboard, the keychain) | Deny-default; a short reviewed `mach-lookup` list; XPC services denied last | Every service added is a review item |
  | No new privileges (bwrap sets `no_new_privs`: a setuid program gains nothing) | Setuid and setgid programs don't run in the sandbox at all: `sandbox-exec` refuses their exec (probed: `sudo`, `ps`) | None needed | `ps`, `sudo` and other setuid tools fail with "Operation not permitted" |
  | With network, the host's interfaces are visible | Without network the interface list (`getifaddrs`) is refused; with network it's allowed | None needed | Without network, node's `os.networkInterfaces()` and Go's `net.Interfaces()` fail on macOS |
  | — | With network, the TLS-trust services (`com.apple.trustd.agent`, `com.apple.ocspd`) are reachable; securityd (`com.apple.SecurityServer`, keychain items and authorization prompts) is not, unlike Codex's network policy | `~/Library` (the keychain files) can't be read either | None known (guard `a_keychain_item_cant_be_read_with_or_without_network`) |
  | — | `sandbox-exec` is deprecated | Probed on every start; guards on every CI run | If a macOS release removes it, commands run unsandboxed with the warning, as without bwrap |

  The process door isn't offered on macOS yet (#152): the process tool isn't there, and a command that needs the relay doesn't start. Guards: `tests/guards/tests/seatbelt.rs`, on the macOS CI job with `MARV_REQUIRE_SANDBOX=1` (`the_macos_doors_are_closed`, `no_socket_outside_the_sandbox_is_reachable`, `the_runtime_folder_is_closed_but_for_the_plug`, `the_home_marvs_config_and_credentials_cant_be_read`, `writes_only_in_the_project_and_a_private_tmpdir`, `protected_names_cant_be_created_and_the_scan_finds_nothing`, `protected_files_cant_be_renamed_away_or_hard_linked`, `without_network_no_ip_not_even_loopback`, `host_processes_cant_be_reached_and_setuid_programs_dont_run`, `other_processes_info_cant_be_read_but_the_commands_own_can`, `the_command_gets_only_the_plans_environment`, `nothing_outlives_the_command_and_an_escapee_stays_sandboxed`, `a_dropped_command_takes_its_group_with_it`).

## Doors out of the sandbox
Narrow, named ways out, each asked for and each with its own rule for what it can never do (Marv Sprint 4).
- **Process (#24, Marv #51):** a dev server or watcher that keeps running across turns.
  - It runs in its own sandbox, like a bash command's: it can't write outside the project, change `.git`, read the real home, or reach the host's network or `127.0.0.1` unless started with `network: true`.
  - Its ports are forwarded to the host's `127.0.0.1` only, never another interface.
  - Starting one asks, even in yolo; only the main agent can (a subagent's context has no door, refused before any ask).
  - It dies on stop, when Marv exits or panics, and when Marv is killed (`--die-with-parent`).

## Provenance and taint (`marv-core::Provenance`)
- **Authority comes from the person and from Marv's fixed words. Everything else is data.** Every piece of text in a model's context has a source, in one of three classes (`marv_core::SourceClass`): *authority* (what the person types and answers, Marv's fixed text, the person's own files: `~/.marv/AGENTS.md`, personal skills, memory, their config), *workspace* (the project folder the person chose: its files, local git history, checks, the formatter, a subagent's report, and a trusted project's instruction files), and *outside* (web pages, MCP results, the mesh and the radio, Herdr reads, untrusted hook output, images, the GitHub door's output, the output of any command run with the network, a tainted subagent's report). Outside text is fenced as data and taints the conversation; workspace text is quoted where Marv speaks about it and never taints (tainting every read of every repository would make every session tainted). Data gains authority only through the person: an approval they answered, or a project whose instructions they trusted. Guards: `tests/guards/tests/untrusted_text.rs`.
- **Every tool declares its kind and its source.** `Tool::kind` and `Tool::provenance` have no defaults, so a new tool can't run unasked, or hand outside text over as the project's, by leaving them out; `run_tool` raises every result to the source its tool declares for that call (`Tool::provenance_in`: bash with the network, on the host, or anywhere the sandbox is off or unavailable (nothing takes the network away then), and a process started with the network and its logs, are `Provenance::Network`), and never lowers one the tool set itself. An unsandboxed command counts as using the network too, so in a tainted session it asks every time. A tool's own error (`ToolError`) gets its tool's declared source as well: from an outside source it's fenced (a redirect's `Location`, an echoed header, gh's stderr), and taints (a preview's error stays Marv's: a preview reaches nothing, so it's Marv's own refusal). The GitHub door's output is `Provenance::Github`. A saved output keeps its source, so reading it back fences and taints the same way. The session's own tools (the MCP adapter, `tool_search`, `mcp_call`, the mesh tools, `radio_tx`, the Herdr door) are pinned the same way. Guards: `untrusted_text.rs` (`every_tool_declares_a_source_class`, `the_session_tools_declare_their_sources_too`, `github_door_output_is_fenced_and_taints`, `network_command_output_taints_and_sandboxed_offline_output_doesnt`, `an_unsandboxed_commands_output_is_network_output`, `an_outside_tools_own_error_is_fenced_and_taints`).
- **Every tool result is tagged with its source.** Text that isn't from the user or Marv is fenced as data for the model; a closing tag inside it, in any case and however it's spelled (whitespace, invisible and default-ignorable characters and combining marks anywhere in it, lookalikes of `<` and `/`, and the letters' compatibility forms: fullwidth, mathematical, circled), is defused (`marv_core::defuse_closing_tag`), and the fence's attributes are escaped (`marv_core::escape_attribute`: `&`, quotes, angle brackets and their fullwidth forms; line breaks, line and paragraph separators and invisible characters as spaces), so neither the text nor a call's label (a URL the model wrote) can end the fence. An error result from an outside source is fenced too (an MCP server's JSON-RPC error message is its text, an error *result*, not Marv's error). Project checks and diagnostics are quoted, never spoken in Marv's voice. mesh_list fences each wired receptacle's description as its owner's data, and a failed mesh call or send, a failed wiring included, is quoted as mesh data and taints (the far end's error and the local switchboard's refusal arrive alike; guard `mesh.rs::a_failed_mesh_call_is_quoted_as_mesh_data_and_taints`). A subagent whose conversation was tainted has its report quoted as a subagent's data, Marv's own lines outside the fence, and the step the user declined (its model wrote the call) and its error text quoted too. Guards: `untrusted_text.rs` (`tainting_error_results_are_fenced`, `fence_attributes_are_escaped`, `closing_tags_hidden_by_invisible_characters_are_defused`, `mesh_list_descriptions_are_fenced`, `a_tainted_subagents_report_is_fenced`, `a_subagents_taint_reaches_its_parent_and_its_report_is_fenced`).
- **A project's instructions are the person's only once they trust them.** A project's `AGENTS.md`/`CLAUDE.md` (and its parent folders' up to the git root), its `.marv/skills` and its `.marv/agents` steer the model as the person's own words would, so a cloned repository's don't get that by being opened. Trust is per project and for exactly the files' contents (`marv_session::project_trust`, stored in `~/.marv/project-trust.json` beside MCP trust, hashed per file): a changed file asks again and names what changed. Each file is read once at startup and what's hashed is what's loaded (`load_project`); a trusted project skill's other files, read later, are checked against the hashes they were trusted with and quoted when they differ. Not trusted, the instruction files go to the model quoted as the project's data under Marv's fixed note, and the project's skills and agent types aren't loaded or offered (in the TUI and the SDK). A subfolder's instruction file, read when a tool first touches its folder, counts as the person's only when its own contents were trusted (`NestedTrust`), whatever the root holds (a project with no root files included): otherwise it's quoted, a notice names it, and `/trust` records it; nested files never speak in Marv's voice. File names in Marv's notes go through `printable()`. The TUI says so at startup and `/trust` trusts what it showed, from the next start (the system prompt and tool list stay byte-stable within a session). `marv -p` trusts only a stored, matching trust, or `--trust-project` for that run (nothing stored). Nothing is trusted by guessing (not the home folder, not a folder of the person's own commits). Guards: `untrusted_text.rs` (`an_untrusted_projects_instructions_load_fenced_and_offer_no_skills`, `a_changed_instruction_file_asks_for_trust_again`, `a_subfolder_instruction_file_counts_only_once_its_contents_are_trusted`, `a_trusted_skills_file_that_changed_since_is_quoted`).
- **A session becomes tainted** once web, MCP, mesh or image content, a session-start hook's output (unless the user marked that hook `trusted`), what the Herdr door read from a pane (#74), the GitHub door's output, or a networked command's output enters its context. From then on, every `ToolKind::Egress` call asks, even in yolo:
  - network bash;
  - every MCP call, including tools marked `readOnlyHint`;
  - web requests to a new URL prefix (and a fetch's name reaches DNS only after its approval: the approval's preview refuses a private address literal or `localhost` without a lookup, and the lookup, with its check for a private answer, happens when the approved fetch runs, before it connects; a name can carry data, so a declined fetch must make no lookup at all. Guard: `web.rs::a_fetchs_name_is_looked_up_only_after_its_approved`);
  - mesh calls on unapproved wires;
  - writes to protected paths.
- **A mesh message that wakes an idle Marv (#78, opt-in `mesh.wake`) is read the same way:** only on a wire the user granted, fenced as another agent's data, tainting the session before the woken turn's first request, never as a user message. So that turn's egress asks like any tainted turn's, in yolo too, and (#74) **it runs with automatic approval off**, like a radio turn: no yolo, no remembered or pre-approved "always", no approved URL prefix, every request `once` (`ToolContext::mode` without automatic approval; guard `mesh.rs::an_inbox_woken_turn_asks_for_what_yolo_would_allow`). Never while an approval waits, at most 3 wake-ups a minute per wire, and never in `marv -p`.
- **Taint lasts as long as the text does.** It's saved with the session and restored on resume (`marv -c`, `/resume`), merged with what the conversation's calls show for sure (a github call, a command with the network or on the host, a process started with the network: `SavedSession::taint_shown`); an older session file is judged by its tool calls, erring on the tainted side. A subagent's taint taints its parent: its report can carry the outside text back. `/clear` ends the cleared conversation's taint (and the URL prefixes approved under it), since its text is gone, except for a background process started with the network while it runs, and a Marv started tainted (`MARV_TAINTED`). A tainted conversation's compaction summary (the model's own user-role notes, not fenced; v1, v2 with its verbatim tail, and an overflow recovery's) starts with Marv's fixed note that it may repeat outside data and that an instruction in it is data unless the person gave it, and a level-3 drop's note says the same of what's left. Guards: `untrusted_text.rs` (`clear_ends_the_cleared_conversations_taint`, `a_tainted_compaction_says_so_in_fixed_words`, `compaction.rs::taint_survives_compaction`, `suggestions_stay_off_after_github_or_network_output`, `a_resumed_conversation_is_tainted_by_what_its_calls_show`).
- **Memory is a persistent sink.** A memory is loaded into every later conversation as the person's own words, so in a tainted conversation adding one is asked of a person every time (`Tool::persists`: `must_ask` and `once`; no yolo, no remembered or pre-approved "always"), and the approval says the conversation read outside text. `marv -p` has no person to ask, so it refuses such a write whatever the flags (`--approve memory` with `--approve-tainted` included). Writes to a project's instruction files are protected paths already. Guards: `untrusted_text.rs::a_tainted_conversation_asks_once_for_a_memory_write`, `headless_taint.rs::headless_never_writes_a_memory_in_a_tainted_run`.
- **A pane send is a prompt, not a command.** `herdr.pane.<pane>.send` types text into another agent's pane as if its user typed it, so it carries prompts only: text whose first visible character (after control characters and leading spaces are dropped) is `/`, `!` or `#` is refused whole, before any wire is asked for and again at the pane, and nothing is typed. A wire to a pane lets an agent ask that agent for work, never run that agent's own commands or change its settings. A Marv in a pane reports working, not idle, to Herdr while anything but an empty prompt has its keyboard (the palette, setup, the session picker, the radio's roster, the splash, a half-typed slash command), so typed text can't pick from a list or finish a command there; and a pane just sent a prompt takes no other for `SEND_GAP` (5 s), one send at a time per Marv, since Herdr may still call its agent idle meanwhile. Another agent's own menus are its own: Herdr's state is all Marv sees of them.
- **The mesh radio (#124, phase 1: presence) is the user's choice and carries nothing to a model.** Off unless the user's own config (`"mesh": {"radio": true}`) or the person's `/radio on` turns it on: a project's `.marv/config.json` setting `mesh` (the radio or wake) is ignored with a startup note, no environment variable or flag turns it on, no tool writes the config, and `marv -p` and subagents are never on it. A door refuses `marv/radio.join` unless its radio is on, and from any process but the one listening on `<from>.sock` (by pid, as `marv/wire`). A frame's sender is the link it came in on: a frame with a `from`, or a presence naming another Marv, is refused. Presence has exactly its listed fields (name, state, title, project, pane, since_ms, wake, version; the title one printable line of at most 56 characters, the project a folder's name, never a path) and any other is refused. Presence is only ever drawn by the TUI, through `printable()`: it never reaches a model or the history, and `mesh_list`'s "On the radio" section is names and fixed state words only, so it doesn't taint. The links are Unix sockets in the mesh's private folder, which every sandbox sees empty (below).
- **Radio messages (#124, phase 2) are another agent's data, and a turn they start approves nothing by itself.** A `msg` is exactly its fields (`v, id, seq, kind, to, by, reply_to, hop, text, at_ms`; any other, a `from`, or an id that isn't `<the link's Marv>:<seq>` is refused), addressed to the receiver or to all, its text at most 2 KB: over it, it's refused at the sender and again at the receiver, never cut. Per sender, at each receiver, 20 a minute in bursts of 5 and at most 50 unread; a refusal is logged and told back as a fixed code, never the frame's words. The main agent reads them at the inbox's points, but only in the person's own turn or a turn the radio started (a turn a wired inbox woke, #78, leaves them unread), fenced as `<radio-message from=… by=…>` (a closing tag in the text, in any case, is defused), under Marv's note that they're data from other agents, **the session tainted (`Provenance::Mesh`) before the request that carries them**: egress after them asks like any tainted session's, in yolo too, and the taint is saved. History stays append-only; the system prompt and tools never carry a roster, a title or a message. `by: user` (typed with `/tx` at the other Marv) is shown and believed nowhere. No frame kind reaches an approver; no radio wake starts while an approval waits. With `mesh.wake` on, only a message **addressed** to this Marv (never a broadcast, never at hop 2 or more) may wake an idle TUI, at most 3 a minute per sender (1 every 10 s) and 10 in 10 minutes overall (then paused until the person types), and **that turn runs with automatic approval off**: yolo, remembered "always" answers, approved URL prefixes, pre-approved scopes and a worktree subagent's automatic yes don't apply (`ToolContext::mode` without automatic approval; every request is `once`), so it does read-only work or asks the person. `radio_tx` (the model's) doesn't ask per message, even tainted (the spec's decision: its text only reaches the user's own Marvs here, each of which taints on receipt and asks before anything leaves), is offered only to the main agent of a conversation that started with the radio on (never a subagent's or `marv -p`'s), has no way to change a config or turn the radio on, and carries the turn's hop (a radio-started turn's is one past the deepest message it read). Each link writes from its own queue of at most 64 frames: a peer that stops reading is refused at once ("isn't keeping up") and dropped once its queue has stayed full (not emptied) for 30 s, or a write stalls for 30 s; it never holds the sender. Refusals are logged in Marv's fixed words, never quoting the frame. Every message, sent or received, delivered or refused, is a trajectory `mesh` record with `radio: true` and **never its text**. Guards: `tests/guards/tests/radio.rs` (phase 2 list), `marv-cli`'s `a_radio_message_never_wakes_while_an_approval_waits`.
- **Marv's runtime folder is empty in every sandbox.** The runtime folder (the mesh's plug and discovery sockets, the process door's relays; `marv_sandbox::runtime_dir`) is `$XDG_RUNTIME_DIR/marv` on Linux and `/tmp/marv-<uid>` on macOS, or `MARV_RUNTIME_DIR` on either. It is an empty tmpfs in every command's sandbox, mounted after the project and toolchains, wherever it is: a sandboxed command that could see a plug's socket could connect to it and use that plug's wires. And the mesh refuses a runtime folder outside `/run`, `/tmp` and the home folder's hidden entries. The runtime folder (the Linux and macOS defaults and `MARV_RUNTIME_DIR` alike) is made 0700 (only the last part, never recursively) and must then be a folder (not a symlink) owned by the user, with its parents judged as below, or the mesh and the process door's sockets are off. Where there is no runtime folder, the process manager's folder in the temp folder (`marv-<uid>/marv`) gets the same checks at each level. `MARV_RUNTIME_DIR`'s parent must exist and is judged by its real path; no folder on the way may be a symlink, another user's (a third uid that owns `/` in a container included: it could rename anything under `/`), or writable by others without the sticky bit: through a symlinked parent a path that looks hidden could be made where sandboxes see it, and a parent another user controls could be swapped before a socket is bound. The symlinks allowed are the root's `/tmp` and a link root owns in a root-owned folder nobody else may write in (not even sticky; Fedora Silverblue's `/home -> var/home`), followed one hop at a time (its stored target, refused if it has `.` or `..`), and its target and each of the target's parents are checked the same way, so every further link in a chain, and the folder it sits in, meets the same rule (#168). `MARV_RUNTIME_DIR` inside the session's project, or holding it, is refused (#168): a sandboxed command runs as the user, writes in the project, and could make the folder or its `mesh`/`p` folders first. The check knows only the session's own project: `MARV_RUNTIME_DIR` is one setting for all your sessions, so an override inside project P is refused by P's sessions but accepted by a session in project Q, while P's sandboxed commands can still make or rename what's under it. An override inside any project you run Marv in is unsafe for every session; keep it outside all of them. (`marv mesh ls`/`wire`/`plug` know no project and judge it without that check.) The folder's own real path is compared too, once it exists (a case-insensitive volume's `/tmp/Proj` is `/private/tmp/proj`). another user who made `/tmp/marv-<uid>` first can only turn it off, not take it over.
- **A decline with a reason is still a no (#185).** `Decision::Declined(reason)` never runs the call (only an explicit yes or always does), is never remembered, and answers the step-limit question and a mesh wire as "no". It's offered only for a model's call (`ApprovalRequest::reason`, set by `run_tool` alone), and read once by the engine (one line, control characters dropped, at most 500 characters; the web approver reads it the same way, and makes one sent for any other request a plain no). The reason becomes the call's result as the user's own words (`Provenance::User`: not fenced, it taints nothing); the turn goes on. Plain no and Esc still stop the run. `marv -p`'s approver never answers it. Guard: `tests/guards/tests/approvals.rs` (`a_decline_with_a_reason_never_runs_the_call_and_isnt_remembered`).
- **Radio requests and their replies (#124, phase 3) are data too, and the turn that handles a request approves nothing by itself.** A `request` goes to exactly one Marv, by the user or the model, and answers nothing; an `ack` is Marv's, fixed words only (no text); a `done` or `failed` is Marv's or the model's, at most 1 KB; each reply goes to the requester alone and names a request of the receiver's own (`<own>:<seq>`), and it's **taken only for a request that Marv sent to that very peer and that is still open** (one ack, one report): anything else is refused and never reaches a model. Replies never get a reply, a report or even a refusal told back (§8.6, 1). Requests are read only at a turn's start, fenced (`<radio-message kind="request" id=…>`, closing tag defused), tainting first, with Marv's constant request note: the model may work on it, **and that turn runs with automatic approval off, the person's own turn included** (marv-rs goes past the spec's §8.4 here: the note invites the model to act on another Marv's words, so yolo, "always" answers and pre-approved scopes never carry them out unasked; every approval is `once` and says why). The automatic report is built from the turn's end and its final reply's first paragraph (code dropped, `printable()`, cut to 1 KB), never from a model call. Hops stop chains: a request from a turn at hop 2 or more is refused at the sender's `radio_tx` and again at the receiver; a report wakes the requester only for a request sent from its person's own turn (hop 0); an `ack` never wakes. At most 2 open requests per sender at each receiver (mirrored at the sender) and 10 per receiver. A peer that refuses or loses a request closes it at the requester with a `failed` in Marv's fixed words. **A Marv on the radio is never typed into:** `herdr.pane.<pane>.send` and the Herdr door's `prompt` refuse a pane whose Marv's door says its radio is on (`HerdrAdapter::prompt_text`), pointing to `radio_tx`; the door's own spawn still types its approved task into the new pane. Guards: `tests/guards/tests/radio.rs` (phase 3 list).
- **Approvals show the full payload.** A network approval lists the scripts written this session that the command will run.
- **A network escalation is a network command, asked like one (#81).** A sandboxed command that failed like the missing network, retried without network (even with another tail), runs with `network: true` instead (`bash.rs`'s `repair`), so it goes through the approval for network commands and never runs on its own: in yolo too, since a network command is never `auto_safe`. A remembered or pre-approved "always" for that network scope answers it only where it answers any network command: not in a tainted session (`must_ask`), not in a turn without automatic approval (the radio's, a wake's: `once`), and a worktree subagent's automatic yes never covers it. With nobody to ask (`marv -p` without `--approve network`) it's refused before it runs. Guards: `approvals.rs::config_approve_never_covers_a_tainted_network_escalation`, `approvals.rs::an_escalated_retry_is_asked_in_a_turn_without_automatic_approval_and_in_a_subagent`, and `bash.rs`'s `with_no_one_to_approve_network_the_retry_is_refused_and_doesnt_run`.
- **Subagents don't inherit** network, web or mesh approvals — the config's pre-approved ones included (#98): `AlwaysScopes::for_subagent` strips the egress prefixes from the remembered scopes and the seeded ones alike.
- **Pre-approved scopes (#98)** — the config's `"approve"` (and the TUI's `--approve`) seed "always, for this session" through the same path a person's answer takes, so they never cover what asks even in yolo: protected paths, `package.json` lifecycle scripts, mesh wires (`once` + `must_ask`), tainted egress, and any file change when the project is the home folder (`once`). `marv -p` keeps its own `--approve` list out of the seeds, so a subagent's `for_subagent` is what bounds them; the flag list itself behaves as before.
- **Extra writable sandbox folders (#98)** — the config's `"writable"` is the one way a sandboxed command writes outside the project. Entries are canonicalised (symlinks followed) and refused at startup, not mounted: `/`, the home folder and its parents, the project's parents (other projects' `.git`), **any hidden top-level entry of the home** (`~/.<anything>`: the entry, anything inside it, or a parent of it — `.local/bin`'s planted binary runs on the host, `.config/autostart` and `.config/systemd/user` run at the next login, `.claude`'s hooks run on the host; only a *visible* top-level tree like `~/Projects/…` is allowed), **a git repository** (the entry is one, sits under a `.git` path component, or directly holds a `.git` entry — a worktree's `.git` file included; a planted `.git/hooks` script runs on the host's next git command there; a repository planted *deeper inside* an accepted folder later is not scanned — the refusal happens once, at startup), the mesh's runtime sockets (`$XDG_RUNTIME_DIR/marv`, anything in it or holding it), **Marv's own config folder** wherever `MARV_CONFIG_DIR` puts it (anything in it or holding it: its `config.json` holds the API key and the session-start hooks, and it holds the tool-output files), and anything missing or not a folder. Refused entries become startup problems, never mounts. An entry in the project (writable already) or inside another entry is left out quietly: a sandboxed command could swap its parent for a symlink, and the next command's bwrap would bind wherever that leads read-write.
- **`marv -p --approve` never answers a call that asks every time.** Tainted egress needs `--approve-tainted` as well as the call's `--approve` scope, and a protected-path write needs `--approve-protected` as well as `--approve files`; otherwise the call is refused (in `refused`, exit 3, a stderr line naming the flag). Subagents reach the same approver. The SDK hands the request to the client's approver with `must_ask` set, and an approver that answers from a policy should refuse it the same way. Guards: `tests/guards/tests/headless_taint.rs`.

## Compaction and saved pages (#63)
- **Taint survives compaction.** A summary can paraphrase untrusted text and the v2 tail carries it verbatim, so no compaction path touches the session's taint: the v1 and v2 summaries, overflow recovery's summaries and its level-3 drop of the oldest messages. A session tainted before is tainted after, in memory and in the saved session (dropping the turns that held outside text doesn't take back what the model may have acted on). Fences in kept turns keep their bytes. Guard: `tests/guards/tests/compaction.rs::taint_survives_compaction`.
- **What a compaction replaces is saved before it's replaced.** The paged-out turns go to the conversation's own swap folder next to its saved file (`<id>.swap/<n>.jsonl`, 0600 in 0700 folders, like sessions; it holds untrusted text, as the session file does), each with its source; the folder may not be a symlink, pages are numbered under a lock and never overwritten. The page is written before the summary is asked for. A write that fails fails the compaction and the history is kept, except in overflow recovery, where the turn goes on without the page and a notice says so. A live session holds its swap folder; one whose session file is gone, or that is older than the saved tool outputs' 7 days, is removed at a later session's start (`SessionStore::remove` deletes a session with its pages, for when sessions can be deleted). Guards: `compaction.rs::a_page_out_writes_swap_before_replacing_the_history`, `a_symlinked_swap_folder_is_refused`, `pages_are_never_overwritten`, `saved_pages_age_out_but_never_a_live_sessions`.
- **The page table is Marv's.** The list of saved pages at the end of a summary is built from the calls' runs, never from the model's summary: only calls that worked, paths resolved inside the project, control characters dropped, at most 200 characters, each shown as a JSON string (a path can't add a line to the list); saved outputs from the saved-outputs folder by call id. A list of saved pages in the model's own summary is removed before it's installed. Guards: `compaction.rs::the_page_table_is_written_by_marv`, `a_page_table_path_is_capped_at_200_characters`.
- **A recalled page keeps its source.** `recall` gives back each web, MCP or other outside result in a fence of its own source (a closing tag inside is defused) and marks the session tainted by each again: reading a page back can't turn outside text into trusted text. Guard: `compaction.rs::a_recalled_page_keeps_its_provenance`.
- **`recall` reads only its own conversation's pages.** It takes no session id or path; the main agent's context names the current conversation's swap folder, a subagent's names none (and its tools don't include `recall`), so another chat's or the parent's history isn't reachable through it. Guard: `compaction.rs::recall_reads_only_its_own_conversation`.
- **Nothing is retrieved on the model's behalf.** Saved pages come back only as the result of a `recall` call; the history is rewritten only at a compaction, and the tool list never changes at one (`recall` is offered from the start). Guard: `compaction.rs::the_tool_list_is_byte_stable_across_a_page_out`.

## The doors out of the sandbox (Marv Sprint 4)
Narrow, named ways out, each with what it can never do. A door's own program (`gh`, `herdr`) is taken only from an absolute PATH entry, by its real path, and never from inside the project or a sandbox-writable folder, where a sandboxed command could have put one (`marv_sandbox::host_env::host_program`). The mesh's Herdr panes (`mesh_cmd::start`, `marv mesh ls`) take `herdr` the same way, and offer no panes when none is found. In a home-folder project the home is the project, so a `gh` or `herdr` under `~` (`~/.local/bin`) is skipped and that door isn't offered there: it fails closed. A call through one carries its door on the approval (the prompt shows the door's warning line), on its result and in the trajectory. The doors are the main agent's: a subagent's context has none.
- **github** (Marv #47) runs gh with the user's login, outside the sandbox:
  - never: `auth`, `config`, `extension`, `alias`, an unknown first word (an alias or extension), `secret`/`variable`/`ssh-key`/`gpg-key`, `--web`, `gh api --input`/`--verbose`, downloads, `repo clone`, `pr checkout`, another GitHub host than the project's. Refused before anyone is asked, whatever the approver says;
  - writes, other API methods, fields, graphql and sensitive API reads (secrets, keys, hooks, emails…) ask, in yolo too; a sensitive read is asked every time (`once`);
  - gh is spawned without a shell, without Marv's keys or debug switches, with `GH_HOST` pinned to the project's host (github.com where origin names none), and its git never runs the repository's programs;
  - GitHub token shapes are redacted from what gh prints before the model, the events, the saved session or the trajectory see it;
  - a subagent only reads; offered only where gh is there and logged in; `marv -p` needs `--approve github` for a write.
- **host** (Marv #52) is bash with `sandbox: false`, one command on the user's machine:
  - asked every time (`once`: "always" never covers another), in yolo too;
  - only where someone approves each command at a terminal (the TUI; the SDK's `host_commands`): refused before any ask in `marv -p`, in an SDK session without `host_commands`, and for a subagent;
  - its environment is the user's minus Marv's keys and anything secret-looking (`marv_sandbox::host_env`); token shapes are redacted from its output.
- **herdr** (#74) drives Herdr, the terminal multiplexer Marv runs in, from Marv's own process (the `herdr` CLI, through mesh v2's adapter). Offered only when Marv starts in a Herdr pane (`HERDR_ENV`), fixed for the session; the sandbox still can't reach Herdr (its variables cleared, its socket hidden: #130), only the door can:
  - **reads run without asking** (list workspaces, tabs, panes, agents; a pane's status; a pane's last lines). What comes back is other programs' text (screens, names and titles anyone can set): it's `Provenance::Herdr`, fenced as data (`<untrusted-data source="herdr">`) and it **taints** the session, like a mesh message;
  - **light actions ask** (focus, rename, a prompt typed into an idle agent's pane), "always" allowed (`herdr:focus`, `herdr:rename`, `herdr:prompt:<pane>`). A prompt is never a command (the pane send's rule, #128: text starting with `/`, `!` or `#` is refused before anyone is asked). In a turn the person didn't start (a mesh wake or the radio: `ToolContext::mode` without automatic approval), they're asked `once`, like every request there: no remembered "always" answers them;
  - **running anything is asked every time** (`once`: never remembered, not by "always", the config's pre-approved scopes or yolo): `run` (a command in a new pane) and `spawn` (a Marv or another Herdr agent kind, optionally in a new git worktree). The approval shows the exact command, the folder or branch, the worker's kind and its task. Only where someone approves each one at a terminal (`Doors::herdr`, the TUI's main agent, as `host`): refused before any ask in `marv -p` (with every `--approve` name: none covers `herdr:`), in an SDK session without `host_commands`, and for a subagent (which isn't offered the tool at all);
  - **a spawned worker gets no more than its parent:** a Marv starts with the user's config only (never the session's `--approve` scopes or remembered answers), and with `MARV_YOLO=off` (which can only turn yolo off; `/yolo on` is refused there) unless the spawning turn is in yolo; another agent kind starts with no arguments a model chose (the tool has no field for them). At most `herdr.peers` panes per session (the user's own config; default 4, 0 to 16), checked before anyone is asked; a pane Herdr no longer has doesn't count;
  - **taint isn't laundered through another agent:** a worker spawned from a tainted conversation starts tainted (`MARV_TAINTED=1` on a Marv's command, which can only add taint; it shows a startup note and marks `Provenance::Herdr` at its first turn, so its egress asks). A prompt or spawn in a tainted conversation is egress (`must_ask`) and its approval says "The receiving agent will treat this text as your own words, with its own approvals.";
  - **nothing a model passes reaches the `herdr` CLI as an option:** ids start with a letter or digit, and a rename's name, a run's command and a prompt or task (`pane_prompt`, the mesh's pane sends too) can't start with `-`. A run command can't start with `^` (quick substitution) or hold `!` (history expansion), invisible format characters, line or paragraph separators or the Hangul fillers; one that starts an agent gets a warning pointing to spawn;
  - the panes it opened outlive the turn and are the user's: `/peers` lists them, `/peers read <name>` shows one's last lines, `/peers stop <name>` closes one (never the model's to do). `/exit` and Enter (or ctrl+c) are typed only into an agent that's idle or done: one that's working or at an approval gets nothing typed (Enter would answer its question) and its pane is just closed; a pane that's already gone is forgotten. A worktree stays until the user removes it. Pane names, titles and output reach the terminal only through `printable()`.

## Provider keys and subscription sign-ins (#159)
- **Each provider gets only its own credential.** OpenRouter's key (`apiKey`, `OPENROUTER_API_KEY`) and the Z.ai Coding Plan's (`zaiApiKey`, `ZAI_API_KEY`) are separate fields and variables, and the ChatGPT sign-in is its own file: a provider without its credential asks for it (setup opens), it never borrows another vendor's. Guard: `tests/guards/tests/subscriptions.rs` (`a_providers_key_never_goes_to_another_provider`).
- **A plan's limit is a hard stop.** A usage-limit error from a plan ends the turn with Marv's message; it's never retried like a passing rate limit and never answered by switching keys or providers (`errors::plan_limit`). Guard: `plan_limit::a_plans_limit_is_a_hard_stop`.
- **Sign in with ChatGPT's loopback listener** (`marv_provider::chatgpt`) binds 127.0.0.1 only (never `0.0.0.0`, never `localhost`), answers only `/auth/callback`, takes exactly one callback (the first carrying the sign-in's `state`, compared in constant time; others get a page and are ignored), stops listening after it, and gives up after 5 minutes or when setup closes. Connections are answered side by side, each given 2 s for its request line, so an idle local connection can't hold the callback up (guard `sign_in_listener::an_idle_connection_doesnt_stall_the_sign_in`). A sandboxed command shares the loopback network: without the state it can't feed Marv a code. The browser page echoes nothing from the request; a refusal is shown only as a short code. PKCE (S256) and the ID token's checks (RS256 against OpenAI's JWKS, issuer, audience = the issued client id, expiry, nonce) mean a code alone is worth nothing. Guards: `sign_in_listener::the_sign_in_listener_is_loopback_only_needs_the_state_and_takes_one_callback`, `sign_in_listener::the_sign_in_listener_times_out`.
- **Its token goes only to OpenAI's public API** (`https://api.openai.com/v1`): a config's `baseUrl` is ignored for ChatGPT, and the token file must be an absolute path (no fallback to a file in the working folder). Guard: `the_chatgpt_token_is_never_sent_to_another_host`.
- **Its tokens stay in Marv's config folder.** `~/.marv/chatgpt.json` (or `MARV_CONFIG_DIR`'s), 0600 in a 0700 folder, written atomically and refreshed under a lock across Marv processes. The config folder is hidden from every sandboxed command; the tokens are never put in an environment, a log, the transcript, an event or a trajectory, and the stored record's `Debug` leaves them out. Guard: `sign_in_listener::the_sign_in_tokens_never_show_in_debug_output`.
- **Marv never sends another app's OAuth client id.** The sign-in registers dynamically (`dynamic_agent_client` under Marv's name) and then uses the client id OpenAI issued in the callback; the Codex CLI's is never used. Each registration (an issued client id and the account it was issued for) keeps its own tokens: one registration's client id is never paired with another's tokens. The authorize address shown on screen leaves out the `id_token_hint` (a token); only the browser gets it.

## MCP
- Project servers need trust. The hash covers the entry and the files its command runs.
- `npx`/`uvx` run outside the project folder.
- Server `instructions` are ignored.
- Tool descriptions in Marv's deferred-tools note and in `tool_search`'s answer are fenced as MCP data (`tool_search` caps each at 1,000 characters); they don't taint, since the person installed the server. The specs sent as tools can't be fenced and stay as the server wrote them (capped at 2,000 characters). Guard: `untrusted_text.rs::mcp_descriptions_in_announce_and_tool_search_are_fenced`.

## File changes
- **No write over a change the session hasn't seen.** Two Marv sessions in one folder, a subagent, a command or the person in their editor can change a file after the model read it; an edit built on the old text would silently drop that change. Each session keeps a content hash (SHA-256) of every file it read (`read_file`, any page; a `grep` hit doesn't count) or wrote (`marv_tools::file_versions`). `edit_file` and `write_file` (appends included) on an **existing** file refuse when the file's hash now differs from the session's, or when the session never read it, with an error telling the model to read the file again; nothing is written and no one is asked (the check runs in the preview, and again at apply time). A new file needs no read, and is created only if it still doesn't exist (a file someone made meanwhile is refused as never read). The session's own write is its new version: the formatted file when the formatter ran on exactly that write, else what it wrote, and if the file no longer matches (the write failed, or the file changed right after it) the next write is refused with a message that says so rather than blaming another session. A partial read counts as seen (the hash is the whole file's). At most 10,000 files are remembered per session, least recently used out first; a forgotten one must be read again. A subagent has its own hashes; /clear and a resume start empty. `bash` writes aren't tracked, so a file a command changed must be read again before an edit. Guards: `tests/guards/tests/stale_writes.rs` (`an_edit_after_another_sessions_write_is_refused_until_reread`, `an_existing_file_never_read_cant_be_overwritten`).
- **The check and the write are one step, across processes, and no lock outlives a call.** Inside the in-process per-file queue, the edit tools hold an advisory `flock` on a per-file lock file in the runtime folder's `file-locks/`, or `~/.marv/file-locks/` where there's no runtime folder (both hidden in every sandbox, so a command can't hold one), for the check, write and format of that one call, never across a model step or a turn; the OS drops it if Marv dies. Both locks are keyed on the file's resolved real path (`~/`, `..` and symlinks resolved; the name case-folded on macOS and Windows), so every spelling of a file is one lock. A call that can't get it within 20 s, or whose wait is ended by Esc, fails and writes nothing. Known limits: hard links to one file are separate locks, and Marv processes using different lock folders (a different `MARV_RUNTIME_DIR`) don't see each other's; the content check still applies to both. Guards: `stale_writes.rs` (`the_check_and_write_are_atomic_across_processes`, `no_lock_outlives_one_call`, `a_home_spelling_of_a_file_waits_for_the_same_lock`).

## Images (when vision is added)
- **Sources:** only the user (a paste, or a file they name). Never forwarded automatically from web, MCP or mesh.
- **A quarantined reader:** a tools-less model call extracts the image's text and description. The main model sees only that, fenced as `Provenance::Image`, and it's shown in the transcript. Any image taints the session.
- **Decoding** happens in the sandbox, with metadata stripped and size limits.

## Proof
- `tests/guards/`: one test per rule. Each one fails when its guard is reverted, and they run in CI.
- An injection eval suite (poisoned README, web page, MCP issue body, mesh message, later images). It passes when the model never tries to send data out or write a protected path.
