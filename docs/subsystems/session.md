# marv-session

The UI-free engine: Marv's `MarvSession` and everything around it. It covers config, the system prompt, sessions on disk, trajectories, usage, memory, skills, agent types, subagents, worktrees, git, project checks, diagnostics, slash commands (the engine side) and the SDK. The TUI, headless `marv -p` and the SDK all drive it. It never imports the TUI.

Spec: the **Config**, **Session**, **SDK**, **Skills**, **Memory**, **Subagents**, **Worktrees**, **Diagnostics**, **Project checks**, **Slash commands**, **Tokens and cost**, **Project keys**, **Private files**, **Sessions**, **Trajectories** and **Compaction** bullets in Marv's `CLAUDE.md`, and the matching `tests/*.test.ts`.

## Port notes

- **Shared state.** `MarvSession` is an `Arc` around one `Mutex<State>`. The lock is never held across an `.await`. The conversation is a `marv_agent::History` (`Arc<Mutex<Vec<ChatTurn>>>`), so a mid-turn compaction swaps it in place, as Marv's `splice` did.
- **A turn runs on its own Tokio task** and pushes into an `EventQueue`. `Turn` reads the queue. Dropping a `Turn` cancels its token, which is Marv's `break`. To wait for the cleanup, use `Turn::finish().await`: `Drop` can't await.
- **Lengths count `char`s** (Marv counted UTF-16 units). This affects the AGENTS.md cut, titles and the 500-character memory entries.
- **Token formatting** (`usage::tokens`) uses integer half-up rounding, to match JavaScript's `toFixed` on ties.
- **Frontmatter YAML** uses `serde_norway`. The YAML error wording differs from Bun's.
- **Project-check patterns** are JavaScript regexes. Rust's `regex` has another dialect (no lookaround, no backreferences), so they're validated at load and matched in the sandbox with `regress`, an ECMAScript engine. Globs use `globset` with `literal_separator` (Bun.Glob: `*` stays in its folder).
- **The check runner is redesigned (#13).** Marv sent TypeScript source to `bun -e` inside the sandbox; marv-rs has no TypeScript of its own. The command is `'<marv>' __run-checks '{"checks":[names],"timeoutMs":30000}'`, with the `marv` binary (`current_exe`) mounted read-only (`CheckPass::read_only`). The runner loads the named checks from the read-only project itself, matches the patterns, and runs `.ts` scripts with bun from the sandbox's `PATH` (30 s each, 1 MB of stdout, 500 violations, 16k of stderr, as Marv's). Without bun it ends as `bun -e` did, `bun: command not found` with exit 127, so the missing-interpreter notice still applies.
- **Project checks are loaded on every pass**, not once per turn and again only after a change to `.marv/checks/`: a check changed some other way (bash) also runs as it now reads.
- **`RunCheck` takes a `CheckRun`** (command, root, extra read-only paths, timeout) and a cancel token. Marv's runner could throw; here a spawn failure comes back as unreadable output (`[couldn't start the command: …]`), which is reported the same way.
- **A panicking provider or tool** (Marv: one that throws) is caught around the turn's body (`catch_unwind`): the turn ends with `Error: <message>` and `TurnEnd`, and the session lives on.
- **`working` is a token** cancelled when the turn's task (or `compact()`) has fully ended; `close()` waits on it. `compact()` frees the session from a drop guard, so a caller dropping its future can't leave it busy.
- **The radio (#124, phase 3: requests):** `mesh::inbox_read` (at a turn's start: requests too, returned as `InboxRead::requests`) and `inbox_note_with` (between steps: `drain_radio_but_requests`, so a request waits for the next turn's start). `turn_body` adds what it read to `State::radio_requests` (`OpenRequest`s, also saved as `SavedSession::radio_requests` and restored on resume; `reopen`ed on the radio), schedules a save, and a turn that handles requests runs with `ToolContext::mode` without automatic approval and `RadioTurnApprover(.., RADIO_REQUEST_WARNING)` (marv-rs deviation from spec §8.4, safer: also the person's own turn). `State::radio_turn` (`RadioTurnFacts`: number, handles, last reply, declined tool) feeds `run_turn`'s `radio_reports`: one `Radio::report` per open request, a `SessionEvent::RadioNote` line per report sent (or not sent), none for a request the model answered. `wake_radio` takes `RadioWakeBy::note` (a request's or a report's wake note). The Herdr door's adapter gets the mesh folder (`set_mesh_dir`) so its prompt refuses a Marv on the radio.
- **The radio (#124, phase 2: messages):** `SessionInit::radio` (`None`: never on it, `marv -p` and the SDK; `Some(on)`: the TUI's, `on` from the user's config at startup). `State::radio_offered` is decided when a conversation starts (`new` from `init.radio`, `clear` from the switchboard's radio being on; a resume keeps the current one, as it keeps the system prompt) and fixes both `radio_tx` in `offered()` (right after the mesh's tools) and `RADIO_PROMPT` with its name in the prompt's tool list. `inbox_note_with` reads the radio's queue for the main agent only, as `RadioRead` says: `Read` in the person's own turn (hop 0), `RaiseHop` in a radio-started turn (its hop rises to one past the deepest message read), `Skip` in an inbox-woken turn (#78, which may auto-approve) and for subagents; it marks `Provenance::Mesh` before anything is sent. `MarvSession::wake_radio` starts a `Woken::Radio` turn: hop one past the message's (`Inner::radio_hop`, read by `radio_tx`), `ctx.yolo` off and `ctx.mode` `CallMode::Radio` (marv-tools: automatic approval off, no yolo, no approved URL prefix, every request `once`; subagents inherit it), the client's approver wrapped in `RadioTurnApprover` for the turn and its subagents, and an empty `AlwaysScopes` (so neither a person's "always" nor the config's pre-approved scopes answer). Trajectory: `TrajectoryRecord::RadioFrame` (serialized `type: "mesh"`, `radio: true`, never the text) through `MeshSink::radio_frame`, `TurnStart::radio_wake` (id, sender, hop; `yolo` recorded as off), `trajectory_stats::radio_stats`. `/tx` is `CommandAction::Tx` (`commands::parse_tx`: leading `@name`s, none for all; refused with the radio off).
- **The radio (#124, phase 1: presence):** config `mesh.radio` (`FileConfig::mesh_radio: Option<RadioSetting>`, `true`/`false` or `{"titles": false}`; `Config::mesh_radio`, default off, and `Config::radio_titles`), read only from the user's own file; `hooks::project_hooks_refusal` notes a project's `mesh` key (radio or wake) as ignored. `/radio [on|off]` (`CommandAction::Radio`, `CommandAction::RadioView`, `commands::RADIO_OFF`). `MeshTool::wireable` adds `Radio::listed` (names and states) for the main agent only, so `mesh_list`'s "On the radio" section stays untainted; no new tool and no tool-spec change. `TrajectoryRecord::Radio` through `MeshSink::radio`. `MarvSession::first_message` is presence's title source.
- **Mesh wake (#78):** `MarvSession::wake(&WakeBy)` starts a turn with no user message when the main agent's inbox has something unread (`None` otherwise; `Busy` during a turn). It shares `send`'s path (`start(.., woken)`): the inbox goes in fenced and tainting as for any turn, `mesh::WAKE_NOTE` is the turn's own text, the transcript records `WakeBy::line()` as `Role::System`, and a woken line's links never become "pasted" web scopes. `mesh::wake_check` and `WakeLimit` decide whether to wake (granted wire, `WAKES_PER_MINUTE` per wire); the caller (the TUI) checks the setting, idleness and open approvals. Config: `mesh.wake` (`FileConfig::mesh_wake`, nested `{"mesh": {"wake": bool}}`, default off). Commands: `/mesh` (`MeshStatus`: the door's name and the wires into the inbox), `/mesh wake [on|off]` (`CommandAction::MeshWake`).
- **Mesh (#15):** with a switchboard, the main agent's plug is `parent` (bound in `MarvSession::new`); its inbox is read before each turn's message and after each step, fenced, tainting the session (`Tainted` is now checked after every non-delta loop event, not only after calls). Each subagent gets its own `worker-N` plug, mounted in its sandbox, with the mesh tools and an inbox read between steps; `SessionAgentHost::mesh` carries the switchboard and wire approver. Wires come from `SessionInit::wire_approver`, else a person through `SessionInit::approve` (never the "always" layer or yolo).
- **Subagents (#12).** `run_subagent` wraps the subagent's loop and `finish_worktree` in `catch_unwind`: a panicking provider or tool (Marv: one that throws) still gets its worktree committed and its branch reported, and a panic while finishing reports `couldn't finish the worktree (…); it's at <dir>.` `finish_worktree` itself never fails: every problem becomes the line the parent reads. A subagent's approver is `SubagentApprover` → `SessionApprover` (its own `AlwaysScopes::for_subagent`, the turn's stop) → the client's. Its tools are `builtin_tools()` ∩ `SUBAGENT_TOOLS` ∩ the type's, in the built-in order (the prompt cache), with `skill` only when there are skills.
- **Worktree git is async** (`run_git` on `tokio::process`), like the nested-repo walk and the folder's removal; Marv's git calls were synchronous. Two cases aren't ported as written: `worktree.test.ts`'s "inherited `GIT_*` variables" sets `GIT_INDEX_FILE` in the test process (here `git_environment` takes the outer environment as a parameter and is tested in `git.rs`), and `agent-tool.test.ts`'s "if finishing the worktree throws" mocks `finishWorktree` (not possible without a seam; the panic path is covered by the panicking-provider test).
- **The process door (#24, Marv #51).** `SessionInit::processes` (default true; offered only where bubblewrap works, fixed for the session: it changes the tool list and the prompt) and `process_manager` (tests pass one with a fake home; default: one made with the session, which makes its folder at the first start: in the runtime folder, else `<temp>/marv-<uid>/marv`, each level through `marv_sandbox::private_folder`). The main agent's context gets `doors.process` and the process host; every agent's (subagents' too) gets `forwards`, so its sandboxed bash reaches the servers. Processes outlive turns, `clear()` and `resume()`; `close()` and `stop_processes()` stop them; `processes()`, `stop_process()` and `processes_offered()` are for the client. The SDK's `SessionOptions::processes` mirrors Marv's `processes` option. Without the door, `process` is free as a custom tool name and not offered.
- **The relay is a hidden subcommand, `marv __relay <spec>` (#24).** Marv sent `relayMain`'s source to `bun -e` inside the sandbox, mounting its own bun at `/run/marv-bun`; the review caught that the published bundle rewrote its `require` into a `__require` that didn't exist there. marv-rs compiles the relay in (`marv_tools::relay`, where bash can use it too) and mounts its own binary (`current_exe`, or a test's fixture via `set_relay_exe`) read-only at `/run/marv-bin`, as `__run-checks` does. The spec is JSON (`{"listen": …}` or `{"connect": [{port, socket}]}`, plus `argv`).
- **`--die-with-parent` follows the thread** that spawned bwrap (`PR_SET_PDEATHSIG`): processes are spawned from async tasks (runtime workers, or the `block_on` thread), never from a blocking-pool thread that may exit while idle.
- **Checkpoints (#22).** Marv's tests replaced `store.snapshot` and `store.chain` on the instance; here `CheckpointStore::fake` (`Fake`: a snapshot answer per kind, a delay, a chain error) does it. `marv_tools::Checkpoint::checkpoint` returns nothing, so "a failing checkpoint doesn't fail the call" can't happen by type; the registry test checks a stop while it's taken instead. Paths come back from git as UTF-8 (lossy): a path that isn't UTF-8 keeps what `add -A` stored. `undo_plan()` is `Result<Result<UndoPlan, UndoRefusal>, SessionError>` (the outer error is a busy or closed session); `undo()` fails with `SessionError::Undo` for a stale plan or a failed pre-undo snapshot. Mesh tools take no checkpoint (another agent changes its own project), like MCP tools, `memory` and `agent`.
- **Trajectory usage** is written with Marv's camelCase field names (`UsageRecord`). `marv_core::Usage` serializes in snake_case, so it isn't used directly.

## marv-rs behaviour changes

- **Fenced project text (fixes a Marv 0.3.0 bug).** The typecheck and project-check notes are now an automatic note in Marv's own words, followed by the project's output inside `<untrusted-data source="project">`. Before, they began `Marv:` and quoted project text verbatim. Guard: `tests/guards/tests/checks.rs`; the oracle's `ts-new-type-error` declares it (`deliberate`, under #41). Results from web, MCP and image tools are fenced the same way in `tool_run_from`. Mesh messages arrive already fenced.
- **"Always" doesn't answer `must_ask` requests** (tainted egress, protected paths): `SessionApprover`. Guard test: `runner::tests::must_ask_requests_are_never_answered_from_always`.
- **Subagents don't inherit network, web, MCP or mesh approvals** (`AlwaysScopes::for_subagent`). Their taint is `TaintState::for_subagent()`. In a worktree, `SubagentApprover` never auto-approves `must_ask` or `once` (a file change in the home folder).
- **Pre-approved scopes (#98):** the config's `approve` names (and the TUI's `--approve`) seed `AlwaysScopes` at session start (`approvals::seed_prefixes`), so they answer through the same path a person's "always" takes: `must_ask` (protected paths, tainted egress) and `once` (host commands, mesh wires, file changes in the home folder) still win. They are listed in the `# Your situation` section (fixed per session, the cache holds). The TUI's and headless's own `--approve` flags are *not* seeds in `-p` (the `ScopeApprover` covers them, as before); a subagent's `for_subagent` strips the egress seeds.
- **The config dir comes only from the real environment.** The CLI builds `Env` from `std::env::vars()`. No project file is ever consulted.
- **Skills, agent files and checks are read only after a realpath containment check** (`marv_sandbox::resolve_within`, or `symlink_metadata` for checks). A symlink out of the project is refused and reported.
  - Exception (#75): a personal skill folder linked to a folder only root can change (`system_owned`: it and every parent owned by root, not group/world-writable) loads from the real target, so `Skill::dir` is that target and the `skill` tool reads there (outside the sandbox, confined by `resolve_within`). `/skills` shows it as `personal: omarchy → /usr/share/…`. A project skill's link is always refused. Tests inject the ownership check (`load_skills_with`, `only_root_can_change`).
  - Started in `~`, `.marv/skills` and `~/.marv/skills` are the same folder (compared after canonicalize): it's scanned once, as personal skills, so each problem is reported once.
- **A background process's new protected files are removed when it ends** (#24): the same scan bash runs after a command (`protected_snapshot` at the start, `scan_created`/`revert_created` when it stops or exits, the note in its `notes`). Marv had no such scan.
- **Session-start hooks (#108).** `SessionInit::hooks` / `SessionOptions::hooks` (default none; only the CLI fills them, from the user's config). A round runs in the background per conversation: `run_start_hooks()` (a client, at start; idempotent), else the first turn; `clear()` and `resume()` start a new one (a round they replace is stopped: its commands killed, its output dropped). The check and the claim are one lock, so concurrent starts run each hook once; `close()` stops a running round, with what it started, and waits for it (at most 5 s); nothing starts after. `project_hooks_refusal` reads only a regular file inside the project (`resolve_within`, opened non-blocking, at most `PROJECT_CONFIG_CAP`). `start_hooks_done()` waits for the current round, for a client to show it. The first turn waits for the round (Esc ends the turn; the output waits for the next one), then the note leads its user message, before the undo note, the inbox and the MCP note, once per conversation. It never goes in the system prompt, which stays byte-identical with or without hooks (tested), so the cached prefix holds; history stays append-only. Subagents never get it (their context is their own prompt). Each run is a `hook` trajectory record (`command`, `exitCode`, `timedOut`, `bytes`, `ms`) in that turn. When an untrusted hook printed something, that turn marks the taint (`Provenance::Hook`, new in marv-core, `taints()` true) before its request: `SessionEvent::Tainted` and a `taint` record, so egress asks from then on, even in yolo.
- **A wrap-up reply at the step limit (#59).** `run_turn` and `drive` (subagents) set `AgentOptions::wrap_up_at_limit`. With no one to say "keep going" (no approver, as in `marv -p`; an approver that answers the step-limit question `Unavailable`, as `marv -p --approve` does; a subagent, which has no `on_limit`), the loop sends one more request with `STEP_LIMIT_NOTE` and `ToolChoice::None`. Its text is the turn's last `Assistant` (the headless reply) or the subagent's report, ahead of Marv's limit line. A "no" in the TUI stops without it. Tests: `turn_tests::with_no_one_to_ask_the_step_limit_gets_a_tools_off_wrap_up_reply` (+ the `Unavailable` and "no" cases), `run_tests::at_its_step_limit_it_reports_a_wrap_up_instead_of_the_bare_limit`, and `marv-cli/tests/headless_step_limit.rs` end to end.
- **New events and records:** `SessionEvent::Tainted`, plus the `taint` and `mesh` trajectory records.
- **The announced-step continue (#90):** when a turn's final reply announced its next step but made no tool call, the loop (marv-agent's `announce`) says "continue" once per turn; the TUI shows a `✻` line and the trajectory gets an `announced_step` record. `MARV_DEBUG_RAW=1` makes the session turn on the providers' raw-response recording (`AgentOptions::debug_raw`), so the turn's `request` records carry `rawResponse` and `finishReason` for diagnosis.
