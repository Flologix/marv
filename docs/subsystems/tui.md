# marv-tui

Marv's terminal UI, rebuilt on **ratatui 0.30 + crossterm 0.29** (Marv used Ink/React). It renders what the engine reports and sends back what the user asks for. It never imports `marv-session`: the boundary is `view.rs`.

Spec: Marv `CLAUDE.md` bullets **Rendering**, **Mouse**, **Selection**, **Replies are Markdown**, **Setup**, **Waiting line**, **Render budget**, **Yolo mode** (status bar), **Tokens and cost** (status bar); `src/app.tsx`, `src/ui/*.tsx`, `src/mouse.ts`, `src/selection.ts`, `src/clipboard.ts`, `src/render-options.ts`; tests `tests/{app,approval,diffview,markdown,martian,messageview,mouse,noticeview,prompt,render-options,render-performance,scrollview,selection,setup,clipboard}.test.ts(x)`.

## The boundary the engine implements

```rust
pub trait SessionPort: Send + Sync {          // every method returns at once; results come back as UiEvents
    fn commands(&self) -> Vec<CommandInfo>;   // the `/` menu and the ctrl+k palette (kind, while_busy)
    fn settings(&self) -> Vec<SettingInfo>;   // the palette's settings, values as they are now (default: none)
    fn send(&self, text: String);             // start a turn
    fn send_now(&self, text: String);         // Alt+Enter during a turn: in at its next step (→ SentNow / NotSent)
    fn queue(&self, text: String);            // #184: Enter during a turn: after it (→ Queued)
    fn unqueue_last(&self) -> Option<String>; // ↑ / ctrl+x: the newest queued message out
    fn take_queued(&self) -> Option<String>;  // Enter on the empty prompt, idle: the oldest out, to send now
    fn run_command(&self, line: String);      // a slash command; UI-side results as events
    fn answer(&self, id: ApprovalId, decision: Decision);
    fn abort(&self);                          // Esc / ctrl+c
    fn load_models(&self, provider: ProviderId);     // → UiEvent::Models
    fn complete_setup(&self, answer: SetupAnswer);
    fn resume(&self, id: Option<String>);            // → UiEvent::Resumed
    fn flush(&self) -> BoxFuture<'static, ()>;       // before exit
}
// App::new(port: Arc<dyn SessionPort>, events: UnboundedReceiver<UiEvent>, options: AppOptions)
```

`UiEvent` mirrors Marv's `SessionEvent` (the turn and its `LoopEvent`s, `Subagent { call_id, title, event }`, `SubagentProgress`, `Compaction`, `TurnEnd`) and adds `Approval { id, request }` (and, marv-rs #201, `ApprovalWithdrawn(id)`: the request's wait was dropped, e.g. another Marv's wire whose caller hung up, so it leaves the queue unanswered) plus the results of port calls (`Message`, `StatusInfo`, `Welcome`, `Clear`, `OpenSetup`, `Sessions`, `Models`, `Resumed`, `Flash`, `Busy`, `Exit`). The engine maps project checks and diagnostics to `Message`s with a `Notice`. The approval queue lives in the TUI as in Marv: each request has an `ApprovalId`, the head is shown with "N more waiting", and Esc answers `No` to the whole queue and then calls `abort()`.

## Port notes

- **Idle CPU (Marv #68).** Ink used 40–60% CPU per session. The App waits in one `tokio::select!` over crossterm's `EventStream`, the `UiEvent` channel and `sleep_until(earliest deadline)`, and draws only when something changed. Every animation exposes a deadline instead of owning a timer: the martian (only while the welcome banner is in the viewport), the 33 ms stream flush, the 20 ms wheel glide, the selection auto-scroll, the spinner (only while shown), and the notice expiries. With nothing animating, the loop sleeps until input arrives. `examples/martian.rs` is a miniature of this loop.
- **Paced streaming (deliberate difference).** Text deltas collect in a buffer. The reply and the reasoning are revealed from it one share per frame (1/7 of what's hidden, at least `REVEAL_MIN_CHARS`), so each provider burst drains over about `REVEAL_MS` (120 ms) instead of landing at once. Marv batched at a fixed 33 ms, so text came in jerks. A backlog over `REVEAL_CATCH_UP` shows at once. Step ends show everything at once. The loop drains all queued events before it draws.
- **What Marv's Ink patches did, and what replaces them:**
  - *Viewport culling* (`patches/ink@8.0.0.patch`). Ink drew every scrolled-away message on every frame: ~270 ms per keystroke on 60 entries, ~30 ms patched. Here each entry caches its wrapped lines per width (Marv's `memo`), `ScrollView` keeps prefix sums of the heights, and only the entries that intersect the viewport are rendered.
  - *Selection overlay* (`transformOutput` + `repaint()`). Marv drew the highlight into Ink's output string, so moving it cost ~3 ms instead of a ~30 ms React render. Here `SelectionStore::transform_buffer` reads and highlights the drawn `Buffer` after the widgets render. Because frames are culled and ratatui diffs cells, moving the highlight is an ordinary cheap draw.
  - *Render speed* (the `string-width` patch, and skipping `findStaticNode`). `string-width` was ~36% of CPU while scrolling, because of its per-character emoji regex. `unicode-width` is a table lookup, and there is no React tree to walk.
  - *Incremental rendering* (`incrementalRendering: true`, guarded by `.marv/checks/render-options.yaml`). ratatui diffs at the cell level natively; the App wraps each frame in synchronized output.
- **Mouse.** `crossterm::EnableMouseCapture` also turns on mode 1003 (every motion), which would wake the loop on each mouse move. `TerminalGuard` writes Marv's `MOUSE_ON` (1002 + 1006) raw instead. crossterm parses SGR codes, including split ones, so Marv's `filterMouseInput` stdin wrapper has no counterpart.
- **Clipboard.** It uses platform tools, then falls back to OSC 52 (`base64` crate). We chose this over `arboard`: no X or Wayland libraries in the static binary, and it works over ssh.
- **printable().** View-model text is raw. The function that draws it calls `marv_core::printable` (`markdown::render`, `message_view::render`, `splash`, `welcome`, approvals, the status bar, agent titles), so the model's conversation is never modified.
- **Martian timing.** Marv re-armed `setTimeout` after each render, so it drifted. `MartianAnimation` adds each step's ms to the previous deadline, so it doesn't drift, and it resyncs instead of replaying when woken more than one loop late.
- **"Send now" (marv-rs).** Alt+Enter (or ctrl+s, for terminals that keep Alt+Enter, such as Windows Terminal; raw mode turns XON/XOFF off, so it arrives) while a turn runs (`PromptOutcome::SendNow`) sends the line with `SessionPort::send_now` instead of leaving it in the prompt (plain Enter is unchanged: nothing is sent while busy). Idle, on a `/command`, or in a subagent's view, Alt+Enter is Enter. The message joins the transcript only when the turn reads it (`UiEvent::SentNow`), so it shows after the step's tool entries; until then the status bar says `· 1 for the next step`, and while busy it hints `alt+enter send now`. `UiEvent::NotSent` (the turn ended first; or the bridge found no turn) puts the text back at the start of the prompt (`PromptInput::give_back`, ahead of anything typed since, its paste chips kept), one message per line (the prompt draws a line break as a new row; only this text has one, where `set` would make multi-line text a chip), with a `✻ Not sent` line. A send now with paste chips sends the pasted text, as Enter does (`PromptInput::text`). The palette lists the key. (marv-cli's bridge no longer emits `NotSent`: it queues that text, below.)
- **The queue (marv-rs #184).** Enter while a turn runs (`turn` set; a `/command`, or work outside a turn, `Busy`, still waits in the prompt) calls `SessionPort::queue`: the line leaves the prompt (and joins the ↑ history), and `UiEvent::Queued(list)` (the engine's whole list after any change; the App also changes its copy at once) shows it above the prompt, `queued › text` per message, at most `QUEUE_SHOWN` (3) and `+N more queued` (`prompt_input::queue_rows`). ↑ on an empty prompt (not browsing the history) takes the newest back into the line with `unqueue_last`; ctrl+x drops it (a flash says so). The status bar hints `enter queues` while busy and, with a queue, `↑ edit queued · ctrl+x drop`; idle with a queue a stop kept, `enter sends queued · ↑ edit · ctrl+x drop`, and Enter on the empty prompt sends the oldest (`take_queued`, then as typed). The queue itself lives in marv-cli's bridge, on the gate that starts turns (`Gate::queued`), shared with input that meets a mesh-woken turn: after a turn that finished (or a wake that did nothing) the next queued message starts there, its line emitted first as a `Message`; after a stop, an error or a limit the person's messages are held (`Gate::held`, with a `✻ Stopped. Your N queued messages wait` line, said once by the end that held them) until they send or queue something (either releases the hold). Input the App already showed (it sent it as if idle, racing a wake) always goes on, ahead of the person's queued messages, and isn't listed. Every change to the queue is listed to the App (`Queued`), also when a queued message starts at once. A queued message `session.send` refuses goes back to the front of the queue. The first `/exit` with messages queued warns that they'll be dropped (the next one leaves), and ctrl+c's exit confirm counts them. "Send now" text the turn never read (`SessionEvent::NotSent`) and a send now that finds no turn join the queue at its front.
- **Not in this crate:** `src/commands/*` (the engine runs them and sends the UI-side results) and Herdr reporting (marv-cli).
- **Two kept copies (#9).** marv-tui depends only on marv-core, so it can't call marv-session's `tool_draft` or marv-tools' `preview_lines`/`file_lines`. `thinking_view` keeps `draft_label`/`draft_preview` (no `regex`) and `diff_view` keeps `preview_lines`/`file_lines` over the view's `DiffLine`, each with the original's tests. To drop them: have the engine send the draft's label and preview in `UiEvent::ToolCallDelta`, and move the two diff helpers to marv-core.
- **Rendering differences from Ink (#9).** Markdown is parsed by pulldown-cmark, not marked: it has no GFM bare-URL autolinks, so `markdown::autolink` finds `http(s)://` URLs in text (`www.` and emails aren't linked). Wrapping follows wrap-ansi as Ink called it, except that the row after an exactly full row doesn't start with the separating space. Tabs are drawn as two spaces (a buffer cell is one column). The quote bar `▎` marks a quote's first row only, as Ink drew it. A diff line that serde can't read fails the whole message's parse (Marv filtered bad lines while drawing); the engine's session loader handles that.

## The command palette (#44)

ctrl+k opens it from the prompt, empty or half-typed, idle or while a reply streams. It replaces the prompt panel while open; the prompt keeps its text underneath, so Esc (or ctrl+k again) goes back to it as it was. Choosing a command or a toggle doesn't touch the typed text either. A value setting that prefills (`Step limit` → `/steps `) does replace it, and the replaced text goes into the prompt history (↑ brings it back).

- **ctrl+k was free.** `PromptInput` types nothing for ctrl/alt + a letter (ink-text-input's behaviour, kept), and the App bound only ctrl+c and ctrl+o; there is no kill-line to shadow. Setup (which has its own text fields) still gets every key first.
- **Never over an approval** (nor the session picker or setup): ctrl+k does nothing there, and an approval, the session picker (`/resume`'s list arriving after ctrl+k) or setup that arrives while the palette is open closes it; they also get keys before it (#113, Greptile: a hidden palette took the picker's keys).
- **"Always" answers queued requests in its scope, never a `once` or `must_ask` one** (a file change in a home-folder project, a host command, a protected path, egress after untrusted content): that one is still shown and asked, with its warning (`always_leaves_a_queued_once_request_in_the_same_scope_to_ask`, `always_leaves_a_queued_must_ask_request_in_the_same_scope_to_ask`). The view's `ApprovalRequest` carries `must_ask` for this.
- **Approvals arm after `APPROVAL_ARM_MS` (400 ms; #113, a behaviour change from Marv).** Closing the palette wasn't enough: an Enter typed for the palette (or the prompt, the same race Marv had) just as an approval appears would answer it with its default, Yes. Each newly shown approval (each new head of the queue, so a double Enter can't answer the next one either) ignores Enter and ↑/↓ until armed; Esc, ctrl+c and PgUp/PgDn over a file list work at once. It looks the same while arming, and needs no deadline: the clock is checked when a key arrives.
- **One list.** The `/` menu and the palette are built from `SessionPort::commands()`; `CommandInfo` gained `kind` (command or skill) and `while_busy`. Settings come from marv-session's settings table (`commands::settings()`, next to the commands), which borrows each command's description. A toggle's action is the command line that flips it (`/yolo off`) and a picker's is its command (`/model`), so the palette sends `SessionPort::run_command` exactly what typing would: the saving and the notice stay in the command's action.
- **While busy.** Entries whose command only shows something or sets a value from the next turn (`Command::while_busy`: `/help`, `/cost`, `/config`, the toggles that are read at turn start…) run during a reply; the rest are dimmed with "(after the reply)", and Enter says so. Esc in the palette only closes it (the next Esc stops the reply); ctrl+c closes it and interrupts.
- **Shortcuts** are `command_palette::SHORTCUTS`, listed and not run; keep them in step with README's Keys table and `/help` (marv-session can't see this crate, so `help_text` has its own short list).

## The shell (#10): measured CPU and known gaps

**CPU** (`examples/fake_session` in a pty via `script`, `top -b -n 3 -d 2 -p <pid>`, 120×40; the fake streams ~4 chars every 10 ms):

| build | idle (martian on screen) | streaming, first seconds | streaming, 20 s in |
|---|---|---|---|
| release | 0.0 / 0.0 / 0.0 % | 0.0 / 1.5 / 2.0 % | 5.0 / 1.5 / 1.0 % |

The streaming reply's finished lines are laid out once (only the unfinished last line is re-wrapped each frame); without that, debug climbed past 30% as the reply grew.

**No `terminal.clear()` at start:** it asks the terminal for the cursor position, and a terminal that never answers (a bare pty) would stop the TUI starting. The alternate screen starts blank.

**Gaps for the engine / other issues:**
- `UiEvent::ToolStart` carries no arguments, so a subagent's view can't show its task (Marv's first user message in `AgentLog`). The engine should send it (e.g. a `prompt` on `ToolStart` for `agent`, or a first `Subagent` event).
- Marv routes a pasted OAuth callback address (`isCallback`) to the pending login *before* the busy check and keeps it out of the prompt history. The App sends `/…` lines and messages as typed; the callback check needs a `SessionPort` hook (or the engine catches it in `send`), and the history should skip it.
- `marv -c`'s "Loading your last session…" (a message typed while the session loads waits) is the engine's to sequence: it should hold `send` until `Resumed`.
- Herdr state reporting (blocked / working / idle) is marv-cli's; the App exposes `busy()` and the approval queue but no hook yet.
- Engine messages get the App's own ids (`UiEvent::Message`'s id is replaced), so restored and new ids never collide.
