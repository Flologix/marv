# marv-provider

The seam between Marv and LLM vendors: the `Provider` trait, the OpenRouter (OpenAI-compatible) and Ollama adapters, SSE/NDJSON parsing, retries, error messages, model lists and provider factories.

Spec: Marv `CLAUDE.md` bullets **Provider seam** and **createProvider**, `src/provider/*.ts`, and `tests/{sse,retry,openai-compat,ollama,models,provider-index,provider-factory}.test.ts`.

## Port notes

- **HTTP:** `reqwest` 0.12 with `rustls-tls`, `stream` and `json`, and no default features. That means no OpenSSL and a single static binary. `Response::bytes_stream()` feeds `sse::parse_sse` (OpenRouter) or `ollama::NdjsonDecoder` (Ollama). Build one `reqwest::Client` per provider and reuse it.
- **Timeouts:**
  - OpenRouter keeps a timeout: 30 s to connect, 300 s per read (reqwest's `read_timeout`, not a total one). It sends keep-alives while it works, so the timeout only catches dead connections.
  - Ollama must not have a total timeout: it sends nothing while the model writes a tool call, and Bun's 300 s limit cut long calls off. A connect timeout is fine.
- **Cancel:** every `stream` races its I/O against `StreamOptions::cancel` with `tokio::select!`. A cancelled stream ends quietly, with no `Error` event. That includes a cancel during a backoff wait (`retry::sleep_abortable`).
- **`stream` returns a `'static` stream.** The adapter copies the history before returning, so the caller can keep appending to its own (and #64 can extend the copy). The returned stream is a channel fed by the retry loop's future (`openai_compat::channel_stream`): the future runs inside the stream, with no spawned task, so dropping the stream drops the request.
- **Prompt cache:**
  - Request bodies are typed `Serialize` structs, so field order is byte order. Don't route them through `serde_json::Value`: another crate could switch on serde_json's `preserve_order` feature through feature unification and silently change key order.
  - `ToolCall::arguments` is sent as the raw text (OpenAI). Ollama needs an object, so it's parsed there; Ollama's cache is local, and Marv does the same.
  - `extra` body fields (`reasoning`) are flattened last.
- **Retry semantics to keep:**
  - The `Retry` event's `attempt`/`max` are n/2, and it comes before each new attempt.
  - `Retry-After` is honoured only as whole seconds, at most 30.
  - Ollama's "unparsable tool call" 500 is retried once and doesn't count as a connection retry.
  - A stream that ends without `[DONE]`, a `finish_reason` or Ollama's `done` line counts as a drop.
  - Invalid JSON in a chunk also counts as a drop (Marv's `JSON.parse` throws into the same catch).
  - After 3 attempts: `"<label>: the stream ended early, before the reply was complete. Try again."`.
- **Network errors (#107):** `retry::retriable_failure` decides. A certificate error (`UnknownIssuer`, `BadCertificate`…) is never retried, though reqwest flags it as a connect error. Otherwise reqwest's `is_connect`/`is_timeout`/`is_request`/`is_body` decide, then `retry::is_network_error` on the whole `source()` chain: Marv's (Bun's) wording plus hyper's and rustls' (`fatal alert`, `BadRecordMac`, `DecryptError`, `close_notify`, `unexpected eof`, "connection closed before message completed"). A pooled connection whose TLS session broke fails on send with `BadRecordMac`; that used to end the turn.
- **Errors inside the stream (#107):** an error object after the 200 is retried like a drop when `errors::transient` says a fresh attempt may get past it (code 408/429/500/502/503/504/52x, or no code and a message like "aborted", "timed out", "overloaded"). After the last attempt the provider's own message is the error. Anything else still ends the turn.
- **Idle timeout (#88):** `openai_compat::STREAM_IDLE_TIMEOUT` (75 s, `OpenAiCompatOptions::idle_timeout`; `None` keeps only the 300 s read timeout). `retry::idle_guard` ends the body with `BodyError::Stalled` when no bytes at all arrive in that time; keep-alive comments count as bytes, so a slow but alive provider isn't cut off. A stall is retried like a drop (#64: kept or continued) and its `Retry` event has `cause: RetryCause::Stalled`. Ollama has none: it sends nothing while a model writes a tool call.
- **`max_tokens` (#96):** OpenRouter requests send `openai_compat::max_tokens_for(model list's top_provider.max_completion_tokens)`: that, at most `DEFAULT_MAX_TOKENS` (32,000, what opencode sends), and the default when unknown. `ProviderFactory::make` and `create_provider` take the whole `ModelInfo` for this (was its reasoning support only), and the session remakes the provider when the list knows the limit. It goes after `tool_choice`, before the extra fields; it isn't part of the prompt, so the cache holds. A 4xx naming `max_tokens`/`max_completion_tokens` resends without it; only when it also says the field is unsupported ("unsupported", "unknown parameter", "unrecognized", "extra inputs are not permitted"…) does the provider leave it out from then on. Any other refusal ("max_tokens exceeds the remaining context") drops it for that request only. **#116:** `OpenAiCompatOptions::context_length` (the model list's `context_length`) clamps it per request with `openai_compat::Room::cap`: at most the window minus the prompt's estimate (body bytes × the highest prompt-tokens-per-byte measured from a reply's `usage.prompt_tokens`, `ASSUMED_TOKENS_PER_BYTE` = 0.25 before any; + 5%, `ollama::PROMPT_MARGIN`), never above the model's limit; when that room is under `MIN_MAX_TOKENS` (1024, or the model's limit if smaller) `cap` returns `None` and the request goes without `max_tokens` (a cap that small would only be refused). The session remakes the provider when the list gives the window (`ModelInfo.context`), not only reasoning or the output limit. A subagent type naming another model gets `factory.make(Some(model), None)`: no window, so no clamp (only the refusal path). The `Room` is shared by every stream of the provider. OpenRouter's "maximum context length is W tokens. However, you requested about T tokens (… N in the output)" (`window_refusal`) records W and T−N against the body's size and resends once with the fitted cap (later requests keep it), or without one when the refit would repeat the refused cap or there's no room; a second refusal in the same stream, or one without those numbers, resends without `max_tokens`. Neither counts as a connection retry. Ollama keeps its own cap (`num_predict`) and sends no `max_tokens`.
- **`reasoningEffort` (marv-rs #143):** `ProviderConfig::reasoning_effort` (the user's config, through `SessionInit`/`SessionOptions` for a `ProviderOption` and `Config::provider_config` for the TUI's factory). `reasoning_for` sends `{"effort": …}` wherever the model reasons: with `/think` on, and to a model whose reasoning is mandatory (thinking off on an optional one still sends `{"enabled": false}`; an unknown model still gets nothing). The config's default is `medium` (`config::DEFAULT_REASONING_EFFORT`; `"default"` sends none, as before). With none, a model that always reasons picks its own: GLM-5.3-flash's is far above what coding needs (one question: 672 reasoning tokens with nothing sent, 0 at low or medium, 103 at high; SWE-bench: 4x the output tokens Codex got from the same model; at medium Marv resolved the same 7/10 with 37% fewer output tokens and 30% less cost, low was no cheaper and slower). The SDK's `SessionOptions::reasoning_effort` defaults to none: a library uses what it's given. A subagent naming its own model is made without model info (`factory.make(Some(model), None)`), so it gets no reasoning field at all, as with `enabled` before. The session's first turn waits up to `LOOKUP_WAIT` (3 s) for a model list still on its way (`lookup_done`), since the turn's provider is fixed for the whole turn.
- **Degenerate replies (#96):** `degenerate::DegenerateGuard` watches each attempt's text and reasoning deltas (not tool-call arguments), plus the readable `text`/`summary` of `reasoning_details` blocks in chunks that carry no plain `reasoning` (the blocks are kept unchanged). When the last 16 KB of either is at least 99% whitespace, or one piece of at most 64 bytes repeated, the request is aborted (`Read::Degenerate`), the attempt is thrown away (`Retry { continued: false, cause: Degenerate { discarded } }`, no backoff), and the request is sent once more with `degenerate::DEGENERATE_NOTE` as a user turn after the history. A second degenerate reply sends `ProviderEvent::Discard { cause }` (the loop throws the attempt away, no new request) and then the error, so none of it reaches the history or the trajectory, and `discardedBytes` covers both attempts. Both adapters.
- **Retry causes:** `marv_core::ProviderEvent::Retry` and `LoopEvent::Retry` carry `cause: RetryCause` (`Dropped`, `Stalled`, `Degenerate { discarded }`). The trajectory's `request` record (or `error`, when the request never succeeded) adds `retries`, `stalled`, `degenerate` and `discardedBytes`, each left out when unset; the tally is closed when the reply ends, usage or not.
- **Ollama `/api/show`:**
  - Concurrent streams ask once. They hold a `tokio::sync::Mutex` and re-check `Measured::trained` after taking it.
  - A failed or empty answer leaves the window as configured and is asked again on the next stream.
  - The configured `context_length` is always the upper bound.
- **`RetryTiming`** replaces Marv's global `retryTiming.scale`. Pass it in the adapter options; tests set `scale` to something like 0.001.
- **Tests that need a server** run against `tests/support/mod.rs`: a hand-rolled HTTP/1.1 responder on 127.0.0.1 (chunked bodies that can end cleanly, drop the connection mid-body, reset it (RST) mid-body or before replying, stall then end, trickle in at a pace, or hang). The oracle's fake server is script-driven, so it didn't fit.

## Planned improvements (Marv issues, not in Marv yet)

- **#56 cache_control breakpoints:**
  - `openai_compat::needs_cache_breakpoints` decides by model id: `anthropic/*` and `google/gemini-*`.
  - `to_messages(.., breakpoints: true)` marks the system prompt and the last message.
  - Every other message keeps exactly the bytes it has without breakpoints (tested).
  - Still to do: measure the cache-hit rate before and after, as the issue asks. Check that an assistant message with only `tool_calls` (empty content) is handled sensibly. Today it stays unmarked, because Anthropic rejects an empty text part.
- **#57 reasoning round-trip:**
  - `Delta::reasoning_details` is collected and emitted as `ProviderEvent::Reasoning` before `Done`.
  - `to_messages` re-sends it as `reasoning_details` on the assistant message.
  - Open question: OpenRouter may split one block over several chunks (same `index`). Check whether the blocks must be merged before they're sent back.
- **#59 `tool_choice: "none"`** is in `ChatRequest` and is sent only for `ToolChoice::None`. Auto requests keep their bytes. Ollama has no equivalent, so it relies on the note.
- **#63 overflow recovery:** `errors::is_context_overflow` is a stub. Collect real OpenRouter and Ollama overflow messages first.
- **#64 continue after a dropped stream (done in both adapters):**
  - `retry::drop_recovery` decides: a drop after text arrived, with no tool call in progress (`ReplyAssembler::tool_call_in_progress`; Ollama: a call already arrived), continues; anything else restarts.
  - Continue: the next attempt sends the history, then the partial text as an assistant turn, then `openai_compat::DROPPED_STREAM_NOTE`. Its `Retry` event says `continued: true`, so the loop keeps the text and appends the rest. Partial text accumulates over several continued drops.
  - Restart: the original request again, with `continued: false`, and the loop discards the attempt.
  - A status or connection retry repeats the last request, and says `continued` when partial text is being kept.
  - `DROPPED_STREAM_NOTE` is duplicated from `marv_agent` (agent depends on provider). `marv_agent` should re-export the provider's.
  - **Jitter:** backoff waits get up to 25% added at random (`openai_compat::JITTER`, `jittered`); `Retry-After` waits are taken as given.
  - Still planned: about 6 attempts for 429/overloaded, and a longer `Retry-After`. Marv's tests expect 3 attempts for 429, so this waits for the spec.
- **#90 how a request ended (marv-rs):**
  - `ProviderEvent::Usage` is `(Usage, marv_core::ReplyEnd)`: the vendor's finish reason always, `raw_response` only when `StreamOptions::debug_raw` was on (`MARV_DEBUG_RAW`, the trajectory's `request` record carries both).
  - OpenRouter: the usage chunk is held and emitted in `ReplyAssembler::finish`, after the tool calls — the finish-reason chunk often arrives after the usage chunk, and the record wants both together. Only with a usage chunk (no phantom requests for servers that don't report usage). Ollama: the `done` line carries usage and `done_reason` together, so it emits there.
  - "The raw last response" is the last attempt's payloads (OpenRouter: the SSE `data` payloads; Ollama: the NDJSON lines) — a retried attempt starts fresh, so a dropped attempt's partial payloads are discarded with it. An unparsable payload is collected too: that's what the recording is for.
