# marv-oracle

A dev crate (not shipped): the fake OpenAI-compatible server, the scenario runner, normalization, diffing and the prompt-cache prefix check behind `tests/oracle/`, plus the tracker MCP fixture. It runs any `marv` binary on a scripted model and diffs what it did against recordings from TypeScript Marv.

Spec: `tests/oracle/README.md`; Marv's `evals/run.ts` (the workspace setup), `evals/tasks/*` (the seed tasks) and `evals/mcp/tracker.ts` (the MCP fixture); the wire format Marv's adapter reads, `src/provider/openai-compat.ts` and `src/provider/sse.ts`; `src/headless.ts` for the `stream-json` events and exit codes.

## Port notes

- **The binary is a parameter** (`MARV_ORACLE_BIN`, or `--bin`). The same scenario records from TypeScript Marv and checks marv-rs.
- **Isolation.** The run never sees the user's setup: `HOME` and `MARV_CONFIG_DIR` are temp folders, and the environment is cleared except `PATH`, because Marv's `resolveConfig` lets `OPENROUTER_API_KEY`, `MARV_MODEL` and `MARV_MAX_STEPS` beat the config file. Personal skills in `~/.marv/skills` would otherwise change the system prompt.
- **Defaults off:** trajectories, diagnostics (the typecheck after edits) and project checks. They write outside the project or run tools the script didn't ask for. A scenario's `run.json` `config` can turn them on.
- **Requests: two checks, neither asks marv-rs for Marv's bytes** (changed from the first version, which compared request bytes with TypeScript Marv's and so would have forced marv-rs onto Marv's key order):
  - *Against the recording, as canonical JSON:* keys sorted, `cache_control` breakpoints (#56) out, a marked message counted as its plain text, and the top-level `max_tokens` out (#112: marv-rs caps each reply, Marv #96; Marv's recordings have no such field, and the value is marv-rs's own choice). Every other value must match. Key order and breakpoints are left to each implementation, so marv-rs's sorted schema keys (`PORTING.md`, "Serialization") pass, and serde_json `preserve_order` isn't needed.
  - *Against the run's own previous request, as bytes (`prefix.rs`):* the prompt cache only needs each run's requests to extend one another. Every message of the previous request must be in the next at the same index with the same bytes, and every other field must be byte-identical. `cache_control` markers don't count (they move to the last message by design), and neither does `tool_choice` (#59's wrap-up sends `"none"`). A compaction rewrites the history on purpose, so `run.json` `prefix_resets` names the request after it. Recordings keep this rule too: TypeScript Marv passes it in every scenario, and a recording that breaks it is refused.
  - Still, don't turn `preserve_order` on in this crate: Cargo unifies features across the workspace, so it would change every crate's serialization in `cargo test --workspace`. The tracker keeps its key order with its own small ordered JSON type instead. `serde_json`'s `raw_value` feature is on (for the byte spans `prefix.rs` reads); it only adds a type.
- **Events compare as JSON values**, one canonical line each. `JSON.stringify` and serde order keys differently, and an event's field order means nothing to a consumer.
- **Worktree subagents (#12).** A worktree's branch and folder end in a random id, and its folder sits under the project key (a hash of the temp path). After the run, `worktree_names` lists `<config>/worktrees/*` (→ `<project-key>`) and the project's `refs/heads/marv/*` branches (`marv/<slug>-ab12` → `marv/<slug>-<id>`). A branch without commits is deleted by Marv, so a scenario whose subagent changes nothing can't name its branch. `git_init` also writes `user.name`/`user.email` into the project's repository: Marv commits for the subagent, and the run's git has no global config.
- **No real model, no money.** The server binds `127.0.0.1` only. A request past the end of the script gets a 500, which the binary reports as an error, so an extra request shows up in the diff instead of hanging. The tracker is local and writes only its own `out.json`.
- **Recording guards:** a run that timed out, left replies unused or broke the prefix rule isn't saved.
- **`.gitignore` in a project** is stored as `gitignore.oracle` (in `project/` and `expect/files/`) and renamed by the runner: under its real name it would apply to this repository and hide the scenario's own files. The non-ignored test fails if one slips in.
- **The tracker** is a subcommand of the `marv-oracle` binary (`marv-oracle tracker <data> <out>`), found next to the test (`target/<profile>/`). Its specs are the TypeScript tracker's `tools/list` answer, byte for byte (`tests/oracle/mcp/tracker-tools.json`). It doesn't validate arguments against the schemas, which the TypeScript's SDK does with zod; scripted calls send valid ones.
- **Not planned: a declined approval.** `marv -p` never asks: with no `--approve`, a call outside yolo is refused ("there's no one to ask", `refused-approval`), and `--approve` answers "yes" or "unavailable", never "no". A decline only happens in the TUI.
- **No test runs in the scripts.** The eval tasks' real models run `bun test`, but its output carries timings and Bun's version, which no normalization makes stable. The scripts read the tests instead, and use `git diff --stat` where a check is wanted.
- **`.gitattributes`** in `tests/oracle/` turns off line-ending conversion, so the CRLF and trailing-space fixtures stay byte-exact.
- **Output goes through `marv_core::printable()`**: diffs and stderr carry model and tool text.

## Deliberate marv-rs differences

marv-rs is held to TypeScript Marv's recordings except where it differs on purpose. Each difference names its Marv issue, or, for a marv-rs security rule no Marv issue asked for, its `docs/SECURITY.md` section. Only a marv-rs check (`Target::MarvRs`, the default for `check`) applies them; TypeScript Marv is always checked against `expect/` exactly.

- **How a scenario declares one.** `run.json` gets `"deliberate": {"issue": N, "why": "…"}` (or `{"security": "<SECURITY.md section>", "why": "…"}`: exactly one of the two), and the scenario gets `expect.marv-rs/` (the same layout as `expect/`). Add `script.marv-rs.jsonl` when the difference changes what the model is asked, so its scripted answers differ too. Loading fails if one is there without the other, so no override is silent. A marv-rs check reads `expect.marv-rs/` (and that script). `expect/` stays TypeScript Marv's recording.
- **Recording one:** `marv-oracle record --target marv-rs --bin $PWD/target/debug/marv <scenario>`. marv-rs refuses to record a scenario without `deliberate`, so it can't overwrite one of Marv's recordings. Check the recording by hand against what the issue says before committing it.
- **Which target.** `MARV_ORACLE_TARGET` (`marv` or `marv-rs`), or `--target`. Without one, `check` means marv-rs and `record` means TypeScript Marv. So checking TypeScript Marv now needs `MARV_ORACLE_TARGET=marv`.

The differences:
- **#64 continue after a dropped stream** (`dropped-stream`, `expect.marv-rs/` and `script.marv-rs.jsonl`). The retry sends the partial reply as an assistant turn plus `DROPPED_STREAM_NOTE`, and the model's scripted answer is only the rest ("xt in upper case."). The result says the sentence once, the second request extends the first (the prefix rule holds), and the files and exit code are Marv's. With Marv's script, whose retry repeats the whole reply, the text would be doubled.
- **MCP results fenced as data** (`docs/SECURITY.md`, "Provenance and taint"; `mcp-comment` and `mcp-fix-from-issue`, `expect.marv-rs/`). Every MCP tool result reaches the model, and the `tool_end` event, wrapped in `<untrusted-data source="mcp" from="<tool>">…</untrusted-data>`. Checked by hand when recorded: with the fence taken out, the events and requests are Marv's line for line, and the files and exit code are identical.
- **Fenced check notes** (`ts-new-type-error`, `expect.marv-rs/`, declared under `docs/SECURITY.md`, "Provenance and taint"). The typecheck's note is Marv's own sentence, then tsc's output inside `<untrusted-data source="project">`, where Marv began it `Marv:`. Only `requests.jsonl` differs (requests 4 and 5); events, files and exit code are Marv's.
- **#59 wrap-up at the step limit** (`step-limit`, `expect.marv-rs/` and `script.marv-rs.jsonl`). With no one to say "keep going", marv-rs sends one more request: Marv's step-limit note, `tool_choice: "none"`, the same tools. The script's 4th reply is the wrap-up, which becomes the result's `reply` (`steps` 4). Checked by hand when recorded: the first three requests, the files and the exit code (2) are Marv's; the reason is still `max_steps`.
- **#85 the plan wording** (every scenario that offers `plan`, no override). The system prompt's plan sentence and the `plan` tool's description are reworded (four or more steps; each update in the same reply as the next tool call). `runner::MARV_RS_TEXT` lists each (marv-rs, Marv) pair, and the canonical comparison puts Marv's text back in the system message and the tool descriptions, so the rest is still checked byte for byte; the raw requests keep marv-rs's text for the prefix rule. Like `MARV_RS_SECTIONS` (`# Your situation`), the pairs are copies: keep them in step with `PLAN_SENTENCE` and `PLAN_DESCRIPTION`. A rewording is one line here instead of re-recording 34 scenarios.
- **#58 parallel read-only calls** (every scenario, no override). The `tool_start`s of a reply's reads come together, and their `tool_end`s arrive as each finishes, which varies from run to run, so a recording can't pin it. For marv-rs, `compare::calls_in_order` puts each run of consecutive tool events back in call order (each start, then its end, matched by tool and label) in both logs before comparing. A sequential log is unchanged by it. The results, requests, files and exit code are still compared as they are.

## Marv behaviours the recordings pin
marv-rs must match these, or note the difference with an issue number:
- **The second tool loop** answers the calls it skips with the cut-off note (`NOT_RUN.cutOff`), not a loop note (`tool-loop`).
- **Requests that aren't steps.** `steps` counts replies that ended in text or tool calls, so these don't count:
  - an empty reply's retry and nudge: `steps` is 1 in `empty-reply`, while the usage covers 3 requests;
  - a text loop's dropped reply (`text-loop`);
  - the compaction's summary request: `steps` is 2 in `mid-turn-compaction` with 3 requests. The usage includes the summary's tokens.
- **A dropped stream's `text_delta`s** are already printed before the retry (`dropped-stream`; marv-rs continues instead, #64 above). A 429's retry prints nothing (`rate-limited`).
- **Compaction events.** The summary request streams no `text_delta`. The turn shows `status: compacting` then `compaction {compacted: true}`, and no second `status: running` (`mid-turn-compaction`).
- **The MCP scenarios pin `mcpTools: deferred`** (marv-rs #87). Marv deferred the tracker's 25 tools (4,654 tokens) past its 4000-token limit; marv-rs offers them directly up to 8000. The recordings are Marv's deferred runs, so `run.json` asks for deferral and they keep checking that path. The direct path is tested in `marv-session` (`turn_tests`).
- **Deferred MCP labels.** For `tool_search` and `mcp_call`, `tool_start`'s label is the raw arguments JSON (`{"names":[…]}`, `{"tool":…,"arguments":…}`), while `tool_end`'s is the tool name(s) (`mcp-fix-from-issue`, `mcp-comment`).
- **An MCP tool called by its own name** (`mcp__tracker__add_comment`) runs as `mcp_call`. The stream shows `tool: "mcp_call"`, and the result ends with Marv's note that it isn't offered as a tool of its own (`mcp-comment`).
- **`status: waiting_for_mcp`** comes before `status: running` whenever an MCP server is configured (the MCP scenarios).
