# Changelog

All notable changes to Marv are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and Marv uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html). While it's below 1.0.0, a minor version (0.**x**.0) may contain breaking changes; a patch version (0.1.**x**) never does.

What counts as Marv's public API: the `marv` command's flags, subcommands and slash commands (and, up to 0.3.0, the SDK, `@flologixai/marv/sdk`), and the files it reads (`~/.marv/config.json`, `.marv/skills/`, `.marv/agents/`, `.mcp.json`, `AGENTS.md`, saved sessions).

## [Unreleased]

### Fixed

- **A TLS error mid-request no longer ends the turn (#107).** `received fatal alert: BadRecordMac`, `DecryptError`, a peer closing without TLS's `close_notify`, and any request reqwest says failed while connecting, sending or reading the body are now retried like a dropped connection (the partial reply is kept or continued, #64). A certificate error (`UnknownIssuer`, an expired certificate…) still isn't: retrying can't fix it.
- **An upstream error sent inside an OpenRouter stream is retried (#107).** When the provider behind OpenRouter aborts, times out or is overloaded after the reply started (`{"error":{"code":502,"message":"The operation was aborted"}}`), Marv retries like a dropped connection instead of ending the turn; if every attempt fails, the provider's own message is shown. A refused request (a 400, an auth error) still ends the turn at once.
- **A stalled stream is retried after 75 s instead of 300 s (#88).** A stream that sends nothing at all (not even OpenRouter's keep-alives) for 75 s is retried like a dropped connection. Trajectory `request` records now say `retries`, `stalled: true`, `degenerate: true` and `discardedBytes` when a request took more than one try.
- **A runaway reply is stopped (#96).** OpenRouter requests send `max_tokens`: the model's output limit from the model list, at most 32,000 (32,000 when the list doesn't say). A provider that refuses the field, or can't fit it beside a long prompt, gets the request again without it (and later requests leave it out only when the provider said the field isn't supported). And a reply whose last 16 KB of text or reasoning is only whitespace, or one short piece repeated, is aborted and asked again once with a note; a second one ends the turn with a clear message (OpenRouter and Ollama).
- **A symlinked `AGENTS.md` can no longer pull a file from outside the project into the prompt.** Marv 0.4.0 read `<project>/AGENTS.md` through any symlink, so `AGENTS.md -> ~/.ssh/id_ed25519` sent the key to the model provider. Instruction files are now read only where their real path stays inside the project (#62).
- **`marv -p --approve mcp` approves MCP calls after an MCP read again.** Once a session had read anything from an MCP server, a call made through `mcp_call` (the deferred tools) was refused as "needs the user's approval", because the wrapper asked under its own name instead of the real tool's scope (`mcp:<server>:<tool>`); in the TUI it asked twice. The real tool still asks once the session is tainted, even in yolo, and without `--approve mcp` the call is still refused.
- **`mesh_list` no longer taints the session when nothing is wired.** Every `mesh_list` result counted as text from another agent, so asking "who's on the mesh?" made every later network command, web request and MCP call ask first, though no other agent had said anything. Now only a list that names wired receptacles (whose descriptions can come from another Marv) taints, as a call's answer and an inbox message do.
- **Omarchy's skills load (#75).** Omarchy links `~/.marv/skills/omarchy` to `/usr/share/omarchy/…`, and Marv refused it as a folder leading outside `.marv/skills`. A personal skill folder may now be a symlink to a folder only root can change (it and every folder above it owned by root and not writable by a group or everyone); the skill is read from there, and `/skills` shows where (`omarchy → /usr/share/omarchy/…`). A link to any other folder, such as `~/.ssh` or the project, is still refused, and so is any such link in a project's `.marv/skills`. A link inside the linked folder still can't lead out of it.
- **Starting Marv in `~` no longer reports every skill problem twice.** There the project's `.marv/skills` is the personal one, and it was scanned twice.
- **A Marv that was killed no longer leaves its mesh socket behind.** `$XDG_RUNTIME_DIR/marv/mesh/` collected a socket for every Marv that didn't exit cleanly; a Marv joining the mesh now removes the sockets nothing listens on.
- **The Herdr adapter tests no longer fail under load (#92).** Their fake `herdr` script could be run while another test's child process still had it open from being written, and Linux refused with "Text file busy". The tests now wait until the script can be run. This was in the tests only: Marv's behaviour hasn't changed.
- **The test suite no longer leaves temp folders in `/tmp` (#89).** Every `cargo test` run left about 120 folders behind (MCP and file-lock test folders that were never removed, checkpoint folders removed too early and then recreated, a TUI test's folder recreated by the session's background `git gc`), and on a machine where `gh` installs itself on first use, a 40 MB fake home per end-to-end test: the `gh auth status` probe timed out and its installer kept writing after the test had cleaned up. A dev machine collected about 6,000 folders and 6.7 GB, which filled the `/tmp` quota and broke other tools in confusing ways. The tests now remove what they make even when they fail, the end-to-end tests turn the GitHub probe off, and CI fails when a test run leaves `marv-*` or `mx-*` folders in `/tmp`.

### Changed

- **An approval ignores Enter and ↑/↓ for its first 400 ms (#113).** A key typed for the prompt or the command palette just as an approval appeared could answer it, and Enter answers Yes. Esc and ctrl+c still decline at once; the prompt looks the same.
- **At the step limit, `marv -p` and subagents reply with a wrap-up instead of stopping dead (#59).** When no one can say "keep going" (a subagent at its 50 steps, `marv -p` with or without `--approve`), Marv asks the model once more, with tools off, to say what it finished, what's left and the next step. That summary is what `marv -p` prints and what the parent agent reads as the subagent's report. The exit code is still 2 and the reason still `max_steps`; the tools are still sent, so the prompt cache holds. A call the model makes anyway is not run. The TUI's "Keep going?" is unchanged.
- **Skills load when the task is clearly their kind, not on every request (#84).** The system prompt said to load a matching skill before starting, and a skill whose description claims every task ("use when starting any conversation") then took over even a one-line fix: on GLM, runs that loaded one were 2.3× slower, with a whole test-driven loop for a small edit. Now the model judges by the task, and small, direct requests skip skills.
- **`mesh_list` names the other Marvs on this machine**, with the inbox a `mesh_send` would use and a note that the user has to wire it first. Before, the model only saw "nothing is wired", and answered "who's on the mesh?" with nobody while `marv mesh ls` listed several. Names only: their folders and panes stay in `marv mesh ls`.
- **`mesh_list` shows the agents in Herdr panes that can be wired, and your own address (#76).** In Herdr it lists each agent pane with the agent Herdr sees there, its state, the Marv in it if any, and its `herdr.pane.<pane>.send` and `.status` receptacles, under "Can be wired", so a model asked to get another agent to do something uses the mesh (one approval) instead of guessing names or running the `herdr` CLI itself. It also says the caller's inbox and the name another Marv sends to (`peer.<marv>.agent.<agent>.inbox`), so it can tell a peer where to reply. With nothing wired, its hint now names the forms that reach another Marv or a Herdr pane, not `agent.<name>.inbox`. Only plain identifiers from Herdr are shown (a pane's given name and folder stay in `marv mesh ls`), so the list doesn't taint the session; a slow or missing Herdr is skipped after 1.5 s. `mesh_call`'s example receptacle is a real one now (`herdr.pane.w1-p2.status`).

### Added

- **Command palette on ctrl+k (#44).** One fuzzy search over the slash commands, skills, settings and keyboard shortcuts, matched on name and description and grouped by kind. It opens at any time from the prompt: what you've typed stays and comes back on Esc, and while a reply streams the entries that don't need to wait (showing things, most toggles) still run, while the others say "after the reply". Settings show their current values: Enter on `Yolo: off`, `Sandbox: on`, `Thinking: …` and the other toggles flips it, saved and announced exactly as the slash command does; `Model` opens the model picker and `Step limit` puts `/steps ` in the prompt. Shortcuts are listed, not run. It never opens over an approval, and an approval closes it. The `/` menu and the palette share one list, so a new command shows up in both. `/help` and the README's Keys table mention it.
- **More instruction files (#62).** Besides the project's `AGENTS.md`, Marv now reads the project's `CLAUDE.md` when there's no `AGENTS.md` (never both), the `AGENTS.md` of each parent folder up to the git root (a monorepo's `packages/` and root files), and your own `~/.marv/AGENTS.md` for every project. Each comes under its own heading with its path, nearest first; the 20,000-character limit now covers them all, the project's file first. A folder below the project with its own `AGENTS.md` or `CLAUDE.md` gets it into the conversation the first time `read_file`, `edit_file` or `write_file` touches a file there, once, as a note on that result (the system prompt, and so the prompt cache, never changes). Subagents get the same files, yours included. The startup notice lists the files when there's more than the project's `AGENTS.md`, and the welcome banner counts them. An instruction file whose real path leads out of the project (a parent's: out of the git root), to a secret (`.env*`, `*.pem`, `id_*`), or into `node_modules`, `target` or `.git`, or that isn't a regular file, isn't read, and the startup notice says why; nested files under those folders are never read. Editing a folder's `AGENTS.md` brings its rules along (the edit's result doesn't show the file), and after a compaction the folder rules come again.
- **Tool arguments are repaired against the tool's schema (#65).** A number or boolean sent as a string (`"limit": "20"`), an object or list sent as a JSON string, a single value where a list is wanted, `null` for an optional field, and a field the tool doesn't have (another harness's `head_limit`) no longer cost an error round trip: the call runs with the repaired arguments, and the result says what was repaired in a `Marv:` note, so the model learns. Only cases with one reading are repaired; `"20abc"` for a number still fails as before. MCP tools get the type repairs only (unknown keys are dropped only when the schema forbids them), on direct calls and through `mcp_call`, so `get_issue` with `{"number": "12"}` reaches the server as `12`. And an MCP call missing a required field, or with a string shorter than its `minLength`, is refused with the field's name before the server is called, instead of, say, posting an empty comment.
- **An idle Marv can start a turn when a mesh message arrives (#78, opt-in).** `/mesh wake on` (or `"mesh": {"wake": true}` in `~/.marv/config.json`) lets a message on a wired inbox start a turn while the TUI is idle, so another agent no longer has to type into this Marv's pane to get its attention. The woken turn reads the message the way every turn does: fenced as data from another agent, never as your instructions, and the conversation counts as tainted (network, web, MCP and mesh calls ask, even in yolo). The transcript says who woke it ("Woken by a message from peer-alpha on agent.parent.inbox"). Off by default. Never during a turn or while an approval waits (the turn reads it, or it wakes a turn once that turn ends), at most 3 wake-ups a minute per wire (over that, you're told once and the messages wait), and never in `marv -p` or after you quit. A message you type just as a wake-up starts isn't lost: it runs when the woken turn ends. `/mesh` shows what's wired to Marv's inbox and whether wake is on.
- **Real-model evals (#73).** `evals/bench.py` runs Marv's 20 eval tasks through `marv -p`, and through `claude -p` for comparison, grades them with each task's hidden tests, and reports pass rate, time, requests, tool calls, tokens and cost. See `evals/README.md`.

## [0.4.0] - 2026-10-14

Marv, rebuilt in Rust. The version goes from 0.3.0 straight to 0.4.0: this release is the Rust build, plus the Sprint 4 work that was unreleased in the TypeScript code, plus what's new in the Rust build. It replaces the TypeScript code in this repository. The behaviour is Marv's: an oracle of 30 scenarios recorded from the TypeScript Marv (the eval tasks and the agent loop's edge cases) checks that the Rust build does the same things, and that its requests keep the prompt cache.

### Changed

- **Marv is one static binary.** Written in Rust, built for Linux x86_64 and aarch64 (static musl). No Bun or Node runtime runs Marv any more, so nothing reads the project's `.env`, `bunfig.toml` or `node_modules` when it starts.
- **`npm install -g @flologixai/marv` installs the prebuilt binary.** The binary for your machine comes as an optional dependency (`@flologixai/marv-linux-x64` or `@flologixai/marv-linux-arm64`, picked by npm), with no postinstall script and no download at run time; the package's `marv` is a small Node launcher that starts it. Or install without npm: `install.sh` from the GitHub release downloads the binary, checks its SHA-256 against `SHA256SUMS`, and puts it in `~/.local/bin` (`--prefix`, `--version`, `--from <your build>`, `--uninstall`).
- **The terminal UI is new (ratatui instead of Ink), and light.** It idles near 0% CPU and streams at a few percent (the Ink interface used 40–60% of a core per session). Replies are revealed at an even pace instead of in clumps as the network delivers them, and the reasoning preview wraps whole words in a fixed-height box, so it types along a row instead of jumping. Everything else works as before: the martian, Markdown, diffs, approvals, pickers, mouse scrolling and drag-to-copy, the `/` menu.
- A new system prompt section, `# Your situation`, tells the model what it can't do from where it is: it has no screen and can't open a window, terminal or pane; the user sees a one-line summary of each tool call, not its output; a program that draws shows nothing in a sandboxed command; commands don't run inside the user's terminal or multiplexer. When no tool can do what's asked, it should say so and give the user the command, and keep replies short, without a closing menu of options. It's fixed per session, so the prompt cache holds.

### Added

- **The mesh: sandboxed agents that can talk** (see the README's "The mesh"). Each Marv runs a switchboard outside every sandbox; an agent reaches it through a Unix socket mounted into its sandbox (so it works with no network), and the model gets `mesh_list`, `mesh_send` and `mesh_call`. Nothing is wired by default: a wire is a grant from one agent to one receptacle (an inbox, a Herdr pane) in one mode, the first use asks you, yolo never wires, and an agent can't wire itself. A message reaches the model fenced as data from another agent and taints the session; each is logged to the trajectory (sender, receptacle, size, never the body), with size and rate limits per wire.
  - A Marv's subagents get a plug with no wires, so the parent and its workers can message each other once you wire them.
  - Several Marvs on one machine: every interactive Marv is on the mesh under `MARV_MESH_NAME` (or the project folder's name and four hex digits), with a private socket in `$XDG_RUNTIME_DIR/marv/mesh/`. `marv mesh ls` lists them. `marv mesh wire 'api -> web:inbox'` asks for a wire, and a wire to another Marv is approved on both ends.
  - Herdr: in a Herdr pane, each Herdr agent pane is a receptacle: `herdr.pane.<pane>.status` reads its state, and `herdr.pane.<pane>.send` types a prompt into it, only while that agent is idle or done.
  - Other agents: `marv mesh plug <marv>` is a stdio MCP server, so Claude Code or opencode in another pane can plug in and be wired like any agent.
  - `marv -p` is on the mesh only when asked: `--approve mesh:<receptacle>` pre-approves wires to that receptacle, `MARV_MESH_NAME` names the run.
- **Background processes: a `process` tool** for dev servers, watchers and anything else that should keep running after a turn (Marv #51). Each runs in its own long-lived sandbox, with a bash command's rules (only the project writable, `.git` read-only, the home folder hidden, no network unless `network: true`), until it's stopped or Marv exits, even when Marv is killed (bubblewrap's `--die-with-parent`). The ports it listens on (1024 and up, at most 4) are forwarded to your `127.0.0.1` on the same port, so `http://localhost:5173` opens in your browser, and nothing on your machine is reachable from the process; a port already taken on your machine isn't forwarded, and the model is told. `start` asks every time a new command starts (yolo too; "don't ask again" covers that exact command); `logs`, `list` and `stop` don't. Sandboxed bash commands reach the running processes on `localhost` without network or an approval, so the model can check its own server and run e2e tests against it. Processes outlive turns, `/clear` and `/resume`, at most 4 at once, with 1 MB of logs each. `/processes` lists them, `/processes stop <name>` stops one, and the status bar shows `N running`. Subagents don't get the tool (their bash still reaches the processes). `marv -p --approve process` lets a headless run start them (`--approve network` too for one on the network); they stop when it ends.
- **The `github` tool** runs the GitHub CLI for the model, outside the sandbox, with your own `gh` login (Marv #47), so "check the current project" reads PRs, CI runs and issues with nothing to set up. Offered when `gh` is installed and logged in (checked once at startup; `MARV_GITHUB=off` hides it). Reads run without asking (`pr list|view|checks|diff|status`, `issue list|view|status`, `run list|view`, `workflow list|view`, `repo view`, `release list|view`, `label list`, `search …`, `status`, `gh api` GETs); changes ask (comments, creating, editing, closing, merging, reviews, releases, re-runs, `workflow run`, `label create`, `gh api` with fields, another method or `graphql`), with "don't ask again" per command, and a merge or close names the repository; `gh api` reads of secrets, variables, keys, webhooks, installations, invitations and emails ask every time. Never run, whatever is approved: `gh auth`, `config`, `extension`, aliases and unknown commands, `secret`, `variable`, `ssh-key`, `gpg-key`, `codespace`, `gist`, `--web`, downloads, `gh api --input`/`--verbose`, `pr checkout` and `repo clone` (they run git outside the sandbox), and any GitHub host but the project's `origin`'s (GitHub Enterprise works). gh is spawned without a shell, gets your environment minus Marv's keys and other secrets (its own `GH_TOKEN`/`GITHUB_TOKEN` kept), talks only to the project's host, never prompts, and runs git without the repository's hooks; tokens in its output are redacted before the model, the transcript, the saved session or the trajectory see them. Subagents can read with it, not write. `marv -p`: reads run, changes need `--approve github`. A failed `gh` in a bash command points to the tool.
- **bash with `sandbox: false`** runs one command on your machine, outside the sandbox, as you (Marv #52), for what can't work in the sandbox (a system service, a tool under the hidden home folder, hardware). Its environment is yours minus `OPENROUTER_API_KEY`, `MARV_*` and anything secret-looking (tokens, passwords, API keys, credentials, URLs with a password), and token shapes are redacted from its output. It asks every time, in yolo too, and never offers "don't ask again"; the prompt shows "Runs OUTSIDE the sandbox, as you, with your files, network and credentials." Only the TUI opens this door: in `marv -p` (whatever `--approve` says; the call counts as refused, exit 3) and in subagents it's refused before anything is asked. With the sandbox already off the flag changes nothing. The system prompt's `# Outside the sandbox` section names only the doors the session has (`github`, `process`, this one).
- **The plan tool** (Marv #15): for a long task, the model keeps a checklist with `plan`, sending the whole list each time (items `pending`, `in_progress` or `done`, at most one in progress, at most 20). No approval: it changes nothing outside the session. The TUI pins it between the transcript and the prompt while something is left to do (`Plan 2/5`, the current item highlighted; hidden on windows under 20 rows). The plan is saved with the session and restored by `/resume` and `marv -c`, dropped by `/clear`, and appended to the summary after a compaction, so what's left survives it. Main agent only. The prompt cache holds: the tool spec and the system prompt's one sentence are fixed per session.
- **`/undo` puts back the files the last turn changed** (Marv #16). Before a turn's first call that can change files (`edit_file`, `write_file`, `bash`, a shared-folder subagent's), Marv snapshots the project's files as a git commit written through a temporary index, and again when the turn ends; a turn that changed nothing keeps none. In a repository the snapshots live under a hidden ref, `refs/marv/checkpoints/<session>`, never your branch, index or stash; outside one, in a git folder of Marv's own under `~/.marv/checkpoints/`. `/undo` shows the turn's files and their diffs (restored, deleted, recreated; files you edited since are marked, files git ignores are listed as not restored) in a scrolling list and asks yes or no; on a yes it snapshots the current state first (so the undo can be undone by hand), writes each file back itself, with its own bytes (CRLF and LFS files included; no checkout filters, no following symlinks out of the project), and tells the model at the start of your next message. `/undo` again goes one turn further back. `/checkpoints on|off` (config `checkpoints`, honored by `marv -p` too). The undo note, the checkpoint chain and the paths each turn reported are saved with the session, so a resume after a restart carries on. Trajectories get `checkpoint` and `undo` records. Old sessions' refs are pruned at a session's first turn (the 20 newest and the last 14 days are kept).
- The model is told what the sandbox can't do (Marv #50): every process a command starts ends with the command, and a sandboxed command's `localhost` isn't yours, so it must never claim a server is running for you. A command that looks like it leaves a process running in the background (`&`, `nohup`, `setsid`, a `dev`/`start`/`serve` run) gets a note that it was stopped; where the session has the `process` tool, the note and the prompt point to it.
- Read-only tool calls in a row (`read_file`, `glob`, `grep`…) run in parallel; their results still go into the history in call order.
- A reply whose stream drops after some text is continued from where it stopped, instead of being thrown away and asked for again. Retries wait a little random extra, so parallel agents don't retry in step.
- On OpenRouter, Anthropic and Gemini models get prompt-cache breakpoints (the system prompt and the last message), and a model's reasoning is sent back with its reply on the next request.
- `edit_file` also matches text that differs only in typographic quotes, dashes, `…` or Unicode spaces (when that match is unique), replacing the file's own text.
- `web_fetch` drops more hidden text before the model sees it: text hidden by common CSS classes, off-screen or in a zero-size box, zero-width and tag characters, and HTML comments in raw Markdown.

### Security

**Upgrade from 0.3.0 and earlier:** they could run code from an untrusted project folder outside the sandbox ([GHSA-46rh-hh68-rhv9](https://github.com/FlologixAI/marv/security/advisories/GHSA-46rh-hh68-rhv9)). 0.4.0 fixes this; the older versions are deprecated on npm.

Hardening from a review of 0.3.0, kept as rules with a test each (`tests/guards/`, one test per rule in `docs/SECURITY.md`, each shown to fail when its guard is removed):

- **The project never configures Marv.** No runtime starts with Marv, so the project's `.env`, `bunfig.toml`, `node_modules` and the like are never read on the way in. Marv's settings come only from `~/.marv/` or a `MARV_CONFIG_DIR` set in your real environment.
- **Protected paths always ask, even in yolo** and even after "don't ask again": `.git/` (any level) and the `core.hooksPath` folder, `.env*`, `.envrc`, `bunfig.toml`, `.mcp.json`, `AGENTS.md` and `CLAUDE.md` at any level, `.marv/`, `.vscode/`, `.idea/`, and `package.json`'s lifecycle `scripts` (a dependency edit doesn't ask). They're read-only inside the sandbox, and one a sandboxed command creates is found and taken back. Paths are checked after following symlinks, dangling ones included.
- **Taint tracking.** Once web, MCP or mesh content is in a session, everything that can send data out asks, in yolo too and whatever was remembered: a command with network, every MCP call (read-only ones included), a web request under a new address prefix ("don't ask again" then covers that prefix, not the whole site), a mesh message on a wire not yet approved. Subagents start tainted when their parent is, and never inherit its network, web or mesh approvals.
- **Untrusted text is fenced.** Tool results are tagged with where they came from; text from outside (web pages, MCP results, mesh messages, project checks and the typecheck) reaches the model fenced as data, never in Marv's voice.
- **Skills are read after `realpath`.** A skill's files and folders can't lead outside it through a symlink, as no tool can follow one out of the project.
- **Nothing from the model reaches the terminal raw**, `marv -p`'s text output included: escape sequences, control characters and bidi overrides are stripped first.
- **MCP:** a project server's trust covers its entry and the project files its command runs; `npx`/`uvx` servers start outside the project folder; a server's `instructions` are ignored.
- The sandbox's `/run` is empty except for Marv's own sockets, and credential files under the mounted toolchain folders (`~/.cargo/credentials`, git's credentials file) are masked.

### Removed

- **Breaking: the TypeScript SDK, `@flologixai/marv/sdk`.** The npm package now holds only the `marv` command. Scripts and other agents use `marv -p` (`--output text|json|stream-json`) or the mesh.
- **Breaking: no macOS build yet.** 0.4.0 ships for Linux (x86_64 and aarch64, WSL included); `install.sh` and the npm launcher say so on other systems.
- **Breaking: project MCP servers need trusting once more.** The trust key is now a hash of canonical JSON, so trust given by 0.3.0 doesn't match.

### Known limitations

- On `/resume` and `marv -c`, the transcript shows your messages and the replies, not the tool entries and notices.

## [0.3.0] - 2026-10-12

Everything since 0.1.2: Sprints 1–3 (0.2.0 was never released on its own). Highlights: headless mode (`marv -p`), MCP servers installed with `/mcp add` and logged in with `/mcp login`, deferred MCP tool loading, project checks, tool-call repair, retries for dropped connections, a loop guard, and the step limit.

### Added

- `/mcp login <server>` logs in to a remote MCP server that asks for an OAuth login, instead of a token in `headers` (issue #18). Marv opens your browser (or, over SSH or without a display, shows the link: paste the address the browser ends up on into the prompt; it goes to the login, never to the model, and shows as `(login callback)`), receives the code on `127.0.0.1` with PKCE and a random `state`, stores the tokens in `~/.marv/mcp-tokens.json` (0600, per server URL; a project's server gets its own login) and connects; new tools reach the model from the next message, as `/mcp trust`'s do. The MCP SDK renews the access token by itself, also across several Marv processes sharing the file. Only `/mcp login` opens a browser or registers Marv with a server: at startup a server without a login shows as `needs login` (in the MCP notice and `/mcp`), and one whose refresh is refused mid-session says so once and its tools fail with "`<server>` needs a new login: the user can run /mcp login `<server>`". `/mcp logout <server>` forgets the login and revokes it where the server allows. Servers without dynamic registration take your own client in the entry: `"oauth": { "clientId", "clientSecret": "${VAR}", "callbackPort", "scope" }` (`scope` overrides the scope the server suggests). `/mcp add` says when a remote server will need a login, and ends with "/mcp login `<name>`". The SDK and `marv -p` use and refresh stored logins, and warn about a server that needs one (`onWarning`, once per server: at startup or when its login runs out mid-turn). The README's "Connect GitHub" keeps the token as the simple path and shows the OAuth-app alternative. Two Marv processes never lose each other's logins (`mcp-tokens.json` is locked across each update with `mcp-tokens.json.lock`: one holder at a time, a holder refreshes it while it works and removes only its own, and a lock untouched for 10 s is a crashed process's, taken over under a second guard file so two waiters can't both take it), and a token file Marv can't read (a newer format, a hand edit) is never written over: the login fails, saying so. A call that arrives while a login reconnects the server goes to the old connection or gets Marv's sentence, never a closed-client error; an untrusted project server refuses `/mcp logout` as it does `/mcp login`. A login cancelled by `/mcp remove`, `/mcp logout`, a new `/mcp login` or quitting stays cancelled even after the browser came back: a token exchange that finishes late saves nothing and never brings a removed server back.
- Startup problems (skills that didn't load, PATH folders the sandbox can't see, a cut AGENTS.md, MCP config problems, agent files) now appear as ONE distinct, colored notice block instead of separate plain paragraphs: a left bar and a bold title in the worst tone's color, "Startup · N notes", with a short headline per problem and its details indented beneath. MCP servers that later fail or wait for `/mcp trust` get their own ("MCP · N notes") block once they're known. Notices live only in the transcript (drawn by a new `NoticeView`); the model never sees them, and saved sessions keep them (a session saved before notices still loads).
- `/mcp add <source>` sets up an MCP server for you (issue #6): an npm package (`@scope/name`, `name@1.2.3`, `npm:`), a PyPI one (`pypi:<name>`, run with `uvx`), an https URL (plain http only to localhost), a name from the official MCP Registry, or a GitHub repository whose README names one of those. Marv pins the exact version (`npx -y <pkg>@<version>`), shows one yes/no approval with the command line, version, publish date, publisher, stated repository, registry namespace, every environment variable the server reads and the exact JSON it writes (with warnings for deprecated or yanked versions, packages first published in the last week, and a README naming a package from another repository), writes exactly that JSON to `~/.marv/mcp.json` (0600, every other entry kept), and starts the server in the running session: no restart. Secrets only as references: `--env NAME` writes `"NAME": "${NAME}"`, `--header "Authorization: Bearer ${TOKEN}"`; typed-in values are refused, and so is a registry entry whose header has a fixed value (only `${VAR}` references are written) or whose argument value starts with `-` (it could be read as an option to npx/uvx). `--name` and server arguments after `--` too. A name one of this project's servers uses is refused before the approval (pick another `--name`), since that server is running under it. `/mcp search <words>` lists the registry's latest active entries; `/mcp remove <name>` takes one of your servers out and stops it; both lock `~/.marv/mcp.json` across Marv processes for the whole read-change-write, so two terminals adding servers at once both keep theirs. The TUI now always has an MCP manager, so the system prompt's MCP paragraph is there even before the first server, and the system prompt suggests `/mcp add` instead of hand-written JSON. Not supported yet: Docker images, building from source, SDK and headless use.
- Docs and a skill for working with GitHub (issue #27): the README's "Connect GitHub" section walks through connecting GitHub's official MCP server ([github/github-mcp-server](https://github.com/github/github-mcp-server)) in `~/.marv/mcp.json` with a fine-grained token read from the environment (`${MARV_GITHUB_TOKEN}`), explains why the `gh` CLI can't work inside the sandbox (no network, hidden home, cleared environment — don't mount `~/.config/gh`), and shows how to limit the server's toolsets with `GITHUB_TOOLSETS` (optional now that deferred tool loading keeps the cost down, still worth it for small models). `examples/skills/github/SKILL.md` (copy into `~/.marv/skills/`) teaches Marv to use the MCP tools instead of `gh`, follow the branch → PR → merge-commit workflow, and never ask for or print tokens. `tests/github-docs.test.ts` runs the section's configs through Marv's own MCP parser and loads the skill with the skill loader, so the docs can't drift into something that doesn't parse.
- Headless mode (`marv -p "<prompt>"` or `marv run <prompt>`): one non-interactive turn in the current folder, built on the SDK. Prints the final reply to stdout; `--output json` outputs a JSON object with the reply, reason, steps, and usage; `--output stream-json` outputs each event as a JSON line. Exit code 0 for a finished turn, non-zero otherwise. Approvals: without `--approve`, only yolo-safe calls run. See `--help` for all options. `--approve` never answers the step limit's "Keep going?": `--max-steps` stops the turn (exit 2) whatever is approved, and an invalid `--max-steps` (`abc`, `-1`) exits 1 rather than falling back to the saved limit. A call refused inside a subagent counts too (exit 3, listed in `refused`); with `-c`, `usage` is the turn's own, not the resumed session's totals; a configured Ollama host and context length are used. (issue #38)
- With many MCP tools connected, Marv no longer sends every tool's full schema with every request (issue #14). Past min(4000 tokens, 10% of the context window), and when it saves at least half, the model gets the tools' names in a note at the start of its first message, loads a tool's parameters with `tool_search` when it needs it, then runs it with `mcp_call` (approvals, "don't ask again" scopes and yolo's rules are the real tool's, unchanged). Fewer tokens per request, a shorter tool list for small models, and the prompt cache holds when a server is trusted mid-session (its tools are announced in the next message instead of changing the tool list). A direct call to a listed `mcp__` tool runs as `mcp_call`, and `arguments` sent as a JSON string are read as the object, each with a note. Decided once per conversation and saved with it. Config and SDK option `mcpTools`: `auto` (default), `deferred`, `eager`; `tool_search` and `mcp_call` are taken names for your own SDK tools. Trajectories record the decision on `turn_start` (`mcpTools`) and each note (`mcp_note`).
- Evals: `--mcp-tools auto|deferred|eager` and `--mcp <servers.json>`, a 25-tool issue-tracker MCP server for evals (`evals/mcp/tracker.ts`), and three tasks that use it: `mcp-fix-from-issue` (fix the bug an issue describes), `mcp-comment` (make a change, then comment on an issue; the check reads what the server recorded) and `mcp-unused` (the server connected but never needed: what its specs cost). `--report` gains prompt tokens per request, and MCP calls per run when there are any.

- An output-heavy eval task, `failing-suite`: a one-line bug (a leftover debug filter dropping every other entry) whose failing `bun test` floods the transcript with a many-hundreds-of-lines diff, plus a hidden check over a different log.

- Both providers (OpenRouter and Ollama) retry a request that failed on the network (connection refused or reset, socket closed, timeout, HTTP 502/503/504 and 429 with `Retry-After`) up to 3 times with backoff (1 s, 4 s, 10 s), showing "Connection lost, retrying…" as a `retry` event that the transcript shows. If the stream had already sent part of a reply, that part is dropped and the whole request is redone, so the prompt cache isn't affected. Esc stops the retries. (issue #36)
- Loop guard: Marv stops a model stuck in a loop. A reply repeating the same sentence (8+ times in a row, checked while it streams) is stopped at once and dropped: none of it, and none of its tool calls, reaches the conversation, and the model is told to take another approach. A tool call repeated with the same result as last time (the same call three times, or two calls alternating) is answered with a note instead of running again; a call that gets a new result each time (the next item from a queue) is new work, not a loop. If the loop goes on after the note, the run stops, and the transcript says why. With `maxSteps: 0` (no step limit) this is what stops a stuck unattended run.

- Project checks (issue #41): a project's rules as code in `.marv/checks/`, one file per rule, either declarative (YAML or JSON: a `glob`, a `forbid` or `require` regular expression, a `message` and a `why`) or a bun script (`*.ts`, its `// glob:` comment first) that prints violations as JSON lines `{file, line, message, why}`. After a step that changed files, Marv runs the checks whose glob matches a changed file, the way it runs the typecheck (in the sandbox, the project read-only, no network, a timeout, never asking), and tells the model only the violations that are new since the turn began, with their why, in the same message as the typecheck's. An obeyed or unrelated check costs nothing. `/checks` lists them, what couldn't be loaded and the last result; `/checks on|off`, config `checks`, SDK option `checks` (on by default; nothing runs without the folder). Session events: `checks`; trajectories: `check` records with `source: "checks"`. The SDK exports the `ProjectCheckResult` and `Violation` types. Marv's own repository has four: the system prompt built only in the constructor and `clear()` (prompt cache), a file that lost more than half of its committed lines (Sprint 1's truncating `write_file`), imports with their `.ts` extension, and `incrementalRendering: true` in Ink's options. A check edited during a turn runs as it now reads after the next step (compared with what the turn began with); a script's `// glob:` may use brace lists (`src/**/*.{ts,tsx}`); a script's output is read as it arrives and capped at 1 MB (past it, the check failed); the README's example check parses.
- `write_file` has `append: true`: add content at the end of an existing file instead of replacing it (the cut-off notes and the system prompt now point there for writing a long file in parts, instead of `edit_file`); a file that doesn't exist is just created, and a last line without a newline gets one first, which the result says.
- Development: every push is reviewed by Open Code Review (`ocr`). A git pre-push hook (`.githooks/pre-push`, turned on by `bun install` unless another hooks path is set) runs `bun run review` and refuses pushes with critical or high-severity findings, or when the review couldn't run. It covers any author, human or agent.
- After the model changes files in a TypeScript project, Marv runs the project's typecheck (in the sandbox, read-only) and tells the model about errors its changes added, anywhere in the project, so it fixes the callers it broke before saying it's done. `/diagnostics on|off`, config `diagnostics`, SDK option `diagnostics` (on by default). Needs the sandbox, a `tsconfig.json` in the folder Marv starts in, and the project's own `typescript` (or tsgo) in that folder's `node_modules` (a global tsc isn't used). The SDK also exports the `CheckResult` and `TsError` types.
- Herdr support: in a [Herdr](https://herdr.dev) pane, Marv tells Herdr what it's doing, so Herdr's sidebar shows it working, waiting for your approval, or done, and `herdr agent list`, `get`, `read` and `wait` see it. Nothing to set up. Herdr 0.8.2 doesn't yet let `herdr agent prompt` or `send-keys` drive agents it doesn't have built in; `herdr pane send-text` and `send-keys` do.
- Malformed tool calls from weaker models are repaired where the meaning is beyond doubt, instead of bouncing back as an error (issue #10): invalid JSON gets raw control characters in strings escaped and parsed again; `bash`'s `timeout` given in milliseconds is divided and clamped to the maximum; a project path written with a leading slash that only exists relative to the project (`/src/x.ts`) is read as that file. Every repaired call's result says what was repaired (`Marv: …`), so the model learns the right form.
- SDK: `maxSteps` sets how many steps a turn runs before it stops (without `approve`) or asks whether to keep going (default 25).
- The step limit is configurable: `/steps` shows the interval, `/steps 40` sets it, `/steps off` (or `0`, or config `maxSteps: 0`, or `MARV_MAX_STEPS=0`) never asks — a long run just keeps going, like Claude Code's and Codex's, while subagents still stop at their own 50. Without an approver, `0` also lifts the hard stop for the main agent's turns.
- CI: a GitHub Actions workflow (`.github/workflows/ci.yml`) runs `bun install`, `bun run typecheck`, `bun test` and `bun run eval --verify` on every pull request and push to main (no API key: `--verify` only checks that every eval task's check fails before and passes with its solution). The runner installs bubblewrap and lifts Ubuntu 24.04's AppArmor restriction on unprivileged user namespaces, so the sandbox tests run rather than skip (the sandbox is Marv's main safety boundary), and the job summary says whether the sandbox really ran. Installs are cached (`~/.bun/install/cache`, keyed on `bun.lock`). `tests/ci.test.ts` checks the workflow file itself.
- A long turn compacts mid-turn: when the context is nearly full after a step's tool calls are in (`runAgent`'s new `onFull`), Marv summarizes the conversation there, not only before the next user message, so a turn with many tool calls can't outgrow the window (Ollama silently dropping old context, OpenRouter rejecting the request). A user note after the summary tells the model to continue where it left off (before a user message the message itself follows the summary). A `compacted` event says it happened, and the usual `status`/`compaction` events say how it went; Esc during it stops the turn, and a failed summary isn't tried again until the next turn.

### Changed

- An `AGENTS.md` longer than 20,000 characters is no longer just cut off (issue #40): it's cut at a whole line, and in place of the rest the model gets the headings after the cut (`#` to `###`, with their line numbers) and is told to read them with `read_file` (`offset`) when its task touches them. Names up front, content on demand, as with skills, so the system prompt and the prompt cache stay small. Marv says once at startup that the file was cut and which sections the model gets by name. `read_file` now shows a long line whole when asked for one line (`limit: 1`; a read of a few lines shares 30,000 characters between them, a long read still cuts lines at 500), and the cut tells the model so; Marv's own AGENTS.md has bullets of several thousand characters on one line. Marv's own CLAUDE.md now puts Commands, Conventions and the prompt-cache rule before the architecture notes, which are grouped under `###` headings.
- The waiting line says "Checking…" (not "Checking types…") while the checks after a step run. SDK: `SessionInit.checks` is now the project checks' switch; the typecheck's test hook is `SessionInit.typecheck`.
- When a sandboxed command without network fails in a way that looks like the missing network (DNS errors, refused connections, timeouts, or tools like `gh`, `curl`, `git fetch` and `npm install`), the model is told the sandbox blocked it and to retry with network on, instead of taking, say, `gh auth status`'s "invalid token" for real. For a failed `gh` command the note adds where to actually go: the GitHub MCP server (`~/.marv/mcp.json`), not another login, and never mounting gh's config into the sandbox (issue #27).

### Fixed

- `/resume` and `marv -r` list sessions saved in the same millisecond in the order they were started, instead of whichever file the folder listed first. It made a test flaky on fast machines (the first CI run on `main`).
- In a git worktree (`.git` is a file pointing into the main repository's `.git`, usually in the hidden home folder), git now works in the sandbox: the worktree's record and the repository's `.git` are shown read-only, and the `.git` file can't be changed. They're only shown when the `.git` file checks out the way git checks it (the record points back at it, under `<repo>/.git/worktrees/`), so a planted `gitdir:` can't show an outside folder to commands that run without asking.
- Tools installed with mise or asdf are visible in the sandbox again: `~/.local/share/mise` and `~/.asdf` join the toolchain folders the sandbox mounts from the hidden home (they hold installs, plugins, shims and downloads, not credentials — nothing to mask). Before, a `node` from mise was on `PATH` but invisible inside the sandbox, so `#!/usr/bin/env node` launchers (every `node_modules/.bin` script, like tsc) failed with `env: ‘node’: No such file or directory`: the post-edit typecheck never ran and reported nothing, and the TypeScript eval tasks couldn't run on such a machine. A `PATH` folder under the home folder that no toolchain mount shows is now reported at startup and by `/sandbox` (with what to do about it), instead of tools failing silently. When a typecheck dies because its interpreter is missing, the notice says that ("tsc needs node, which the sandbox can't see") instead of "unreadable".
- File tools read a path starting with `~/` as the home folder, not a folder named `~` in the project (outside the project it's refused, as any other path there). `edit_file` no longer suggests `write_file` for a missing file whose folder doesn't exist either, which led a model to create a stray copy instead of editing the real file.
- A file rewritten with `write_file` showed only removed lines in the collapsed diff (and the approval prompt). It now shows the first few removed lines, then the start of the new file, also with ctrl+o for a rewrite of more than 400 lines.
- SDK: a rejected API key or an unknown model no longer says to run `/setup` or `/model`; the error names the option to change instead (`provider.apiKey`, `provider.model`).
- Ollama: the cap on each reply shrinks to the room the prompt leaves in the context window, so in a long conversation the prompt plus the reply no longer outgrow it (the cap had been a fixed share of the window, up to half with thinking on).
- Ollama never runs a model past the context length it was trained for: `/api/show` reports it (`model_info.*.context_length`), and the configured `contextLength` (still the upper bound — Ollama can't tell what fits in VRAM) is capped at it, for `num_ctx`, the reply cap, and the context-usage report.

## [0.1.2] - 2026-10-08

### Security

- The sandbox no longer exposes the host's `/run`. It had been mounted read-only, but a read-only mount doesn't stop a process from connecting to the sockets in it. A sandboxed command (which runs without asking in yolo mode, the default) could reach the user's D-Bus session and start programs outside the sandbox with `systemd-run --user`, and could reach the GPG and SSH agents, the keyring, the display and docker's socket. `/run` is now an empty folder in the sandbox. Only the folders on `PATH` and the DNS config that live there are shown again, read-only. Affects 0.1.0 and 0.1.1: update with `npm i -g @flologixai/marv@latest`.

### Changed

- The system prompt always explains how to set up an MCP server (where the config goes, its format, and that `~/.marv` isn't reachable from the sandbox), so the model hands you a correct config instead of inventing keys.

## [0.1.0] - 2026-10-06

The first public release, on npm as `@flologixai/marv`.

### Added

- A full-screen terminal UI with streaming Markdown replies, mouse-wheel scrolling, drag-to-copy and a `/` command menu.
- An agent loop with tools: `read_file`, `glob`, `grep`, `edit_file`, `write_file`, `bash`, `web_fetch`, `memory`, `skill` and `agent`. It asks before continuing past 25 steps, retries an empty reply, and never runs a tool call cut off at the output limit.
- `edit_file` matches forgivingly (trailing whitespace, indentation), keeps CRLF line endings, and shows the closest lines when nothing matches. `edit_file` and `write_file` say when a change breaks the file's syntax.
- Providers: OpenRouter (any tool-capable model) and Ollama (local models), with a model picker and `/think`.
- A bubblewrap sandbox for commands on Linux, and yolo mode (on by default): sandboxed commands and edits in the project run without asking; everything else shows a diff or the command first.
- `web_fetch`: web pages as Markdown, and GitHub repositories, folders and files through GitHub's API.
- MCP servers (stdio and Streamable HTTP) in Claude Code's `.mcp.json` format; a project's servers start only once trusted (`/mcp trust`).
- Skills (`.marv/skills/`), subagents with Claude Code-compatible agent types (`.marv/agents/`), optionally in their own git worktree, and memory across sessions.
- Saved sessions (`marv -c`, `marv -r`, `/resume`), automatic and `/compact` compaction, and token and cost tracking (`/cost`).
- Trajectory logs with feedback (`/good`, `/bad`, `/label`) and `bun run stats`.
- The SDK: `createSession()` from `@flologixai/marv/sdk` runs Marv from code, without the UI.
- Evals: `bun run eval` runs real models on small tasks with hidden checks.
